# 2026-09-21 — 판정은 495건 쌓여 있었고, 집행하는 사람이 없었다

## 0. 한 줄

**`authoritative` 등급으로 서빙되던 495건이 «근거가 틀렸다»고 이미 판정돼 있었다.**
판정은 2026-09-15 에 끝났고, 그것을 집행하는 경로가 없어 엿새 동안 그대로 나갔다.

## 1. 어떻게 드러났나

경보와 집행기가 **서로 다른 말을 하고 있었다.**

```
backlog-watch   anchor-contradicts-type 위반=495 (도입시 0, Δ+495)
anchor-withdraw 조회 40 · 철회 0
```

둘 다 맞았다. 판정은 저장돼 있었고(`kwave_kdb_anchor_audit`), 집행기는 그것을 읽지 않았다.
`DrainWithdrawWrongAnchors` 는 `AuditPersonAnchors` 로 **새로 조회할** 대상을 고르는데,
그 감사는 30일 신선도를 지켜 이미 본 것을 다시 보지 않는다(`AnchorAuditFreshness`).
9/15 에 전량 감사를 돌렸으므로 그 뒤로 감사기는 아무것도 돌려주지 않았다.

**판정하는 자리와 집행하는 자리가 다르면, 판정은 쌓이고 아무 일도 일어나지 않는다.**

## 3. 고친 것

### 3-1. 저장된 판정을 집행하는 경로 (`anchor-enforce`)

정책은 새로 만들지 않았다. 무엇을 자동으로 떼고 무엇을 검수로 보내는지는
`DrainWithdrawWrongAnchors` 가 9/15 dry-run 으로 정한 그대로다 — `name-element` 만 자동,
나머지는 검수. 쓰기도 같은 `withdrawOneAnchor` 를 쓴다.
**바뀐 것은 대상을 어디서 고르느냐 하나뿐이다.**

```
kdb-app anchor-enforce [N] [go]      기본 dry-run · 외부 호출 없음
```

운영 실행 결과:

```

2회차 철회 0 (멱등)
되돌림 기록 kwave_kdb_recheck_log(verdict='anchor-withdraw') 32건
```

등급강등이 24건인 이유: 나머지 8건은 tmdb 등 **다른 권위 ref 가 남아 있어** 등급을
유지하는 것이 맞다. ref 를 뗐다고 무조건 내리지 않는다.

검수로 보낸 463건(type-mismatch 278 · human-on-character 139 · not-human 19 · fictional 1)은

지우고 틀린 유형을 남긴다(씨스타19·엠블랙이 그 예다). 사람이 가린다.

### 3-2. ★경보가 자기 사유를 부정하고 있었다

32건을 철회한 직후에도 불변식은 **495 그대로**였다. 불변식이 «판정이 있는가»만 보고
«그 근거가 아직 붙어 있는가»를 안 봤기 때문이다. 감사 행은 «언제 그렇게 판정했다»는
기록이라 남는 것이 맞고, 위반인지는 **ref 가 아직 붙어 있는가**가 정한다.

둘 다 고쳤고 **시험으로 묶었다** — 이 결함의 원인이 「세는 자리」와 「집행하는 자리」가
다른 모집단을 본 것이므로, 다시 갈리면 시험이 막는다.

```
TestAnchorEnforcementMatchesInvariant    불변식의 술어 3개를 집행기가 다 보는지
TestAnchorAutoWithdrawIsNameElementOnly  자동 철회가 name-element 를 넘지 않는지
```

가드가 무는지 실제로 확인했다 — 집행기에서 술어를 하나 빼니 파일명과 함께 FAIL 했다.

고친 뒤 실측: **위반 438** (495 중 57 은 ref 가 이미 없다 — 내 32 + 이전 정리분 25).
