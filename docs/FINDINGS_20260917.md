# 2026-09-17 — codex 를 켜면서 드러난 것들

오너 지시 두 가지를 반영하는 과정에서 나온 발견을 적는다.

> "api 는 사용하지 않고, cli 에이전트로 사용한다."
> "인정해" (음역을 정본 표기로 인정할 것인가에 대한 답)

## 1. codex 가 어제 안 켜진 진짜 이유 — 모델 이름에서 `sol` 이 빠졌다

오너는 처음부터 **"5.6 sol low"** 라고 말했다. 내가 `CODEX_MODEL=gpt-5.6` 으로 적었다.

ChatGPT 계정(구독) 경로에서는 모델이 제한된다. 실측:

```
gpt-5.6          400 "not supported when using Codex with a ChatGPT account"
gpt-5            400  같음
gpt-5-codex      400  같음
gpt-5.1-codex    400  같음
codex-mini-latest 400 같음
────────────────────────────────────
gpt-5.6-sol      ✓ 정상 동작
```

`--model` 을 아예 빼면 기본값이 `gpt-5.6-sol` 이다. 그래서 이름을 안 주면 되고, 주려면
정확히 `gpt-5.6-sol` 이어야 한다. compose 기본값을 바로잡았다.

### auth.json 은 사람이 만드는 파일이 아니다

어제 나는 오너에게 "auth.json 을 넣어 주세요"라고 요청했다. **틀린 요청이었다.**
그 파일은 `codex login` 이 만든다. 필요한 것은 파일이 아니라 로그인이다.

```
codex login --with-api-key      API 키 방식 (오너 방침상 사용 안 함)
codex login                     ChatGPT 계정 브라우저 로그인 → ~/.codex/auth.json
```

오너 맥에 이미 ChatGPT 로그인이 있어(`codex login status` → `Logged in using ChatGPT`)
그 인증을 서버로 옮겼다. 컨테이너에서 `Logged in using ChatGPT` 확인.

코드는 이미 `OPENAI_API_KEY` 를 자식 프로세스 env 에서 **명시적으로 제거**한다
(`codexcli.go` `sanitizedEnv`) — API 모드로 새지 않는다. 오너 방침과 코드가 일치한다.

## 2. 원장이 판정자를 안 적는 분기가 **일곱 곳** 있었다

codex 를 켜고 첫 판정을 보니 이랬다:

```
검증 결과 현재 값이 정확: The current English title matches …
```

누가 판정했는지가 없다. 어제 `by` 를 붙이면서 분기를 빠뜨렸다. 고치고 "여섯 곳"이라고
커밋했는데, **내가 만든 테스트가 일곱 번째를 찾았다**(`finalizeApply` 안의 보호값 경로).

```
verify.go  current 분기               라벨 없음
verify.go  빈칸 가드                  modelLabel()(설정값)을 적고 있었다
verify.go  finalizeApply 보호값 경로   라벨 없음  ← 테스트가 찾음
review.go  다섯 분기                  전부 라벨 없음
```

**사람이 분기를 세는 방식은 실패한다.** 그래서 소스를 읽는 테스트 두 개로 잠갔다:

- `TestEveryLedgerBranchNamesTheJudge` — 원장에 쓰는 모든 분기가 `by` 를 달아야 한다
- `TestModelLabelIsNotWrittenToLedger` — 설정값은 원장에 못 들어간다

### 실증

```
codex 검증 결과 현재 값이 정확: The established official English title is
"Confidential Assignment 2: International," … "Cooperation 2" is a literal
mistranslation, not the title used by English-language media.
```

`codex 검증` 이라 적혀 있고 **이번엔 사실이다.** 같은 날 원장에 `gemma 재검증` 도
찍혔다 — 상한 소진으로 내려간 건들이다. 둘을 구분해 적는다는 것이 확인됐다.

## 3. 음역 인정 — 프롬프트가 금지하고 있었다

종전 프롬프트(작품 유형):

```
For drama/movie/show/song_album this is the OFFICIAL LOCALIZED TITLE
(translation), **not romanization**.
```

공식 제목이 아직 없는 작품은 소비자가 음역을 보내 줘도 전부 보류로 빠졌다. 대기 25건
중 12건이 정확히 이것이고, 사유에 증거가 남아 있었다:

```
"The client suggested a romanization, but the rule…"
"There is no official or widely recognized Vietnamese…"
"The client's suggestion is a phonetic transcription…"
```

**순서를 고정해서** 허용했다 — 공식 제목이 있으면 그것이 이기고, **없을 때만** 음역을
받는다. 지어낸 음역은 여전히 거절한다. 흐리면 음역이 실제 공식 제목을 밀어내고,
그건 «빈칸 > 틀린값» 위반이다.

### 결과 (대기 25 → 7)

```
한집살림     → ハンジプ・サルリム        반영   ← 음역 인정 효과
대한민국 1교시 → Daehanminguk Ilgyosi     반영   ← 음역 인정 효과
전선야곡     → 戦線夜曲 / Battle Line Serenade  반영 (codex 검증)
오싹한 연애   → 恋は命がけ / Spellbound / Chilling Romance  반영
```

남은 7건(Stay Awake ×3, OVER X ×4)은 접수 24시간이 안 지나 재검증 대상이 아니다.
내일 자동으로 들어간다.

## 4. 보이지 않는 문자 하나가 한 달을 묶었다

「오싹한 연애」의 일본어 제목 정정이 **8월 16일부터** 운영자 대기였다. 제안값은
`恋は命がけ` 로 완벽한 일본어인데:

```
U+604B U+306F U+547D U+304C U+3051 U+FEFF
                                   ↑ BOM
```

`IsValidSpellingForLocale("ja", …)` 가 그 한 글자 때문에 거절했고, 원장에는
«ja 문자셋 가드 미통과» 라고만 남았다. **화면으로는 절대 찾을 수 없다.**

소비자는 웹에서 제목을 복사해 보낸다. BOM·제로폭 조이너·방향 표식은 그 과정에 흔히
딸려 온다. 내용이 맞는데 안 보이는 문자로 버리는 것은 오거부다. 가드를 느슨하게 하지
않고 **입력을 정리**한다(`stripInvisible`).

> 곁가지: 그 문자를 테스트 파일에 리터럴로 적었더니 Go 컴파일러가 거부했다
> (`illegal byte order mark`). 보이지 않는 문자는 사람과 도구를 동시에 속인다.
> 테스트는 전부 `﻿` 이스케이프로 적었다.

## 5. ★아직 안 고친 것 — 정정 재검증에 속도 제한이 없다

오늘 codex 를 켜고 **30분 만에 일일 상한 60회가 소진**됐다.

```
07:32  codex 라우팅 켬
07:56  codexcli: 일일 상한 소진(60/60) — gemma 로 내려간다
```

설계한 강등은 정확히 작동했다 — gemma 로 내려가고 원장에 `gemma 재검증` 으로 사실대로
적혔다. **하지만 왜 30분 만에 60회를 썼는가가 문제다.**

```
KDB_RESEARCH_INTERVAL_SECONDS = 8        (.env)
RetryStuckPending(ctx, 5)                 매 tick 5건

→ 8초마다 5건 = 분당 최대 37회 LLM 호출
```

정정이 조금만 밀리면 하루치 예산이 **2분 만에** 사라진다. 오늘은 내가 25건을 재큐해서
터졌지만, 밤사이 30건이 쌓이면 똑같이 터진다.

### 함께 봐야 할 것 — `ReapStale` 이 잘못된 컬럼을 본다

```go
// review.go:76
UPDATE kwave_kdb_corrections
   SET status='pending', resolution='검증 미완료(프로세스 재시작) — 운영자 심사'
 WHERE status='verifying' AND created_at < now() - interval '10 minutes'
```

`created_at` 은 **정정이 접수된 시각**이지 검증을 시작한 시각이 아니다. 의도는
"크래시로 verifying 에 갇힌 행 복구"인데, 이 조건이면 **접수된 지 10분 넘은 정정은
검증에 들어가는 즉시 회수 대상**이 된다. 검증이 진행 중인데 pending 으로 돌려놓으면
같은 건을 두 번 판정한다.

이 테이블에는 "verifying 에 들어간 시각" 컬럼이 없다(id·entity_id·locale·
returned_value·suggested_value·evidence_url·reporter·reason·status·resolution·
created_at·resolved_at·proposed_value). 그래서 `created_at` 을 쓴 것으로 보인다.

**고칠 방향**: `verifying_since timestamptz` 컬럼을 추가(마이그레이션)하고, verifying
전이 시 기록해 그 값으로 회수한다.

### 상한은 올렸다 (60 → 300)

> 오너 지시: "cli 를 사용하니 우선 한도 올려서 진행해봐."

60 은 **API 과금을 전제로** 정한 수였다. 지금은 ChatGPT 계정으로 돌아 토큰당 비용이
없으므로 그 근거가 사라졌다. 실측 위에 300 을 잡았다:

```
최근 14일 · LLM 판정이 필요한 정정
  일평균 13건 · 최대일 35건(09-16)
  정정 1건당 재시도 포함 약 2.5회  →  최대일 소요 ≈ 88회
실측 소진 속도
  분당 2.5회 (동시성 1~4, 오늘은 직렬)  →  300 을 다 쓰는 데 2시간
```

최대일의 3배 이상 여유이고, 몰래 사라질 수 있는 크기가 아니다.

**폭주 위험이 낮은 이유**는 상한이 아니라 실행 구조에 있다: `acquireCodexSlot` 이
동시 실행을 1~4로 묶는다(access token 만료가 임박하거나 판독 불가면 1). 그래서
`RetryStuckPending` 이 8초마다 5건을 집어도 실제 호출은 직렬로 흘러나간다.
**tick 당 건수를 줄이는 것보다 이 구조를 유지하는 것이 중요하다.**

그래도 남은 문제는 그대로다 — 정정이 크게 밀리면 300 도 몇 시간이면 닿는다. 그때
어떻게 되는지는 이미 확인했다: gemma 로 내려가고 원장에 사실대로 적힌다. 멈추지 않는다.

### 남은 양이 이제 보인다

`CodexBudgetSnapshot` 은 **소진된 순간에만** 불리고 있었다("일일 상한 소진(60/60)").
그래서 오늘 30분 만에 바닥난 것을 *바닥난 뒤에야* 알았고, 60 이 맞는 수인지 판단할
근거가 없었다. cand-evidence tick(20분)이 이제 매번 찍는다:

```
kdb.cand-evidence(tick): promoted=N contam?=N /N · 네이버예산 n/400 · codex예산 n/300
```

300 이 맞는 수인지는 **이 줄을 며칠 보고** 정하면 된다 — 또 추측하지 않는다.
그 호출이 사라지지 않게 테스트로 잠갔다(`TestCodexBudgetIsObservableBeforeExhaustion`).

> 내가 처음에 이것을 "무한 루프"라고 적었다가 실측으로 철회했다. 40초 관측에서
> `retried` 로그 0회, `n_tup_upd` 1322 고정 — 루프가 아니라 재큐 처리 중의 버스트였다.
> 다만 위 두 결함(속도 제한 없음 · 잘못된 컬럼)은 코드를 읽으면 그대로 있다.

## 6. ChatGPT 계정을 쓸 때 따로 생각할 것

API 키가 아니라 **오너 개인 ChatGPT 계정**으로 돈다. 그래서:

- 토큰당 과금은 없다. 대신 **계정의 사용 한도**를 서버가 함께 쓴다.
- 서버가 많이 쓰면 오너가 다른 곳에서 쓰는 codex 가 영향을 받을 수 있다.
- 일일 상한 60회는 **API 과금을 전제로 정한 숫자**다. 계정 방식에서는 기준이 달라진다
  — 돈이 아니라 오너의 작업 한도를 나눠 쓰는 문제다.

**이건 내가 정할 일이 아니라 오너가 정할 일이다.** 지금은 60 으로 두었다.
