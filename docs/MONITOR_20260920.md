### 고치려다 **안 고친 것** — 위키백과 근거 자동 반영 레인

막혀 있던 정정 3867(`나 혼자 산다 / zh`)을 보고 「클라이언트가 위키백과 근거를 냈는데
집는 경로가 없다」고 판단해 레인을 하나 썼다. 그리고 배포 전에 실물을 셌다:

```
위키백과 근거가 달린 미결 정정      1건
그 레인이 실제로 적용 가능한 건     0건
최근 30일 위키백과 근거 정정 40건 → auto_applied 30 · rejected 9 · proposed 1
```

**기존 경로가 이미 이 부류를 처리하고 있었다.** 3867 이 멈춘 이유도 경로 부재가 아니라
**운영자 잠금**이었다:

```
나 혼자 산다  canonical_zh = "Home Alone" [operator-locked] · operator_locked = true
              canonical_zh_hant = 我獨自生活 [correction-verified]
```

잠금은 설계상 불변이고 자동 반영 대상이 아니다. 레인을 배포했으면 아무것도 안 잡는
**조용한 0건**이 됐을 것이다 — 이 저장소가 iTunes 1,025건으로 데인 그 모양이다.
커밋을 되돌렸다.

**남는 것은 운영자 결정 하나다**: 간체 칸에 영어(`Home Alone`)가 잠겨 있고 번체 칸에는
`我獨自生活` 가 있다. 소비자가 zh.wikipedia 근거로 정정을 신고했다. 잠금을 풀지 결정이 필요하다.

### 새로 찾은 것 — 간체 칸의 로마자 25건 (자동 수리 금지)

간체 칸이 라틴 전용인데 번체 칸에는 한자가 있는 active 행이 **25건**이다:

```
김민정   zh=Winter        zh_hant=金玟廷    ← Winter 는 다른 사람 예명이다
슬리피   zh=Sleepy        zh_hant=金聖源
조슈아   zh=Joshua        zh_hant=洪知秀
스텔라장 zh=Stella Jang   zh_hant=張星銀
우즈     zh=WOODZ         zh_hant=曹承衍
```

`zh_variant_repair` 는 한자↔한자 오배치만 보므로 이 부류를 못 본다. 그런데
**t2s 로 자동 변환하면 안 된다** — 번체 칸 자체가 오염된 행이 섞여 있다:

```
룰라(group)       zh_hant=第100天    ← 노래 제목
멜로디데이(group)  zh_hant=藝仁       ← 멤버 이름
아이코닉(song)     zh_hant=伊藤由美   ← 일본 가수 이름
```

옮기면 오염이 간체 칸으로 번진다. **먼저 25건의 번체 칸을 검수해야 한다.**
검수 뒤 깨끗한 것만 t2s 로 채우는 것이 순서다.

ja 칸도 같은 모양이 **236건**이지만 판단이 다르다 — 일본어는 로마자 예명이 실제로
쓰인다(WOODZ·MAYA). 같은 규칙을 적용하면 안 된다.

## 2회차 — 2026-09-20 15:10 KST (회차 중 오너 지시: 묻지 말고 조사해서 시스템을 고쳐라)

### 근본 원인 — zhwiki 레인은 **구조적으로 한자를 못 가져온다**

1회차에서 찾은 「간체 칸의 로마자 25건」을 파고들었다. zh.wikipedia 표제가 이미 답을
갖고 있는데(`스텔라장 → 張星銀`) 왜 안 들어오는지 조건을 하나씩 갈라 봤다.

```
status/잠금 · 칸조건 · en있음 · URL있음 · QA통과   → 전부 통과
실제 기각 사유:
  기각 호시     (en-mismatch) 제목=權順榮 en=Hoshi
  기각 스텔라장 (en-mismatch) 제목=張星銀 en=Stella Jang
  기각 윤채     (en-mismatch) 제목=鄭尹彩 en=Yoonchae
```

`zhWikiVerdict` 는 **문서 제목이 canonical_en 과 다르면 기각**한다. 라틴 제목
(BIGBANG·GOT7)에는 맞는 앵커지만, **한자 제목은 정의상 en 과 같을 수 없다.**
그래서 이 레인은 이름이 「zh.wikipedia 제목 레인」이면서 한자 표기를 **한 건도**
가져오지 못한다. 매 회차 434건을 뽑아 0건을 쓴다.

9/19 에 「zh.wikipedia 제목이 있는데 기계값이 남았다 — 414건」으로 넓힌 것도
실제로 채운 것은 **라틴 제목뿐**이었을 가능성이 크다. 다음 회차에서 확인한다.

### 이번에 고친 것 — dry-run 이 거짓말하고 있었다

종전 dry 는 SELECT 를 통과한 것을 전부 「채움」으로 찍었다. UPDATE 에는 한자 조건이
더 걸려 있어 실제로 써지는 수와 달랐다:

```
종전 dry:  "채울 것 = 389건"
정직한 dry: "실제로 써질 것 = 0건"
```

389건 대부분이 `웨이커 WAKER→WAKER` 처럼 **같은 값**이거나 라틴→라틴이었다.
로그가 «389건 채움»이라 말하는 동안 원장은 한 칸도 바뀌지 않았다. 판단 근거가
거짓이면 그 위의 모든 결정이 틀어진다 — UPDATE 의 WHERE 를 Go 로 재현한
`zhWikiWouldApply` 하나를 dry 와 실제 쓰기가 **같이** 보게 했다.

### 함께 넣은 규칙 — 라틴 전용 값은 한자 표제가 덮는다

zh.wikipedia 표제(prio 6)는 wikidata-label(prio 5)을 못 덮는다. 위키데이터 라벨은
봇이 영어 라벨을 복사한 경우가 많아서, 중국어 칸에 로마자가 **영구히** 남는다.
등급은 그대로 두고 **값의 모양**을 조건으로 걸었다 — 현재 값이 라틴 전용이고 표제가
한자면 표제가 이긴다. 반대 방향(b16194b)은 그대로 막혀 있고 운영자 잠금도 불가침이다.
번체 표제는 t2s 로 변환해 간체 칸에 쓴다(9/17 에 87건 치운 「간체 칸의 번체」 재발 방지).
