### 고치려다 **안 고친 것** — 위키백과 근거 자동 반영 레인

막혀 있던 정정 3867(`나 혼자 산다 / zh`)을 보고 「클라이언트가 위키백과 근거를 냈는데
집는 경로가 없다」고 판단해 레인을 하나 썼다. 그리고 배포 전에 실물을 셌다:

```
위키백과 근거가 달린 미결 정정      1건
그 레인이 실제로 적용 가능한 건     0건
최근 30일 위키백과 근거 정정 40건 → auto_applied 30 · rejected 9 · proposed 1
```

**기존 경로가 이미 이 부류를 처리하고 있었다.** 3867 이 멈춘 이유도 경로 부재가 아니라
**운영자 잠금**이었다:

```
나 혼자 산다  canonical_zh = "Home Alone" [operator-locked] · operator_locked = true
              canonical_zh_hant = 我獨自生活 [correction-verified]
```

잠금은 설계상 불변이고 자동 반영 대상이 아니다. 레인을 배포했으면 아무것도 안 잡는
**조용한 0건**이 됐을 것이다 — 이 저장소가 iTunes 1,025건으로 데인 그 모양이다.
커밋을 되돌렸다.

**남는 것은 운영자 결정 하나다**: 간체 칸에 영어(`Home Alone`)가 잠겨 있고 번체 칸에는
`我獨自生活` 가 있다. 소비자가 zh.wikipedia 근거로 정정을 신고했다. 잠금을 풀지 결정이 필요하다.

### 새로 찾은 것 — 간체 칸의 로마자 25건 (자동 수리 금지)

간체 칸이 라틴 전용인데 번체 칸에는 한자가 있는 active 행이 **25건**이다:

```
김민정   zh=Winter        zh_hant=金玟廷    ← Winter 는 다른 사람 예명이다
슬리피   zh=Sleepy        zh_hant=金聖源
조슈아   zh=Joshua        zh_hant=洪知秀
스텔라장 zh=Stella Jang   zh_hant=張星銀
우즈     zh=WOODZ         zh_hant=曹承衍
```

`zh_variant_repair` 는 한자↔한자 오배치만 보므로 이 부류를 못 본다. 그런데
**t2s 로 자동 변환하면 안 된다** — 번체 칸 자체가 오염된 행이 섞여 있다:

```
룰라(group)       zh_hant=第100天    ← 노래 제목
멜로디데이(group)  zh_hant=藝仁       ← 멤버 이름
아이코닉(song)     zh_hant=伊藤由美   ← 일본 가수 이름
```

옮기면 오염이 간체 칸으로 번진다. **먼저 25건의 번체 칸을 검수해야 한다.**
검수 뒤 깨끗한 것만 t2s 로 채우는 것이 순서다.

ja 칸도 같은 모양이 **236건**이지만 판단이 다르다 — 일본어는 로마자 예명이 실제로
쓰인다(WOODZ·MAYA). 같은 규칙을 적용하면 안 된다.

## 2회차 — 2026-09-20 15:10 KST (회차 중 오너 지시: 묻지 말고 조사해서 시스템을 고쳐라)

### 근본 원인 — zhwiki 레인은 **구조적으로 한자를 못 가져온다**

1회차에서 찾은 「간체 칸의 로마자 25건」을 파고들었다. zh.wikipedia 표제가 이미 답을
갖고 있는데(`스텔라장 → 張星銀`) 왜 안 들어오는지 조건을 하나씩 갈라 봤다.

```
status/잠금 · 칸조건 · en있음 · URL있음 · QA통과   → 전부 통과
실제 기각 사유:
  기각 호시     (en-mismatch) 제목=權順榮 en=Hoshi
  기각 스텔라장 (en-mismatch) 제목=張星銀 en=Stella Jang
  기각 윤채     (en-mismatch) 제목=鄭尹彩 en=Yoonchae
```

`zhWikiVerdict` 는 **문서 제목이 canonical_en 과 다르면 기각**한다. 라틴 제목
(BIGBANG·GOT7)에는 맞는 앵커지만, **한자 제목은 정의상 en 과 같을 수 없다.**
그래서 이 레인은 이름이 「zh.wikipedia 제목 레인」이면서 한자 표기를 **한 건도**
가져오지 못한다. 매 회차 434건을 뽑아 0건을 쓴다.

9/19 에 「zh.wikipedia 제목이 있는데 기계값이 남았다 — 414건」으로 넓힌 것도
실제로 채운 것은 **라틴 제목뿐**이었을 가능성이 크다. 다음 회차에서 확인한다.

### 이번에 고친 것 — dry-run 이 거짓말하고 있었다

종전 dry 는 SELECT 를 통과한 것을 전부 「채움」으로 찍었다. UPDATE 에는 한자 조건이
더 걸려 있어 실제로 써지는 수와 달랐다:

```
종전 dry:  "채울 것 = 389건"
정직한 dry: "실제로 써질 것 = 0건"
```

389건 대부분이 `웨이커 WAKER→WAKER` 처럼 **같은 값**이거나 라틴→라틴이었다.
로그가 «389건 채움»이라 말하는 동안 원장은 한 칸도 바뀌지 않았다. 판단 근거가
거짓이면 그 위의 모든 결정이 틀어진다 — UPDATE 의 WHERE 를 Go 로 재현한
`zhWikiWouldApply` 하나를 dry 와 실제 쓰기가 **같이** 보게 했다.

### 함께 넣은 규칙 — 라틴 전용 값은 한자 표제가 덮는다

zh.wikipedia 표제(prio 6)는 wikidata-label(prio 5)을 못 덮는다. 위키데이터 라벨은
봇이 영어 라벨을 복사한 경우가 많아서, 중국어 칸에 로마자가 **영구히** 남는다.
등급은 그대로 두고 **값의 모양**을 조건으로 걸었다 — 현재 값이 라틴 전용이고 표제가
한자면 표제가 이긴다. 반대 방향(b16194b)은 그대로 막혀 있고 운영자 잠금도 불가침이다.
번체 표제는 t2s 로 변환해 간체 칸에 쓴다(9/17 에 87건 치운 「간체 칸의 번체」 재발 방지).

### 다음 회차에 할 것 (순서 확정)

1. **한자 제목의 앵커를 따로 만든다.** en 대조는 라틴 제목에만 쓰고, 한자 제목은
   보유 `canonical_zh_hant` 와 t2s/s2t 대조로 확인한다 — 일치하면 독립 확인 성립.
   `윤채`(제목 鄭尹彩 vs 보유 鄭允彩)처럼 **불일치는 기각**해야 한다(어느 쪽이 맞는지 모른다).
2. 9/19 의 414건이 실제로 무엇을 채웠는지 원장으로 확인
3. `김민정` 은 다른 문제다 — source_urls 에 `Winter (歌手)` 문서가 붙어 있다.
   aespa Winter 의 문서이고 김민정과 다른 사람일 수 있다. 앵커 오배치 점검 대상.

### ★내가 처음에 틀리게 읽은 것 — RSS 는 고장이 아니라 폐기다

```
kwave_news_whitelist  rss_url 보유 90곳 · poll_status='ok' 55곳
마지막 폴링 2026-07-03 23:32   (79일 전)
kdb-app env:  KDB_DISABLE_RSS_POLLING=1
```

이것을 보고 「기획의 심장이 멈췄다」고 적었다가 근거를 찾아보니 **의도적 폐기**였다:

- `f993d1c fix(discovery): 유튜브 한 페이지가 브라질 매체 5곳으로 둔갑해 매체합의를 만들고 있었다`
- `KDB_UNRESOLVED_BOTTLENECK_ALTERNATIVES_20260710.md` — 「상시 RSS 키워드 수집 = **의도적 폐기**」
- `tick.go:28` — 「on-demand 검색 발굴(research worker)로 대체 중」

매체 합의가 오염원이어서 끄고 on-demand 검색으로 갈아탔다. **기획 문서만 그대로다.**

### 그래서 진짜 문제 — 1안도 2안도 그 자리를 못 메웠다

```
폐기한 1안 (매체 합의)      0.3%
갈아탄 2안 (on-demand 검색)  2.1%   local-usage 1.9 + local-search 0.2
둘의 합                      2.4%
그 자리를 메운 것            기계값 59.9%
```

24시간 로그의 레인 활동도 같은 말을 한다 — `romanize 36 · localfill 11 · opencc 10 ·
ondemand 6` 으로 **파생·기계 레인만 돈다.** 권위 API 레인은 로그에 안 나온다.

**전어→鲭鱼(고등어) 는 이 구조의 결과다.** 현지 표기를 확보하는 경로가 2.4% 밖에
못 채우니 나머지를 기계번역이 메우고, 기계번역은 뜻을 옮기므로 종명·고유명사에서 틀린다.
레인 하나를 고쳐도 이 비율은 안 움직인다.

## 4회차 — on-demand 발굴이 왜 2.1% 인가 (3회차 1번 과제)

### 답: 처리율이 하루 ~50건인데 대상이 1.5만 칸이다

```
발굴 큐 (14일)   유입 = 종결 100%  — 큐는 막혀 있지 않다
   결말 구성     활성화 22~26% · **후보 멈춤 59~61%** · 기각 2~8%
현지표기 생산량  하루 49~54건 (9/18~9/20 원장 기준)
대상             ja 기계 6,344 · zh 기계 5,467 · ja 빈칸 1,408 · zh 빈칸 2,152 = 약 1.5만 칸
```

하루 50건으로 1.5만 칸 → **300일.** 설정은 `KDB_LOCALFILL_BATCH=10 · FANOUT=3`.
큐가 막힌 게 아니라 **삽이 작다.** 그리고 퍼낸 것의 60%가 candidate 에서 멈춘다.

### 검색 0건률 — 퍼낸 것의 3/4 을 그 자리에서 버린다

앱 재배포 직후 48분 로그 기준 localfill 13건 중 **10건이 「검색결과 0건」**.
(주의: 처음에 이것을 「24시간 13건」으로 읽었다. 앱이 48분 전에 재시작해 로그가 그때부터다.
 실제 처리율은 로그가 아니라 원장에서 봐야 한다 — 위의 하루 50건이 그 수치다.)

### 이번에 고친 것 — sogou 제거

```
2시간 로그: sogou 689줄 · wikidata 281 · mojeek 18 · wikipedia 8 · baidu 2
sogou 의 suspend 줄: 0
오류: ErrorContext('searx/engines/sogou.py', 56, ..., 'AttributeError')
```

HTTP 실패가 아니라 **엔진 코드 안의 예외**라 SearXNG 자동 격리가 안 걸린다. 매 검색마다
다시 불려 매번 같은 자리에서 터진다(345줄/시). `searxng/settings.yml` 이 2026-08-08 에
qwant 을 뺀 기준(「자동 격리를 우회하는 엔진」)과 **같은 조건**이라 같은 처방을 했다.

**정직하게**: 이건 노이즈·지연을 줄이는 위생 수정이지 0건률을 고치지 않는다.
그리고 zh native 엔진이 baidu 하나만 남는다(baidu 는 격리 정상·생존).

### ★적용이 막혀 있다 — 설정이 다른 에이전트의 작업 공간에 있다

`kdb-searxng` 의 설정은 `/home/aiin/kdb/repo/searxng` **바인드 마운트**다. 그 디렉터리는
다른 에이전트가 쓰는 공유 배포 체크아웃이라 직접 고치지 않았다. 브랜치에만 담았다.
적용하려면 main 반영 후 `docker compose ... up -d --force-recreate kdb-searxng` 가 필요하다
(CI 는 `kdb-app` 만 건드린다).

1. **후보 멈춤 60%** 가 최대 손실이다. 발굴이 끝났는데 왜 active 로 못 가는지 —
   근거 요건을 못 넘는 것인지, 넘었는데 승급 경로가 안 도는 것인지 가른다.
2. `KDB_LOCALFILL_BATCH` 상향의 안전 상한 — gemma 호출량·검색 부하로 계산한다.
3. 권위 API 레인이 24시간 로그에 안 보이는 이유 (3회차 2번 과제)

### 범위 정리 (오너 지시 2026-09-20)

일반명사 DB·정정 요청 처리는 **다른 에이전트 담당**이다. 이 브랜치의 taxon 레인
(`internal/kdb/taxon*.go`, `migrations/0150_taxon_name.sql`)은 그 영역과 겹치므로
**병합하지 않고 그대로 둔다.** 내 일은 요청 구간 모니터링과 자체 수정이다.

## 5회차 — 후보 멈춤 60% 의 원인 (4회차 1번 과제)

### 답: 순환 교착이다

```
최근 7일 신규    active 1,904 · candidate 976 · rejected 58
                 active    평균conf 0.71 · 검증등급 1,904/1,904
                 candidate 평균conf 0.40(전부 동일) · 검증등급 0 · 출처URL 1 · 시도기록 976/976
```

후보는 **시도를 안 한 게 아니다.** 976건 전부 `enrich_attempts` 기록이 있다.
발굴은 했고 **근거를 못 찾았다.** 승급 경로는 정상이다(active 는 검증등급 100% 보유).

그런데 표기를 채워 줄 레인들의 선정 조건이 전부 이렇다:

```
zhwiki · mdl · itunes · opencc   →   WHERE status='active'
실측: song_album 중 ja 빈칸   active 449 · candidate 263
```

**후보는 「근거가 없어서」 후보인데, 근거를 만들어 줄 레인이 후보를 안 본다.**
후보 → 근거 없음 → active 못 감 → 레인 대상 아님 → 근거 못 받음 → 계속 후보.

일부 레인은 후보 전용 승급 경로를 갖고 있다(`DrainITunesSongCandidates`,
`DrainTMDbCandidates`, `DrainMusicBrainzCandidates`). 배치는 `8` 이다(cmd/kdb/main.go).
**그 경로가 없는 유형이 문제다.**

### 멈춘 후보 976건의 유형 — 권위 소스가 없는 영역이 드러난다

```
song_album 213   iTunes/Discogs 있음 · Spotify 키 없음(오너 대기)
person     196   권위 API 없음 — wikidata 에 없으면 검색뿐
event_tour 120   권위 소스 없음
show        82   TMDb 있음
organization 75  권위 소스 없음
company     75   권위 소스 없음
agency      33   권위 소스 없음
character   31
```

`event_tour + organization + company + agency = 303건(31%)` 은 **후보 승급 레인
자체가 없는 유형**이다. 여기는 배치를 키워도 안 움직인다.

### 곁가지로 확인된 것 — 「선언만 된 출처」의 정체

`SourceNaverPeople` 은 상수와 우선순위 표에만 있고 **값을 쓰는 레인이 없다.**
NAVER 키는 설정돼 있지만 검색 보조(localfill)로만 쓰인다. 3회차의 「0칸 출처 33개」 중
적어도 일부는 이렇게 «선언만» 이다 — 레인이 있다는 것과 다르다.

### 이번 회차 산출물

`scripts/kdb-candidate-gap.sh` — 위 세 가지(근거 보유·시도 여부·레인 사정거리)를
한 화면에 본다. 매 회차 같은 질의를 새로 짜던 것을 끝낸다.

### 다음 회차

1. **후보 승급 레인이 없는 유형 303건** — organization/company/agency 는 공식 사이트가

2. `KDB_LOCALFILL_BATCH` · 후보 승급 배치 `8` 의 안전 상한 계산
3. person 196 — wikidata 에 없는 인물을 무엇으로 채울지

## 6회차 — 권위 소스 없는 303건 (5회차 1번 과제)

### 먼저 찾은 것: 레인 유형 목록에 둘이 빠져 있었다

## 7회차 — 위키데이터로 못 푸는 것의 **대안** (오너 지시: 리서치해서 해결방안을 찾아라)

6회차에서 「303건은 위키데이터 밖에 있다」까지 갔다. 거기서 멈추면 아무것도 안 바뀐다.
**이미 키를 가진 것부터** 찔렀다.

### 실증 ① NAVER 검색 API — 키를 이미 갖고 있다

`KDB_NAVER_CLIENT_ID/SECRET` 은 설정돼 있고 지금은 검색 보조로만 쓰인다. 조직 이름으로
부르면 **공식 사이트가 1순위로 나온다**:

```
세트렉아이           → satreci.com
소니뮤직엔터테인먼트코리아 → sonymusic.co.kr
하이브 레이블스        → YouTube 채널 "HYBE LABELS"
```

### 실증 ② 한국 기업 사이트는 title 에 한글·영문을 병기한다

```
satreci.com       <title> 쎄트렉아이 - SATREC INITIATIVE     ← 우리 값은 Setrek-i (gtranslate)
sonymusic.co.kr   og:site_name  Sony Music Entertainment Korea
```

한국어 원문이 같은 title 에 있으면 **「이 사이트가 그 대상의 것」이라는 앵커가 공짜로
성립**한다. 영문명과 앵커를 한 번에 얻는다.

### 파일럿 12건 — 그리고 판별식이 실측에서 나왔다

후보(organization·company·agency) 12건으로 돌렸다. 영문명 확보 6건, 그중 **2건이 오매칭**.
그런데 오매칭 2건은 성격이 같았다 — **제3자 플랫폼 페이지**다:

```
채택  메이아이       → mAy-I                  may-i.io/
채택  픽스업헬스      → PhyxUp Health          phyxuphealth.com/
채택  KICCA        → Korea Institute Of Certified Cost Analyst   kicca.or.kr/
채택  LIG디펜스앤에어로스페이스 → LIG Defense&Aerospace   ligdefenseaerospace.com/
기각  이타디엑스      → InnoForest             innoforest.co.kr/company/CP0…   스타트업 DB
기각  케이바이오게이트웨이 → Wbiz                 wbiz.or.kr/biz/areaDetail.do    중소기업 포털
```

**공식 사이트는 루트에서 자기 이름을 보여주고, 제3자 DB 는 경로 안쪽에 싣는다.**
`URL 경로 깊이 ≤ 1` 조건 하나로 오매칭 2건이 정확히 걸러진다 — 4/4 정확, 오매칭 0.

도메인 일치(영문명의 알파벳이 호스트에 포함)만으로는 **안 된다** — InnoForest·Wbiz 도
그 조건을 통과한다. 한국어 병기 앵커도 단독으로는 안 된다(제3자 DB 페이지에도 한국어
회사명이 있다). **경로 깊이가 결정적이다.**

### 설계는 이미 있고 레인만 없다

`SourceOfficialPage`("official-page", prio 4) 상수가 **이미 선언돼 있다.** 3회차에서
「원장에 0칸인 출처 33개」로 찾았던 그것이다. 채울 레인만 없다.

```
후보(organization·company·agency)
  → NAVER 검색(키 보유)  → 1~3위에서 제3자 도메인 제외
  → 경로 깊이 ≤ 1 인 페이지만  → title/og:site_name 에서 라틴 추출
  → 한국어 원문 병기 확인(앵커)  → canonical_en = 값, source='official-page'
```

### 다른 대안들의 상태 (실측)

| 원천 | 상태 | 비고 |
|---|---|---|
| **NAVER 검색** | **키 보유·작동 확인** | 위 경로. 지금 쓸 수 있는 유일한 것 |
| DART OpenAPI | 키 필요 (`status 010 등록되지 않은 인증키`) | **무료·자동 발급.** 한국 법인의 공식 **영문명 전량**을 준다 — 기업 유형에 가장 정확하다 |
| data.go.kr 사업자정보 | 키 필요 | 이미 오너 대기 목록 |
| GBIF | 키 불필요 | 생물종 전용(5회차 범위 밖) |

**DART 키는 받을 가치가 크다** — company 유형은 검색 추정이 아니라 법정 영문명으로 끝난다.

### 다음 회차

1. 위 레인을 구현한다(`official-page`). 배포 전 dry-run 으로 수확과 오매칭을 센다.
2. 제3자 도메인 목록은 실측으로 채운다(namu.wiki·saramin·jobkorea·innoforest·wbiz…).
3. person 196건은 이 경로가 안 맞는다 — 따로 본다.

## 8회차 — **스스로 성장하는 시스템**의 첫 조각 (오너 지시)

> *"너의 역할은 시스템을 제대로 구축하는 것이다. 요청과 답변을 보면서 우리 KDB 가
> 부족한 것을 빨리 찾아 답변하도록 개선하는, 스스로 성장하는 시스템을 구축해야 한다."*

맞는 지적이다. 7회차까지 나는 매 회차 손으로 SQL 을 파서 결핍을 찾았다. 그건
시스템이 아니라 내 노동이고, 내가 없으면 멈춘다.

### 무엇부터 지어야 하나 — 반복해서 데인 자리가 답이다

하루 동안 같은 병으로 세 번 데였다. 전부 **「레인이 무엇을 했는지 어디에도 안 남는다」**:

```
zhwiki    dry-run 이 「389건 채움」이라 말하는 동안 원장은 0건 바뀌었다
localfill 로그 13줄을 24시간치로 읽었다 — 앱이 48분 전 재시작한 것이었다
org-anchor 유형 둘을 넓혔는데 실제 수확은 50건 검사에 0건이었다
```

로그는 앱 수명만큼만 살고, 0건일 때 아예 안 찍는 레인이 많다. **안 돈 것과 돌았는데
0건인 것을 구별할 수 없다.** 이 구별이 없으면 다음 판단이 전부 추측이 된다.

### 지은 것 — 레인 성과 원장 (0151 + lane_ledger.go)

세 수를 **절대 섞지 않고** 적는다.

```
scanned  선정 쿼리가 뽑은 행
applied  원장이 실제로 바뀐 수     ← 이 둘을 섞은 것이 389건 거짓말의 원인이었다
skipped  뽑았지만 안 쓴 수 + 사유별 계수(jsonb)
```

DB 제약으로 `applied <= scanned` 를 강제한다. 기록이 실패해도 레인은 계속 간다 —
계측기가 본체를 죽이는 것이 가장 나쁘다.

### 끝단 확인 — 원장이 **스스로 진단을 말한다**

복원 DB 에 붙여 zhwiki 레인을 dry 로 돌렸다:

```
zhwiki-title [dry] ★조용한0건: scanned=429 applied=0 skipped=429
  reasons={"바꿀 근거 없음":349, "en-mismatch":42, "bad-url":35, "multi-url":3}
```

**2회차에 내가 하루 걸려 찾은 `en-mismatch` 를 이제 한 줄이 말한다.** 그리고
`IsSilentZero(runs, scanned, applied)` 는 순수 함수라 시험이 규칙을 고정한다 —
한 회차 0건은 정상이고(대상이 없을 수 있다) **여러 회차 뽑기만 하는 것**이 병이다.

`LaneHealthSince(24h)` 로 「조용한 0건인 레인」이 질의 한 줄로 나온다.

### 이것이 성장 고리의 어디인가

```
요청 로그 ─→ 결핍 진단 ─→ 공급원 선택 ─→ 레인 실행 ─→ [수확 측정] ─┐
   ↑                                                              │
   └──────────────── 다음 대상 선정 ←─────────────────────────────┘
```

`[수확 측정]` 이 비어 있어서 고리가 끊겨 있었다. 그 자리를 메웠다. 남은 것:

1. **나머지 레인에 배선** — zhwiki 하나만 붙였다. 46개 레인 전부가 같은 원장을 쓰면
   「어느 레인이 헛도는가」가 매일 자동으로 나온다.
2. **결핍 진단의 자동화** — 지금 요청 로그를 SQL 로 파는 부분. 유형×locale 결핍
   순위를 상시 표로 두면 레인 선정이 그 순위를 따라간다.
3. **화면** — `/admin/health` 에 두 표를 올린다. 3회차에서 「장치는 있는데 아무도
   안 켠 경우를 하루에 여덟 번 만났다」고 적은 것의 처방이다.

## 9회차 — 레인 배선 확산 + 자동 신호

8회차에서 원장을 만들고 zhwiki 하나에만 붙였다. 나머지에 확산했다.

### 배선 방식 둘

레인마다 사정이 다르다. 두 가지로 나눴다.

```
① 계수기가 없는 레인  NewLaneRun → Scan/Apply/Skip → defer Record   (zhwiki · opencc)
② 계수기가 이미 있는 레인  RecordCounts(가진 수를 그대로 옮긴다)      (org-anchor · kowiki)
```

②를 따로 둔 이유: org-anchor 는 사유별 계수를 이미 열 개 갖고 있다. 거기에 Scan/Apply 를
다시 심으면 **같은 것을 두 번 세게 되고, 두 수가 갈라지면 어느 쪽이 맞는지 알 수 없다.**

### 끝단 — 정상 레인과 병든 레인이 한눈에 갈린다

```
opencc:canonical_zh_hant  scanned=8  applied=4  {"문자셋 규칙 위반":2,"상위 출처라 못 덮음":2}
opencc:canonical_zh       scanned=0  applied=0  {}            ← 대상이 없다(신호 아님)
org-anchor [dry]          scanned=0  applied=0  {}
zhwiki-title              scanned=349 applied=0 {"바꿀 근거 없음":349}   ← 조용한 0건
```

`scanned=0` 은 병이 아니라 대상이 없는 것이다 — 판정이 그 둘을 정확히 구분한다.
opencc 가 「건강한 레인은 이렇게 생겼다」의 본보기다: 뽑고, 쓰고, 왜 못 썼는지 말한다.

### 자동 신호 (물음: 「신호가 올라오면 자동으로 잡을 수 있도록 설정했나?」)

8회차 시점의 정직한 답은 **아니오**였다. 기록만 하고 잡는 것은 사람이었다. 그래서 붙였다:

- **기록하는 그 자리에서 판정한다.** 스케줄러를 새로 두지 않았다 — 「장치는 있는데
  아무도 안 켠」 경우를 하루에 여덟 번 만났기 때문이다. 레인이 돌 때마다 스스로 본다.
- **3회차 연속부터 울린다.** 한두 회차 0건은 대상이 없던 것이다. `CountSilentStreak`
  는 순수 함수고 시험이 경계를 고정한다 — 임계가 1이면 경보가 늑대소년이 된다.
- **`GET /v1/health` 에 `lanes_silent` 를 싣는다.** 로그는 앱 수명만큼만 살고 아무도
  안 본다(backlog-watch 가 같은 이유로 조용했다). 헬스는 이미 주기적으로 불린다.
  700ms 예산으로 따로 돌리고 실패하면 필드만 빼고 나간다.

실증(복원 DB, non-dry 3회차): 1·2회차 기록만 → **3회차에 `★신호` 발화** →
`SilentLanes(24h) = [zhwiki-title]`.

### 배포 경로를 갈랐다

`feat/lane-ledger` — origin/main 에서 새로 따서 **taxon 레인을 완전히 뺀** 브랜치다
(`taxon_name`·`LocaleFillHintFor` 참조 0건 확인). 단독으로 빌드·vet·전체 시험을 통과한다.
일반명사 DB는 다른 에이전트 담당이므로 그쪽과 섞이지 않게 한 것이다.

담긴 것: 레인 원장(0151)·자동 신호·헬스 노출 · zhwiki dry 정직화와 라틴 규칙 ·
searxng sogou 제거 · 후보 교착 진단 스크립트.

**main 에 병합되는 순간부터 운영에서 자동으로 쌓이고 울린다**(CI 가 migrations/*.sql 을
적용한다). searxng 설정만 컨테이너 재생성이 따로 필요하다.

## 10회차 — 병합·배포. 그리고 내가 만든 사고 둘

오너 지시: 「커밋하고 병합해서 제대로 작동되게 해」.

### 사고 ① 회귀 template 에 직접 썼다

끝단 확인을 하며 복원 DB 에 non-dry 로 레인을 돌렸다. 그런데 그 DB 가
**회귀의 template** 이었다:

```
scripts/run-isolated-regression.sh:  CREATE DATABASE kdb_platform_migration_test TEMPLATE kdb
내가 쓴 곳:                          kdb-p1-restore-db 의 kdb  ← 바로 그 template
```

첫 회귀에서 `TestEntityCenterAgainstRestoredInventory` 가 실패했다. 내 코드 탓인 줄
알았는데, template 을 정리한 뒤 실패한 시험만 양쪽에서 돌리니 **둘 다 통과**했다:

```
main (632fc6c)            ok internal/kdbadmin 2.420s
feat/lane-ledger (341a778) ok internal/kdbadmin 2.475s
전체 회귀 main             33/0 · race 31/0 · 전부 통과
```

즉 실패는 코드가 아니라 **내가 만든 환경 오염**이었다. 바꾼 4행은 확인해 보니 운영과
같은 값이었고, 내가 만든 `kwave_kdb_lane_runs` 표를 template 에서 지웠다.
**앞으로 끝단 확인은 template 이 아니라 일회용 사본에서 돌린다.**

### 사고 ② searxng/settings.yml 은 git 으로 바꿀 수 없다 — 배포가 죽었다

병합 직후 배포가 이 줄에서 멈췄다:

```
error: unable to unlink old 'searxng/settings.yml': 허가 거부
drwxrwxr-x 2 977 977  /home/aiin/kdb/repo/searxng     ← 컨테이너 사용자 소유
배포 계정 aiin 은 uid 1000 — 그 디렉터리에 쓰기 권한이 없다
```

파일을 지우려면 **디렉터리** 쓰기 권한이 필요하다. 그래서 내용이 무엇이든 이 경로는
git 으로 못 바꾼다. 4회차에 「설정이 공유 체크아웃에 바인드 마운트돼 있다」고 적어
두고도 그 함의를 끝까지 따라가지 않았다.

더 나쁜 것은 **배포가 중간에 끊겨 공유 체크아웃이 더러워진 것**이다(추적 파일 12개
변경 + untracked 6개). 다른 에이전트가 쓰는 자리다. 즉시 복구했다 —
`git checkout -- .` 후 **내 커밋 소속 untracked 만 골라** 제거했다(남의 것은 안 건드린다).

처방: sogou 제거를 되돌렸다(ca0aec5). 진단은 유효하다(sogou 가 자동 격리를 우회해
345줄/시). 다만 **디스크만 고치는 것도 안 된다** — git 버전과 달라지는 순간 다음
배포가 같은 자리에서 또 죽는다. 올바른 해법은 디렉터리 소유권 복구(sudo)나 설정
주입 방식 변경이고 **운영자 판단이 필요하다.**

## 11회차 — 시스템이 스스로 다음 대상을 말했다

### 성장 고리가 닫혔다

```
결핍 원장 360칸 · 최근 측정 17:28:30   ← 내가 부르지 않았다. 레인 기록에 업혀 스스로 돌았다
레인 원장  zhwiki-title 2회차 824건 뽑아 0건   ← 같은 곳을 가리킨다
헬스       lanes_silent 없음(아직 2회차 — 3회차부터 신호). 판정이 정확하다
```

시스템이 말한 결핍(내가 1회차에 손으로 판 것과 같은 결론):

```
unmet      person 367낱말/566요청 (이재명·이재용·조국) · song_album 342/487 · show 120/154
locale_gap person zh_hant 299/412 (결이·구름·최보필) · show zh 82/149 · song_album zh 114/145
```

`person unmet` 은 다른 에이전트의 범위 작업과 겹치므로, 내 영역인 `person zh_hant` 를 잡았다.

### 계획한 처방이 실측에서 0건이었다 — 쓰기 전에 쟀다

2회차에 찾아 둔 「en-mismatch 게이트가 한자 제목을 구조적으로 기각한다」를 고치려 했다.
앵커를 보유 zh_hant 대조로 바꾸는 설계였다. **코드를 쓰기 전에 수확을 쟀다:**

```
zh위키 URL 보유 3,657 · 번체 보유 3,214 · **번체있고 간체빈칸 0**
person 결핍의 실체: zh·zh_hant **둘 다 빈칸 515건** · 번체만 있음 2건
둘 다 빈칸 515건 중 — zh위키 URL 4 · 위키데이터 QID 156 · ko위키 URL 135
표본: 결이(QID 0·URL 0) · 구름(0,0) · 최보필(0,0)
```

앵커로 쓸 zh_hant 가 없다. zhwiki 레인을 고쳐도 상한이 **4건**이다. 안 썼다.

### 그래서 이 결핍은 「채우는 문제」가 아니다

`결이·구름·최보필` 은 어느 외부 DB 에도 없다. 한국 인물의 한자 이름은 **본인의 한자**라
규칙으로 만들 수 없다 — ja 는 kana-rule 이 있지만 zh 는 그런 규칙이 없다(KDB 문서가
이미 인정한 한계다). 그러면 처방은 「채운다」가 아니라 **「못 채운다고 정확히 말한다」** 다.

### ★그런데 그 말하기가 고장나 있다

```
둘 다 빈칸 person 515건 — zh 시도 기록 439건(85%) · **소진(exhausted) 표시 5건(1%)**
소비자 응답(24h): ready 340 · preparing 139 · review 110 · new 108 · unfillable 16
```

**439건이 시도해서 실패했는데 소진 표시가 안 붙는다.** 그래서 소비자에게 계속
`preparing` 으로 나간다 — 기다리면 채워질 줄 알고 폴링하지만 영원히 안 채워진다.
`unfillable` 상태도 `ExhaustedLocales` 도 이미 있다. **장치는 있는데 표시가 안 붙는 것**이
병이고, 이 저장소가 반복해 만난 그 모양이다.

### 곁가지 — 다른 에이전트가 0150 을 썼다

`7b44122 fix(mig-0150)` · `c1e7324 feat(common-noun): 일반명사에 제 구간을 주고…`.
일반명사 DB 가 올라갔고 마이그레이션 0150 도 그쪽이 가져갔다. 내 taxon 브랜치
(feat/category-sources)의 0150 은 번호가 충돌한다 — 어차피 병합하지 않기로 한 것이라
그대로 둔다. **그 영역은 그쪽이 닫았다.**

### 다음 회차

## 12회차 — 자동 신호가 실제로 떴고, 거짓 답 하나를 고쳤다

### ★신호가 운영에서 스스로 올라왔다

```json
GET /v1/health → "lanes_silent":["opencc:canonical_zh_hant","org-anchor","zhwiki-title"]
```

4회차 연속 뽑기만 하고 한 건도 못 쓴 세 레인을 **시스템이 이름으로 내보냈다.**
사람이 로그를 뒤지지 않았다. 8회차에 「신호가 올라오면 자동으로 잡히나」라는 물음에
「아직 아니다」라고 답했던 것이 이제 「예」가 됐다.

### 소진 표시가 안 붙던 이유 — 정책 스킵은 시도로 세지 않는다

`exhausted` 는 `attempts >= 2`(maxAttempts) 일 때만 선다. 그런데 근거 없는 칸은
L4 를 건너뛰는 **정책 스킵(ground-strict-skip)** 으로 끝나고, 그 경로는
`recordPolicySkip` 이 **attempts 를 건드리지 않는다.** 그래서 영원히 0 이다:

```
canonical_zh attempts=0 4,564건 중 ground-strict-skip 2,481(54%) · (빈값) 1,327 · wikidata 652
그중 30일 이전에 멈춘 것 3,605건 · 가장 오래된 것 2026-06-13 (3개월+)
비교: canonical_vi 는 72%가 소진 표시(4,066/5,644) — zh 만 5.7%였다
```

그동안 소비자는 `preparing` 을 받았다 — 「기다리면 채워진다」는 뜻인데 채워질 일이 없다.
**최근 7일 271회 요청(120낱말)이 그 거짓 답을 받고 있었다.**

### 고친 것 — 값이 아니라 **안내**를 참으로

`ExhaustedLocales` 가 「오래 멈춘 정책 스킵」도 소진으로 본다. 값은 건드리지 않는다.
소비자는 `unfillable` + `fill_hint` + 정정신고 경로를 받는다. 근거가 생겨 칸이 채워지면
`recordAttempt` 가 행을 지우므로 자동으로 풀린다. 임계 30일은 정책 스킵 쿨다운(7일)보다
넉넉해야 「아직 재방문 중인 것」을 소진이라 부르지 않기 때문이다.

```
새 조건으로 소진 처리될 칸: zh_hant 1,664 · zh 1,555 · ja 992 · vi 279 · pt_br 277 ·
                            id 259 · es 214 · en 7   (그중 zh 는 실제 빈칸 active 1,035)
```

### 이번 회차의 순서가 규칙대로였다

시스템이 말한 결핍 순위를 먼저 읽고 → 대상을 고르고 → **코드를 쓰기 전에 수확을 재고**
→ 구현 → 시험 → 병합. 11회차에 상한 4건을 확인하고 안 쓴 것과 같은 절차다.
