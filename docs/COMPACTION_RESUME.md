**ja 1,065건으로 확대하지 않았다.** 40% 오류를 밤새 5배로 늘리는 것은 지시의 취지가
아니라고 판단했다. 되돌리는 것은 한 줄이다:
```sql
UPDATE kwave_entities SET canonical_zh='', canonical_zh_source='' WHERE canonical_zh_source='gtranslate-raw';
UPDATE kwave_entities SET canonical_ja='', canonical_ja_source='' WHERE canonical_ja_source='gtranslate-raw';
```
**판단 근거**: 같은 배포에서 `locale_absent` + `fill_hint` 가 나가기 시작했다.
"빈칸이 한글 잔존을 만든다"는 문제는 **값이 아니라 지시**로 이미 풀렸다.
그렇다면 40% 틀린 값을 더할 이유가 약해진다 — 그래도 운영자 결정이다.

### 안전한 채움은 소진됐다


## 7. 실측이 잡아낸 내 오판 (같은 실수 반복 금지)

1. **"적재 비계 880MB 정리"** — 681MB 는 비계가 아니라 흡수분의 **자체 ID 앵커**
   (`basis_record_id`)였다. FK 세 개가 `ON DELETE RESTRICT`.
2. **`tourapi_ko 12` → 관광지** — 문서 기억으론 맞지만 이미 분류된 2,033건 중
   **heritage 1,170 · nature 739**. 세부 일치율 57.6%. 코드는 "장소다"까지만 말한다.
3. **`shared_buffers` 4GB 권고** — 가용 메모리를 재보고 1GB 로 철회했다.
4. **"3분에 3건 오류"** — `--since` 를 잘못 걸어 재시작 **전** 로그를 보고 있었다.
5. **③과 ④를 이어 붙이면 브랜드 12개가 사라진다** — 각 스크립트는 옳은데 이어 붙이면
   지키려던 대상을 잃는다. 스크립트 하나씩만 읽어선 안 보이는 자리다.
6. **⑤를 그대로 돌리면 ④를 되돌린다** — 범위 밖으로 뺀 45,734건에 분류 근거를 다시 쌓을
   뻔했다. "각 단계가 맞다"가 "이어 붙여도 맞다"를 뜻하지 않는다.
7. **되돌리기 처방을 시험하지 않고 문서에 적어 뒀다** — `classification_reason` 이 NOT NULL
   이라 적어 둔 처방이 실제로는 실패한다. 시험해 보고서야 알았다.
8. **격리 회귀가 5커밋 전 코드를 시험하고 있었다** — 워크트리 체크아웃 실패를 `|| true` 가
   삼켰다. "PASS" 가 **무엇에 대한 PASS 인지** 확인되지 않으면 PASS 가 아니다.

9. **`locale_ambiguous` 상관 서브쿼리가 match 를 느리게 한다** — 계획을 보니 **5번만**
   돈다. 범인은 2~3자 이름 6,468건마다 **정규식을 새로 컴파일**하는 필터였다.
   같은 종류의 결함을 앞서 고쳐 봤다는 것이 오히려 성급한 지목을 낳았다.
10. **22번 SMART 가 PASSED 니 디스크는 멀쩡하다** — 커널 로그에 진행 중인 I/O 오류가
   있었다. 운영자 피드백이 먼저 맞았다. **SMART 는 전부가 아니다.**
11. **`docker-compose.override.yml` 은 장비별 파일이다** — 추적되는 파일이었다.
   23번에서 덮어썼다가 `git checkout` 으로 되돌렸다. 하마터면 `git reset --hard`
   한 번에 조용히 사라질 뻔했다.
12. **172.19.0.0/16 을 23번에도 그대로 쓰면 된다** — `gemma4-moe_default` 가 쓰고 있었다.
   "Pool overlaps" 로 실패해서 알았다. 옛 장비의 주소를 새 장비에 그대로 옮길 수 없다.

13. **"격리 회귀 5/5 통과"라고 여러 번 보고했다** — 그 template 은 표기 1,249건짜리
   흡수 이전 스냅샷이었다(운영 2,686,762). 수치를 재 보고서야 알았다.
   **통과했다는 말은 무엇에 대고 통과했는지 말할 수 있을 때만 뜻이 있다.**
14. **회귀 template 이 낡은 줄 모른 채 계속 썼다** — 8번(옛 코드를 시험)과 짝이다.
   시험 환경 자체를 주기적으로 재지 않으면, 시험은 조용히 의미를 잃는다.

**전부 그럴듯했고 전부 틀렸다.** 기억·직관이 아니라 데이터에서 도출한다.
그리고 **하나씩은 맞는 것들을 이어 붙일 때** 특히 조심한다 — 5·6·7 이 그 자리였고,
**같은 종류의 결함을 전에 고쳤다는 기억**이 9번처럼 엉뚱한 지목을 낳기도 한다.
8·13·14 는 한 덩어리다: **검증 장치 자체를 검증하지 않으면 통과가 통과가 아니다.**

15. **"P4.02 는 여행 출처를 연결하는 일"이라고 읽고 시작했다** — 재어 보니 표기는 이미
   전부 들어와 있었고(en 341,796·ja 303,379), 충돌도 0건이라 규칙도 필요 없었다.
   막고 있던 것은 **출처가 아니라 대상 상태 두 가지**였고, 그것을 여는 코드 경로가
   wikidata 만 받아 자체 ID 앵커라는 계약 자신의 원칙과 어긋나 있었다.
   **과제 제목이 가리키는 곳과 실제 병목이 다를 수 있다.** 제목을 믿고 짓지 않고 먼저 쟀다.
16. **수요 기반 규칙이면 대상을 고를 수 있다고 봤다** — 302건을 고르는데 그 안에
   `아일랜드`(소비자는 **drama** 로 보냈다)·`돈`(**movie**)·법정동 `상원` 9건이 그대로 있었다.
   규칙은 선별을 **돕는** 것이지 대신하지 못한다. 그래서 스크립트에서 선별을 빼냈다.
17. **내가 만든 활성화 도구가 결함 인물 15,009명을 열어 줬다** — 여행 대상을 기준으로 쓴
   규칙을 인물에 그대로 적용한 것이 문제였다. 여행 출처(tourapi·aihub·seoul_dict)는
   **데이터셋 단위**로 권리가 정해져 항목 식별이 근거가 아니고, wikidata 는 **항목 단위**다.
   같은 규칙이 두 출처에 다르게 적용돼야 했다. 5·6·7 과 같은 자리다 —
   **조각마다 옳은 것을 이어 붙일 때 틀린다.** 도구를 만든 당일에 그 도구를 의심해서 잡았다.
18. **"흡수분 인물의 표기가 wikidata recorded 라 좋다"고 P4.02 결론에 적었다** — 맞는 말이지만
   근거 행을 열어 보니 `source_record_id` 가 QID 가 아니라 TDB UUID 였다(65,487/65,972).
   **provider 칸이 'wikidata' 라는 것과 그 표기가 추적 가능하다는 것은 다른 말이다.**
19. **회수한 QID 를 `export_allowed=true` 로 넣었다** — 그러면 DB 트리거의 "재사용 가능한
   정체성 근거"를 **그 QID 가** 만족시켜 대상이 **QID 때문에** 열린다. 실측: 회수 434건이
   전부 `tdb export=false / wikidata export=true` — 자체 관측은 자격이 없고 외부 항목이
   문을 열고 있었다. **운영자가 "QID 는 기본이 아니라 보조"라고 짚어 줘서 알았다.**
   고치려고 false 로 내렸더니 트리거가 외부 ID 까지 `withdrawn` 으로 만들어(677→243)
   방금 회수한 항목 지목이 날아갔다. **플래그가 아니라 문을 여는 쪽에서 강제해야 했다** —
   활성화 자격을 `자체ID근거` 로 바꿨다.
20. **"P5 = 동일성 판정"이라고 문서 9곳에 적었다** — P5 는 **단일 writer 전환**이고
   동일인 판정은 P2.05·P4.07 이다. 운영자가 "round 5 이니?"라고 물어서 확인하다 드러났다.
   **번호를 외워서 쓰면 안 된다. 원장을 열어 확인한다.**
22. **"기존 원장 보강을 공통 원장으로 흘리는 다리"를 만들려 했다** — 트리거가 막는다:
   `legacy names belong to original KDB writer`. kdb 소유 행에 표기가 0건인 것은
   **결함이 아니라 설계**였다(I04). 정해진 길은 채택(AdoptLegacy)이고 그것이 P5 다.
   **"비어 있다"를 "고장났다"로 읽지 않는다 — 계약을 먼저 본다.**
23. **wikidata 만 보고 "출처가 없다"고 했다** — 운영자가 "wikidata 만 wiki 가 아니잖아",
   "기존 kdb 는 여러 군데서 소스를 찾아 업데이트했잖아"라고 짚어 줬다. 세어 보니
   **어댑터가 22개**(kofic·kmdb·kopis·musicbrainz·itunes·discogs·mdl·ott·tmdb …) 있었다.
   **코드를 안 보고 데이터만 보면 이미 있는 것을 못 본다.**
24. **kowiki 수율을 기존 기록(10%)으로 가정할 뻔했다** — 표본을 재니 **1.0%** 였다.
   같은 도구라도 **대상 집단이 다르면 수율이 다르다**(기존은 미검증 K-엔티티,
   여기는 식당·숙박 POI). 남의 실측을 내 실측으로 쓰지 않는다.
25. **`git add -A` 로 관계없는 작업까지 main 에 밀어 넣었다** — 분류 현황 UI 가
   tourapi 마이그레이션 커밋에 섞여 **격리 회귀 없이** 배포됐다(CI 는 통과).
   브랜치 검증 절차를 스스로 정해 놓고 건너뛴 것이다.

21. **UI 를 만들지 않아도 일이 된 줄 알았다** — 근거·원장 계층만 고치고 화면을 안 건드렸다.
   운영자가 "머 크게 달라진 것이 없어"라고 했을 때 확인해 보니 공통 원장 관리 화면이
   **다 구현돼 있는데 메뉴에 링크가 없었다.**
   **화면이 없는 기능은 없는 기능과 구별되지 않는다.**

26. **이전 때 옛 `kdb-app` 이 붙어 있던 망 4개 중 1개만 옮겼다** — 새 중계(`kdb-shim`)를
   `dockers_backend` 에만 붙이고 끝냈다. 옛 컨테이너는 `mediafine_default` ·
   `kdb-platform_kdb_internal` · `kdb-platform_dockeraiinplanetcom_backend` 에도
   붙어 있었다. `mediafine_default` 전용 컨테이너에서는 **`kdb-app` 이름 자체가 안 풀렸다.**

   **이름 확인을 안 한 게 아니다.** 이전 절차(`cut.sh` 7단계)는 소비자와 같은 방식으로
   `curl http://kdb-app:9100/v1/health` 를 돌렸고 통과했다. 문제는 **그걸 한 망에서만**
   했다는 것이다. 바꿔 놓는 대상이 몇 개의 망에 붙어 있었는지를 **먼저 세지 않았다.**

   **교체 절차에는 "바꾸기 전 원본의 접점을 전부 열거한다"가 들어가야 한다.**
   한 곳에서 통과한 것은 한 곳에서 통과한 것일 뿐이다.

   조치: `docker network connect --alias kdb-app mediafine_default kdb-shim`
   (내 컨테이너만 붙였다. 남의 컨테이너는 재기동도 안 했다.)
   재발 방지: 중계 정의를 임시 파일이 아니라 `scripts/old-server-shim.sh` 로 원장에 넣었다.

27. **500개가 쌓인 임시 폴더에서 `full.sh` 라는 이름을 다시 썼다** — 스크립트를 만드는
   파이썬이 서식 오류로 죽었는데(`date +%H` 의 `%` 가 파이썬 서식으로 해석됐다),
   **파일은 안 만들어졌고 같은 이름의 9월 13일자 옛 파일이 대신 운영 서버에서 돌았다.**
   그 옛 파일은 회귀 실행기였고 안에 `pg_terminate_backend` 와 `DROP DATABASE` 가 있었다.

   피해는 없었다 — 대상 변수가 내 일회용 컨테이너(`kdb-p1-restore-db`)를 가리켰고
   운영은 표기 2,686,762·restarts=0 그대로였다. **운이 좋았던 것이지 설계가 막은 게 아니다.**

   두 가지를 바꾼다:
   ① 임시 스크립트 이름에 **날짜와 용도**를 박는다(`qidrun_20260914_a.sh`).
      `full.sh` · `run.sh` · `chk.sh` 같은 이름은 재사용 사고를 부른다.
   ② 스크립트 본문을 만들 때 **파이썬 `%` 서식을 쓰지 않는다.** `.replace()` 를 쓴다.
      본문에 `%` 가 들어갈 일이 흔하다(`date +%H`, `%s`, 백분율).
   그리고 생성이 실패했으면 **실행하지 않는다** — 파일 존재 여부를 확인한다.

28. **간체↔번체 자동 교정을 만들었다가 감사에서 세웠다 — 절반이 틀렸다**
   `사랑이 온다` 의 zh_hant 가 `爱情来了`(간체)인 것을 찾고 28건인 줄 알았다. 글자표로
   재보니 1,850건, opencc 로 재보니 992건(zh_hant 458 · zh 534)이었다. **세 번 다 다른 수**다.

   쓰기 전에 읽기 전용 감사(`kdb-app zh-variant-audit`)를 만들어 눈으로 봤고,
   **제안된 변환의 절반이 틀렸다**:
   ```
   박보영 朴寶英 → 樸寶英    朴은 번체에도 있는 한국 성씨 한자다. 樸은 '순박하다'
   박규리 朴奎利 → 樸奎利    (외 7건 더 — 朴씨 전부가 걸렸다)
   최리   崔里   → 崔裏      里=마을 / 裏=안쪽
   김기두 金基斗 → 金基鬥    斗=말·이름 / 鬥=싸우다
   ```
   `s2t(v) != v` 는 **"v 가 간체다"가 아니라 "v 를 간체로 읽을 수도 있다"** 였다.
   朴·里·斗·准·后·云 는 양쪽에 다 있는 글자다. opencc 는 그걸 모른다.

   **돌리지 않았다.** 돌렸으면 번체 칸의 한국 인명을 수백 개 망가뜨렸다.

   **교훈 두 개.**
   ① 결정적이라고 안전한 게 아니다. 한자 변환은 결정적이지만 **문맥 없이는 틀린다.**
      "외부호출 0 · 벌크안전" 이라는 말에 속으면 안 된다.
   ② **쓰기 전에 읽기 전용으로 세어 보는 도구를 먼저 만든다.** 이번엔 그게 값을 했다.
      숫자만 봤으면(992건) 그럴듯해서 돌렸을 것이다. **표본을 눈으로 봐야 했다.**

   남은 일: 간체가 확실한 것만 고른 목록을 손으로 만들어 교정한다. 자동은 안 된다.
