## §0. 새 세션 첫 명령 (상태 40초 파악)

```bash
cd /data/home2/kdb.aiinplanet.com

# 가동 이미지 + 정적 IP. IP 는 반드시 172.19.0.240 이어야 한다.
docker inspect kdb-app --format 'image={{.Config.Image}} ip={{range .NetworkSettings.Networks}}{{if .IPAddress}}{{.IPAddress}} {{end}}{{end}}'

# 이 세션에서 만든 레인의 상태
docker logs kdb-app --since 2h 2>&1 | grep -E "wd-locale|tmdb-locale"

# CJK 빈칸 현황 (active·미잠금 기준 — 전체 숫자에 속지 말 것)
docker exec kdb-db psql -U kdb -d kdb -c "
SELECT count(*) FILTER (WHERE COALESCE(canonical_ja,'')='') ja,
       count(*) FILTER (WHERE COALESCE(canonical_zh,'')='') zh,
       count(*) FILTER (WHERE NOT EXISTS (SELECT 1 FROM kwave_entity_external_refs r
                                           WHERE r.entity_id=e.id)) 앵커없음
  FROM kwave_entities e
 WHERE status='active' AND operator_locked=false AND COALESCE(canonical_ko,'')<>''
   AND (COALESCE(canonical_ja,'')='' OR COALESCE(canonical_zh,'')='');"
```

### ★빌드·배포 (Go 툴체인이 호스트에 없다)

호스트에 `go` 가 없다. 컨테이너에서 빌드·테스트한다. `-buildvcs=false` 가 필요하다
(마운트된 소스에서 VCS 스탬핑이 실패한다).

```bash
docker run --rm -v "$PWD":/src -w /src \
  -v kdb_go-mod-cache:/go/pkg/mod -v kdb_go-build-cache:/root/.cache/go-build \
  -e PATH=/usr/local/go/bin:/usr/bin:/bin golang:1.23-bookworm sh -c '
  gofmt -l <바꾼파일>; go build -buildvcs=false ./... && go test -buildvcs=false ./internal/...'
```

⚠ `cmd/kdb/main.go` 는 **원래부터 gofmt 미준수**다(import 순서, tmdb 줄). 내가 만든 게
아니니 전체 포맷하지 말 것 — 무관한 diff 가 커진다.

배포는 **반드시 두 compose 파일을 다 넘긴다.** `-f` 하나만 쓰면 override 가 자동 로드되지
않아 정적 IP(172.19.0.240)를 잃고 nginx 오라우팅이 난다(23d8be8).

```bash
sed -i 's/^KDB_APP_IMAGE=.*/KDB_APP_IMAGE=kdb-app:<tag>/; s/^KDB_BUILD_VERSION=.*/KDB_BUILD_VERSION=<tag>/' .env
docker build -q -f Dockerfile.kdb-app -t kdb-app:<tag> .
docker compose -f docker-compose.kdb.yml -f docker-compose.override.yml up -d kdb-app
```

`KDB_APP_IMAGE` 와 `KDB_BUILD_VERSION` 은 **별개 변수**다. 후자를 안 바꾸면 health 가
옛 버전을 보고한다(`kdbapi/api.go:748`).

## §1. 재시도 규칙 통일 (0100~0105)

레인마다 "7일 쿨다운" "30일 쿨다운"이 제각각이었고, 그 때문에 앵커가 있는데도 재선택
자체가 안 되는 엔티티가 쌓였다. 한 규칙으로 모았다 — **입력 지문이 같으면 재시도하지
않는다. 다르면 즉시 재시도한다. 90일이면 무조건 한 번 다시 본다.**

| 마이그레이션 | 내용 |
|---|---|
| 0100 | `kdb_fill_input_hash(uuid)` — 정본·타입·별칭·8로케일·인물상세·외부식별자를 md5 |
| 0104 | **실체화**. 함수 호출이 15,491건 × 0.17ms = 11,375ms 였다 → 컬럼 + 트리거로 **32ms** (355배). 백필 16,487행 + 트랜잭션 내 불일치 검사 |
| 0105 | 원장 `input_hash` 를 **트리거로 강제**. 호출부가 26군데(20파일)라 하나씩 고치면 또 빠뜨린다 — 실제로 0104 직후 `enrichground` 20건이 `input_hash=''` 로 쌓였다 |

`internal/kdb/fill_retry.go` 의 `FillRetryPredicate` / `FillRetryBlockedFields` 가 단일
진실이다. **새 레인을 만들 때 쿨다운을 직접 쓰지 말고 이걸 쓴다.**

★0105 는 기존 `input_hash=''` 행을 **소급하지 않는다.** 지금 지문으로 채우면 "그때 실제로
시도했는지 알 수 없는 것"을 시도했다고 단정하는 셈이다. 빈 값이면 "재시도 가능"으로 읽히고
한 바퀴 돌며 정직한 지문이 쌓인다.

효과 실측: 캐스케이드 선택 가능 엔티티 **6 → 192건**.

## §3. ★CJK 우물 전수 실측 — 자기정정 2회

오너 지적: **"일본어, 중국어를 못채우는데 어떻게 할건데?"**

### 자기정정① sitelink 만 세고 label 을 안 셌다

첫 보고에서 "ja 천장 40건"이라고 했다. 위키백과 **문서(sitelink)** 만 센 수치였다.
레이블까지 세니 ja 148 · zh 112 로 3배였다. **문서가 없어도 레이블은 있는 경우가 ja 만
90건**이다. 이 둘을 섞으면 안 된다.

### 자기정정② 레이블의 "존재"와 "유효성"은 다르다

정정한 수치로 드레인을 만들어 돌렸더니 `checked=120 filled=0` 이 나왔다. 결함을 의심하고
파고들었더니 **드레인이 맞고 내 추정이 틀렸다**:

- **ja 63건 중 62건은 이미 우리 DB 에 채워져 있었다.** 그 엔티티들의 빈칸은 zh 쪽이었다.
  "ja 레이블이 있다"와 "ja 를 채울 수 있다"는 다른 말이다.
- **zh 96건 중 66건이 로마자·한글 복사본이다.**

```
체리블렛      → Cherry Bullet
러블리즈      → Lovelyz
우주소녀 쪼꼬미 → 우주소녀 쪼꼬미   ← zh 레이블에 한글이 그대로
매니지먼트 숲  → Management SOOP
```

문자셋 가드(`IsValidSpellingForLocale`)가 제대로 막은 것이다.

zhwiki **문서 제목**도 확인했다. 통과한 7건이 전부 `APRIL (女子團體)` `Lily (歌手)` 처럼
**동음이의 괄호 때문에** 한자 검사를 통과한 것이지 이름이 아니었다.

### 결론 — 세 방향으로 같은 답

**위키데이터는 한국 엔티티의 중국어 이름 출처가 아니다.** 봇이 로마자 이름을 복사해 둔
것이다. 1차 파동(207건)에서 확보한 건 **2칸**이었다.

0106(§4) 적용 후 지문이 바뀐 94건 + `StripDisambig` 로 깨끗해진 레이블 덕에 2차 파동이
돌아 최종 436건 처리 · **11칸**이 됐다. 그중 **4칸이 틀려서 되돌렸다**(§4.5) — 순증 7칸.

| 판정 | 건수 |

| nothing-new | 399 |
| name-element (앵커가 "인명 요소" 항목) | 19 |
| filled | 11 → **유효 7** |
| anchor-mismatch | 7 |

★`wd-locale` 이 `nothing-new` 만 쌓는 건 **정상**이다. 고장으로 오판하지 말 것.

옥씨부인전 → 玉氏夫人传 / オク氏夫人伝 偽りの身分 真実の人生

### 그래도 레인을 만든 이유 (d877e6e, `internal/kdb/wikidata_locale_drain.go`)

QID 를 **가진** 엔티티에서 로케일을 일괄로 꺼내는 경로가 **아예 없었다**:

- `wikidata_person_drain` 은 QID 가 **없는** candidate 에 QID 를 붙이는 승급 전용이다
  (45행에서 ref 보유분을 명시적으로 제외).
- QID 를 가진 쪽은 캐스케이드 L3 뿐인데 그라운딩 60~90초에 묶여 1회에 6건만 돈다.

`tmdb_locale_drain` 이 TMDb 쪽에서 똑같은 사각지대를 닫은 전례를 그대로 따랐다. 우물은
말랐지만 **사각지대 자체는 실재했고**, 앞으로 들어오는 엔티티는 이 레인이 자동으로 잡는다.

가드 3개 — 이름요소 제외 / 앵커 일치 확인(실데이터 359건 중 349건 통과, 차단 7건은 전부
검토 가치 있음: `DK↔Dplus Kia` 등) / **조회 실패는 기록하지 않음**(전송 실패를 내용
판정으로 남기면 위키데이터가 잠깐 죽은 사이 지나간 엔티티가 "레이블 없음"으로 잠긴다 —
이 저장소가 다섯 번 고친 계열).

## §4. 정본 94칸이 이름이 아니라 분류 딱지였다 (5bbaa03, 0106)

```
아이비   ja  アイビー (歌手)      →  アイビー
산이     ja  San E（ラッパー）     →  San E
초능력자 ja  超能力者 (映画)       →  超能力者
유니콘   zh  Unicorn (女子团体)    →  Unicorn
```

출처는 문서 제목이 아니라 **위키데이터 레이블 자체**다. Q6099788(아이비)의 ja 레이블이

것들은 그 오염값에서 파생된 2차 오염이다.

지우지 않고 **괄호만 떼서 교정**했다(빈칸 > 틀린값이지만, 여기선 교정하면 맞는 값이 된다).
이전 값은 `lane='disambig-strip:<loc>'` 에 남는다.

## §4.5. ★자기정정③ — 내가 만든 가드가 4건을 오염시켰다 (b109e83, 0107)

배포한 레인이 채운 11칸을 **검수했더니 4건이 틀렸다.** 넷 다 위키데이터 ko **레이블**은
우리 정본과 다르고 **별칭**에만 우리 이름이 있어서 내 앵커 가드를 통과한 것이다:

```
바이브(group)   ← Q87730005 "네이버 VIBE"  = 음악 스트리밍 서비스
DK(SEVENTEEN)  ← Q85976326 "Dplus Kia"   = 이스포츠 구단
제이(ENHYPEN)   ← Q26220991 "Jae"        = DAY6 제이 박(다른 인물)
라미            ← Q114690838 "김성경"
```

**별칭은 "그 이름으로도 불릴 수 있다"는 사전적 사실이지 동일성이 아니다.** 짧은 활동명
(DK·제이·MJ·바이브)은 별칭 목록에 흔해서, 별칭을 인정하면 동명이인 가드가 사실상 없는 것과
같아진다. 이 저장소가 반복해 밟은 함정이다("아몬드"→프랑스 영화, "이정후"→야구선수).

별칭 분기를 제거했다. 손해가 없다는 건 실측으로 확인했다 — 앵커 보유 359건 중 레이블 일치
349건(97%), ko 표기 자체가 없어 판별 불가 3건. 별칭 분기가 추가로 통과시킨 건 오탐뿐이었다.
회귀 테스트를 실제 QID·레이블로 고정했다(`wikidata_locale_drain_test.go`).

★**교훈: 새 레인이 처음 쓴 값은 반드시 눈으로 검수하라.** 11칸은 눈으로 볼 수 있는 양이고,
안 봤으면 4건이 그대로 남았다. 가드 3개를 붙이고도 뚫렸다.

### 다음 세션이 판정할 것 — `lane='wdlocale-bad-anchor'` 4건
