# KDB 운영 노트 — 세션을 넘어 반복해서 쓰이는 사실들

핸드오프(`KDB.handoff-*.md`)가 **한 세션에 무엇을 했는가**의 기록이라면, 이 문서는
**여러 세션에 걸쳐 반복해서 참조되는 사실과 함정**만 추린 것이다. 핸드오프는 차수가
쌓이면 아무도 42차까지 거슬러 읽지 않는다 — 그래서 "다음에도 또 필요할 것"만 여기 남긴다.

> **출처**: 이 문서는 에이전트 메모리
> (`.claude/projects/-data-home2-kdb-aiinplanet-com/memory/*.md`, gitignore 대상)의
> 내용을 팀이 읽을 수 있게 옮긴 것이다. 그쪽은 매 세션 자동 로드되는 실동 파일이라
> 지우거나 옮기면 안 된다. **둘 중 하나만 고치면 갈라진다** — 내용을 바꿀 때 양쪽을 함께
> 볼 것. 최종 갱신 2026-08-09.

## 1. 서버는 KDB 전용이 아니다 — 부하 보고가 오면 테넌트부터 분리하라

`/data/home2/kdb.aiinplanet.com` 호스트는 **8코어 멀티테넌트**다. kdb 외에 mediafine ·
issuetalk · trendbiz · kenterhub · nbntv · edipresso · hobbyissue · tdb 등이 같은 머신에 있다.

**KDB 평시 기준선** (2026-08-08 실측, 10초 지속 표본)

| 컨테이너 | CPU |
|---|---|
| kdb-app | 0.22% |
| kdb-db | 0.26% |
| kdb-searxng | 1.23% |
| **합계** | **1코어의 1.7% = 서버 전체의 0.2%** |

평시 load average 2.17 / 8코어 = 27%.

**왜 적어두나:** "kdb 실패로 서버 부하, CPU 높음" 보고를 받아 점검했는데 **KDB 가 이 서버에서
가장 가벼운 축**이었다. 진짜 소모원은 전부 KDB 밖이었다 — 최대는 root SSH 세션에 남겨진
무한 스핀 루프(`until [ $(wc -l < f) -gt $(wc -l < f) ]` — **자기 자신과 비교라 참이 될 수
없다**), 그다음이 mediafine · issuetalk 컨테이너의 `go run`.

**적용법**

- 부하 보고가 오면 **`docker stats` 를 컨테이너별로 먼저 찍어 테넌트를 분리**한다.
  보고에 프로젝트 이름이 들어 있다고 그 프로젝트가 원인인 게 아니다.
- **순간값이 아니라 누적 CPU 시간**(`ps -eo pid,time --sort=-time`)으로 정렬한다.
  순간값은 psql 쿼리 하나에도 흔들린다(실제로 kdb-db 가 0.06% ↔ 11% 로 요동쳤다).
- `docker stats --no-stream` 1회는 스파이크를 잡는다. **10초 이상 표본**을 봐라.
- 증상이 CPU 가 아닐 수 있다. 저 보고 때 KDB 의 진짜 실패는 **검색 엔진 7/10 사망**이었고
  CPU 로는 1.23% 였다.
- ⚠ **컨테이너 로그는 UTC, 호스트는 KST.** `docker logs` 본문 타임스탬프를 그대로 읽고
  "9시간 전에 멈췄다"고 오판하기 쉽다 — `docker logs --timestamps` 로 대조할 것.
- ⚠ **mt-fill 로그는 `docker logs kdb-app` 에 없다.** cron(매시 :20)이 `docker exec` 로
  돌려 `logs/locale-fill.log` 로 간다. 앱 로그만 보고 "미배선"이라 오판하기 쉽다.

## 2. CJK 채움 천장 — 어디까지가 부재이고 어디부터가 배선 구멍인가

### 소진이 실측된 경로 (다시 파지 말 것)

| 경로 | 상태 | 근거 |
|---|---|---|
| 위키데이터 레이블 | 소진 | 앵커 보유 207건 전수 → 순증 **7칸**. zh 레이블 96건 중 66건이 로마자·한글 복사본(`체리블렛→Cherry Bullet`) |
| TMDb | 소진 | 410건 처리 → 유효 앵커 22건(**수율 5%**). 무매칭 384건은 편성 시간대(`SBS 금토드라마`)·코너명이라 애초에 엔트리가 없다 |
| 구글번역 + 게이트 | 소진 | 이미 다 돌았다(gtranslate ja 1,888 · zh 2,664칸). gemma 게이트가 2,232건 기각. **오너 결정(08-07): 게이트 유지** |
| **MusicBrainz** | **소진(08-08 측정)** | zh 빈칸 표본 30건에서 **MB 매칭 93%인데 CJK 별칭 0%** |
| **보유 zh.wikipedia URL** | **소진(08-14 처리)** | 67건 전량 처리 → zh 60칸 + zh_hant 60칸. **다른 언어엔 애초에 없다**(en/id/es/vi/pt 0, ja 1) |
| **위키데이터 이름검색**(QID 미보유분) | **불가(08-15 측정)** | 표본 136건 → ko 라벨 일치 21%인데 **정답은 3%**. 나머지는 동음이의 쓰레기(`코뿔소`→코뿔소과, `판`→版本, `성기`→生殖器) |
| **보유 ko/en wiki URL → langlinks** | **소진(08-15 측정)** | 99건 전수 → **7칸**, 그중 6칸이 라틴 통과(`4minute` `UNB`). 진짜 CJK 획득 1건(`유정→磪有情`) |
| **iTunes jp/cn 스토어프론트** | **오염원(08-15 측정)** | trackId 앵커로 45건 조회 → jp/cn 이 **로마자 영문**을 돌려준다(`진또배기→Jinttopagi`, `들꽃이 될게요→Wild flower`). 현지 제목이 아니라 음반사 국제 메타데이터 |

⚠ **iTunes 레인을 "빈칸도 채우게" 열지 말 것.** `itunes.CountryFor` 가 jp/cn/tw 를 매핑해
두었고 `itunes_drain.go:86` 은 codex-fallback 로 **이미 채워진 칸의 라벨만 승격**하는 확인
전용이다. 사장된 배선처럼 보이지만 위 측정대로 **열면 canonical_ja 에 영문이 들어간다.**
이 값은 en 대조용으로만 쓸 수 있다.

**MusicBrainz 는 머리에만 있고 꼬리에는 없다.** `BTS→防弾少年団` `소녀시대→少女時代` 는
있지만 그 머리는 이미 채워져 있고, 방탄소년단·트와이스·블랙핑크는 **operator-locked 로
`BTS`/`TWICE`/`BLACKPINK`** 다 — 오너가 한자 번역이 아니라 라틴 브랜드명을 잠갔으므로
MB 값을 가져오면 그 결정을 덮는다. **레인을 만들 근거가 없다.**

### zh 소스 실측 분포 (2026-08-08)

gtranslate 28.5% · wikidata-label 22.3% · tmdb 14.8% · wikipedia-zh-variant 11.9% ·
codex 8% · romanization 6.4% · **searxng 경로 3.2%** · musicbrainz 0.2%

두 가지를 오해하기 쉽다.

1. **`wikipedia-zh-variant`(11.9%)는 새 출처가 아니다** — 기존 한자값의 간↔번 변환이라
   zh 가 아예 없는 건은 못 채운다. 획득이 아니라 파생이다.
2. **searxng 의 baidu/sogou 가 CAPTCHA 로 죽어도 CJK 병목이 아니다** — 3%다.

### ★그러나 "소스 없음"으로 닫기 전에 레인의 선정 조건부터 읽어라

천장은 맞았지만 그 **아래에 배선 구멍이 셋** 있었다(2026-08-08 하루에 발견·수정).
전부 "채울 수 없어서"가 아니라 **선정 쿼리가 안 집어서** 비어 있었다.

| # | 구멍 | 원인 |
|---|---|---|
| ① | 라틴 원제 18건이 8칸씩 | `canonical_ko ~ '^[ -~]+$'` (ASCII 전용). 최다 원인은 `It’s 2PM` 의 **곡선 아포스트로피 U+2019** — K-pop 표제의 표준 표기다 |
| ② | `term` 11건이 영구 미판정 | mt-fill 이 타입으로 제외만 하고 **판정을 원장에 안 남김** |
| ③ | 라틴 `zh` 의 `zh_hant` 영구 빈칸 | OpenCC 가 한자를 요구. 변환이 아니라 **항등**이 정답(`Wavve` 는 번체도 `Wavve`) |

결과 `active-cjk-actionable` **34 → 0**.

**네 번째를 찾으려면** 각 레인의 `~ '[...]'` 스크립트 조건과 `entity_type` 필터를 훑고
**"이 조건에 안 걸리는 건은 누가 판정하나"** 를 물어라.

### "레인이 판정했다"와 "레인이 판정을 기록했다"는 다르다

레인이 성공(UPDATE)만 기록하고 기각을 안 남기면, 못 채운 건이 경보에 영원히 "미판정"으로
남는다. **새 CJK 레인을 만들면** (a) `cjkFillLaneSQL` 에 field 를 추가하고
(b) **기각도 원장에 남겨야** 한다. `fill_input_hash` 가 `entity_type` 을 포함하므로(0104)
타입제외 판정은 타입이 고쳐지면 자동으로 풀린다 — 낙인 걱정 없이 남겨도 된다.

### 경보 읽는 법

`active-cjk-gap-raw`(~1,900)가 아니라 **`active-cjk-actionable`** 을 볼 것. raw 의 98%는
판정이 끝난 원본 부재분이다. `wd-locale` 이 `nothing-new` 만, `tmdb-anchor` 가 `no-match`
만, `mt-fill` 이 `bad-title` 만 쌓는 건 **정상**이다.

agency · channel_outlet · brand_place · character 는 권위 출처 자체가 없으니 기계번역을
붓지 말 것 — 오너 원칙 **"빈칸 > 틀린값"**.

**위 미착수 지렛대는 2026-08-14 에 처리했다**(`zhwiki-title` 레인, zh 60 + zh_hant 60칸).
남은 7건은 dataqa 오염판정 5 + en 뒷받침 실패 2. 다른 언어 위키백과에는 같은 지렛대가
**애초에 없다** — zh 만 컸던 이유는 다른 로케일엔 폴백 레인(gtranslate·kana-rule·
romanization)이 있는데 zh 엔 라틴 값을 만들 폴백이 없어서다.

이 레인의 가드는 **en 대조**다. 위험은 값이 아니라 **URL 이 남의 것**인 경우이고
(`라미`←/wiki/Lami 인데 en=Haram · `유정`(Brave Girls)←/wiki/磪有情=최유정), 문서 제목이
`canonical_en` 과 대소문자·구두점을 접어 일치할 때만 쓴다. 그 오매칭 셋은 **dataqa 가
이미 zh 오염으로 판정**해 두 경로가 독립적으로 같은 답을 냈다.

⚠ **미해결**: `IsValidSpellingForLocale("zh", …)` 는 zh 에 **한자를 요구**하는데,
라틴 zh(`Wavve`·`HYBE Labels`)를 쓰는 레인이 둘 있다(`DrainLatinKoToCJK`·
`DrainZhWikiTitle` — 둘 다 그 게이트를 안 지난다). **어느 쪽이 옳은지 정해진 적이 없다.**
넓히면 외부소스 23곳에 함께 영향이 가므로 소스별 드라이런이 먼저다.

### 남은 빈칸의 실제 상태 (2026-08-15 전수)

ja 947 · zh 1,375 · zh_hant 1,375. **zh_hant 는 zh 와 건수까지 동일하다** — opencc 전량
파생이라 독립 경로를 만들 이유가 없다. zh 를 채우면 따라온다.

이 중 **미판정은 ja 2 · zh 3 뿐**이고 나머지는 mt-fill 이 종결했다(ja bad-title 922 /
zh bad-title 1,029 · literal 291 · bad 44). 기각 사유 원문 45건을 읽었고 **전부 정당**
하다(`진이→斤`, `누난 너무 예뻐`→서술문, `들꽃이 될게요→Wild flower`, `필 스페셜→
感觉特别`). **게이트 완화는 답이 아니다** — 07-26 이후 지운 오염이 정확히 이 종류다.

**유일하게 남은 실행 가능분은 "라틴 통과" 128칸**(zh 99 · ja 29)이다. 기각 사유가
`영문 그대로·미번역` 계열이고 123건이 라틴 `canonical_en` 을 이미 갖고 있다 —
`비투비→BTOB` `투모로우바이투게더→TXT` `롤라팔루자→Lollapalooza`. 중화권·일본 매체가
실제로 라틴으로 쓰는 브랜드인데 게이트가 "번역 실패"로 본다. **타입 제한 필수**
(agency·channel_outlet·brand_place·group·event_tour). 제목류는 실제로 번역되므로 제외.
이건 위 `IsValidSpellingForLocale("zh")` 미해결과 **같은 결정**이다 — 따로 정하면 갈라진다.

### 하부구조: 근거 없는 active

ref 와 `source_urls` 이 **둘 다 전무한 active 가 4,573/11,361(40%)**. gap 엔티티 1,842 중
1,371 이 여기 속하고, 그 1,371 중 **1,243 이 `verification_tier='evidenced'`** 다 —
근거가 0인데 등급은 "근거 있음". 이들의 ja/zh 가 빈 건 채움 실패가 아니라 **외부에 존재
하지 않는 엔티티라서 이름이 없는 것**이다. 하류(채움)에서 풀 수 없고 intake 문제다.
CJK 채움률을 올리려는 시도가 여기서 막히면 **엔티티를 지우거나 등급을 내리는 쪽**이
정답이지 값을 만들어 넣는 쪽이 아니다.

## 3. 대리지표 함정 — 이 저장소가 반복해서 밟은 것

집계 숫자는 **모든 경우 그럴듯했다.** 틀렸다는 건 개별 값을 눈으로 봐야만 보였다.
`filled=144` 는 그 자체로는 성공처럼 읽힌다.

### 같은 유형의 반복 (전부 실제 사고)

1. **sitelink ≠ label** — 위키백과 *문서* 만 세고 위키데이터 *레이블* 을 안 세서 확보
   가능량을 3배 낮게 봤다(ja 40 → 실제 148).
2. **레이블의 존재 ≠ 유효성** — "zh 112건 확보 가능"이라 했는데 96건 중 66건이 로마자·
   한글 복사본. 실제 확보분 1건.
3. **별칭 일치 ≠ 동일성** — 앵커 가드가 위키데이터 별칭까지 인정해 **다른 대상의 이름**을
   4건 써넣었다(`바이브`←네이버 VIBE, `DK(SEVENTEEN)`←Dplus Kia 구단,
   `제이(ENHYPEN)`←DAY6 제이 박).
4. **alt 표기 일치 ≠ 동일성** — 3번을 고치고 **하루 만에** 다른 소스에서 재발. TMDb 가
   시즌을 항목 하나로 접고 각 시즌 제목을 alternative_titles 에 넣기 때문에, 시즌
   엔티티가 프랜차이즈 항목에 붙었다.
5. **검수 범위도 대리지표가 된다** — 레인의 *대상* 컬럼(ja/zh)만 봐서 "오염 2칸"으로
   셌는데, 그 앵커를 소비하는 레인이 **7개 로케일**을 채우고 있어 실제로는 6칸이었다.
6. **가드가 막던 것 ≠ 가드가 지키던 것** — ASCII 전용 가드를 넓혔더니 그 가드가 **우연히**
   격리하던 매큔-라이샤워 로마자(ŏ/ŭ)가 풀려 14칸이 오염됐다. 한 인물이 locale 마다 다른
   이름이 됐다(`양수경`: vi/es=`Yang Su-kyŏng` vs id/pt_br=`Yang Soo Kyung`).
7. **"개선 가능 N건" ≠ "N건을 고쳐야 한다"** — 세 항목을 처리하는데 **셋 다 드라이런이
   "하지 마라"고 답했다.** zh_hant 368건 덮어쓰기는 값이 바뀌는 6건이 전부 나빠졌고
   (`씨스타 SISTAR→Sistar` — 공식이 대문자다), 비ASCII 하이픈 32건은 30건이 정상 표기였다.
   **검증 소스가 더 높다고 값이 더 나은 게 아니다.**
8. **경보의 "사유"도 대리지표다** — `active-latin-gap` 이 ⚠ 85건을 울리며 사유에
   "규칙으로 채워지는 층이라 남으면 배선 문제"라고 **단언**했다. 믿고 두 단계를 팠는데
   297칸 전부 가드가 설명했다(**설명 안 되는 칸 0**). `active-cjk-gap-raw`·
   `never-examined-gap` 에 이은 **세 번째 판**이고, 이건 숫자만 부풀린 게 아니라
   사유가 **거짓을 적극적으로 주장**해 다음 세션을 없는 구멍으로 보낸다.
9. **두 레인이 각각 옳으면서 함께 틀릴 수 있다** — `candidate_ttl` 이 기각(notes 에
   `[ttl-expire:reject]` 스탬프) → `rejudge` 가 wikidata 근거로 복원 → TTL 의 재선정이
   `notes NOT LIKE '%[ttl-expire:%'` 라 **영영 다시 못 집는 한 방향 덫**. 레인을 하나씩
   읽으면 안 보이고, 두 기각의 **명제**("K-엔티티가 아니다" vs "기한 내 실증 실패")를
   나란히 놓아야 보인다.

10. **권위 소스도 스스로 정정한다 — 값의 *출처* 가 아니라 *시점* 이 낡는다**(08-15).
    TMDb 는 방영 전 **직역 가제**를 달았다가 공개 시점에 공식명으로 갈아탄다. `유부녀
    킬러` 의 en-US name 이 2026-06-30 18:24:53 UTC 에 `Married Woman Killer`→
    `A Bona Fide Killer` 로 바뀌고 21초 뒤 옛 값은 US alternative_title 로 강등됐다.
    우리는 06-10 에 읽어 저장했고, **모든 `canonical_en` 기록자가
    `COALESCE(canonical_en,'')=''` 가드**라 다시 읽는 레인이 없었다(tmdb_drain 은
    candidate 전용 + tmdb ref 보유분 제외, tmdb_locale_drain 은 타깃에서 en 제외).
    그 사이 `verification_tier='authoritative'` 는 계속 찍혔다 — 등급은
    `sig.auth_providers IS NOT NULL` 한 줄이라 **앵커 존재만 보고 값 출처·최신성은
    안 본다**(active authoritative 6,569건 중 5,233건이 추측 출처 값을 하나 이상 보유).

11. **"원작 언어 비-ko" 는 앵커 오부착 신호가 아니다**(08-15). 전수 스윕 73건 중
    대부분이 **정당한 외국 작품**이었다(`어느 가족`/万引き家族, `추락의 해부`,
    `와호장룡`, `은혼`). 확진 오부착은 3건뿐이고 전부 **"이름 불일치 ∧ 비-ko"
    교집합**에서만 나왔다(`소울메이트`→Soulm8te[en 2026], `헌트`→The Hunt[미국 2020],
    `범죄자`→犯罪者[ja]). 단일 조건으로 셌으면 70건 오탐 — KDB 가 한국 작품 전용이
    아니라는 전제부터 확인할 것.

    ⚠ **TMDb id 는 미디어 타입별로 별개 네임스페이스다.** `/tv/322571`(일본 드라마
    `犯罪者`)과 `/movie/322571`(`Presumed Guilty`, 1991)은 다른 작품이다. 조사 중 손으로
    media 를 틀리게 넣고 "같은 id 가 응답을 세 번 바꿨다"고 오진했다 — 실제로는 세 번 다
    다른 레코드였다. entity_type→media 매핑(drama/show=tv, 그 외=movie)을 조회마다 확인할 것.

13. **엄격한 레인이 거부한 것을 느슨한 레인이 되살린다**(08-15, 9번의 새 사례).
    `tmdb-anchor` 가 `범죄자` 를 **foreign-original 로 거부**하고 18분 뒤,
    `enricher/layers.go` 의 `tmdbTitles` 가 **같은 앵커를 생성**했다(ja `Hanzaisha`,
    zh `犯罪者` 재오염). 그 경로는 `Enrich` 의 정규화 제목 일치만 보고 ref 를 썼고,
    `ON CONFLICT ... SET external_id=EXCLUDED` 라 **운영자가 고쳐둔 재부착까지 덮었다**
    (실측: `소울메이트` 617882→1307118, `헌트` 727340→514847 로 원복. 고친 지 20분 만이다).
    처방: **제목 회수는 느슨해도 되지만 정체 단언(ref)은 앵커 드레인과 같은 엄격도**로만.
    규칙 사본을 만들지 말고 `SearchExactKoreanID` 를 그대로 호출한다(refguard-20260815-1).
    ★부수 교훈: **ref 를 지울 때 canonical_*_source 의 provider 라벨도 함께 해제**할 것 —
    라벨이 남으면 `api-source-no-ref` 계열 회수가 같은 식별자를 다시 찾으러 간다.
    ★★**고쳤다고 끝이 아니다.** 이 사고는 배포 후 경보를 다시 읽다가 발견했다. 데이터
    교정은 적용 직후가 아니라 **한 사이클 뒤에 다시 확인**해야 한다.

14. **라벨과 문서명은 어느 쪽도 항상 옳지 않다**(08-15, 1번의 반대 방향 재발).
    wikidata `ja` 라벨이 한자인데 jawiki **문서명**은 가타카나인 경우가 있다
    (`박병은` パク・ビョンウン, `임시완` イム・シワン — 우리 값이 이미 문서명과 같았다).
    라벨만 믿고 "교정"하면 멀쩡한 값을 한자로 훼손한다. 인물 ja 는 **문서명 우선,
    라벨은 차선**.

15. **두 값이 같다 ≠ 출처가 둘이다**(08-15). `mt-fill` 라틴 승계 분기를 "우리
    `canonical_en` == 구글 ko→zh 번역"으로 열었다. 근거가 둘이라 안전하다고 봤는데,
    채워진 85칸 중 **61칸의 `canonical_en_source` 가 `gtranslate`** 였다 — 우리 en 도
    구글이 만든 값이라 **같은 엔진이 같은 답을 낸 것**이었다. 그 순환논증으로
    `서순라길→Seosunra-gil` `에스케이재원→SK Jaewon` 같은 **한국어 이름의 로마자**가
    zh 칸에 들어갔다. 전량 되돌리고 증거 독립성 가드를 추가했다 — en 출처가 기계 추측이
    아니거나(`wikidata-label`·`local-usage`·`musicbrainz`…), `canonical_ko` 자체가
    라틴을 품을 때만(`몬스타X` `갓세븐(GOT7)` `MBC드라마넷`).
    처방: **합치를 근거로 삼기 전에 `*_source` 컬럼을 실제로 조회할 것.**
    ★부수 교훈: **승계도 값을 오염시킨다.** `아이들(G)I-DLE` 의 이미 깨진
    `canonical_en`(`G)I-DLE`)을 그대로 zh 로 복제했다 — 원본이 깨져 있으면 승계는
    깨짐을 퍼뜨린다(괄호 균형·시작문자 검사 추가).

16. **같은 규칙을 손으로 두 번 쓰면 한쪽이 빠진다 — 이번엔 확증 계약이었다**(08-15).
    `tier='evidenced'` 승급 전에 **근거 URL 을 대장(`kwave_kdb_evidence_refs`)에
    적재하고, 0건이면 승급하지 않는다**는 계약이 08-02 에 `candidate_evidence.go` 에만
    손으로 쓰였다. 같은 승급을 하는 `ActiveAuditPass`·`EvidencePass` 두 레인에는 빠져
    있었고, 그 둘은 검색 hit 의 **URL 을 `[]string` 으로 버린 뒤** evidenced 를 줬다.
    결과가 `evidenced-unretrievable` **3,419건**(전량 `verified_tier_at` 08-10 주)이다.
    지표는 그걸 세고 있었지만 **고치는 경로가 없었다** — 선정 쿼리가 `unverified` 만
    봐서 한 번 잘못 붙은 evidenced 는 영원히 재검토되지 않았다.
    처방: 규칙을 `requireEvidenceForTier`/`gatherRelevantHits` 로 뽑고 세 레인이 공유.
    선정에 **"evidenced 인데 되짚을 근거 없음"** 을 더해 자기치유(근거 남기면 유지,
    못 남기면 unverified 강등)로 만들었다. 실측 재조사 20건 → 근거 확보 8 · 강등 8.
    ★**일괄 강등하지 않은 이유**: 상당수는 실재가 맞고 근거만 안 남긴 것이다
    (`사랑의 리퀘스트`=KBS 1TV 예능). 전부 내리면 **참인 주장까지 버린다.**
    ★★**두 풀을 한 쿼리에서 `ORDER BY 급한것 DESC` 로 섞지 말 것** — unverified 565 가
    앞에 있으면 재조사 3,419 에 영원히 못 닿는다. `UNION ALL` + 각각 `LIMIT` 으로 나눈다.

17. **병합이 패자의 근거를 버렸다 — 서빙 중인 주요 엔티티가 앵커 0으로 살고 있었다**
    (08-15, 해결). 16번 강등이 드러냈다 — `몬스타X`(active, urls 0 · ref 0)가 강등되길래
    봤더니 `MONSTA X`(urls 9 · ref 1 · **authoritative**)와 `몬스타엑스`(urls 9 · ref 1)가
    **`status='rejected'`** 였다.

    원인은 `applyMerge` 다. 승자는 **LLM 의 `same_as` 가 지목**하고 가드는 `wellFormed`
    하나뿐이며, 은퇴시킬 때 **`aliases_ko` 와 person_details 만 옮기고** 외부 식별자·
    `source_urls`·로케일 표기·검증등급을 패자와 함께 죽였다. 근거 없는 쪽이 승자로 뽑히면
    근거가 통째로 사라진다.

    규모: 정규화 동명으로는 6건만 보였지만, **`aliases_ko` 연결고리**(applyMerge 가 패자의
    canonical_ko 를 승자 별칭에 넣는다)로 세니 **229쌍 · 근거 0인 승자 53건**이다.
    EXO · GOT7 · MONSTA X · RIIZE · DAY6 · TWS · BTOB · 더보이즈 · 티파니 영 · Wavve ·
    호텔 델 루나 · 유 퀴즈 온 더 블록 · 지구오락실이 전부 여기 있었다.

    처방: `carryEvidence`(decide.go)가 은퇴 **전에** 패자의 ref·source_urls·근거대장·
    로케일 빈칸·상위 검증등급을 승자로 옮긴다. **승자를 바꾸지 않는다** — 어느 쪽이
    살아남을지는 정체 판단이 아니라 표기 선택이고, 한국어 DB 에서는 한글이 canonical_ko 로
    남는 편이 옳다(`몬스타X` > `MONSTA X`). 피해는 이름이 아니라 근거 소실이다.
    기존 피해는 `kdb-app merge-evidence-repair` 로 230쌍 복구(같은 carryEvidence 재사용 —
    규칙을 SQL 로 다시 쓰지 않는다). 결과: 근거 0인 승자 **53 → 0**.

    ★**등급이 거짓말을 멈추자 비로소 보였다** — 빈 레코드가 `evidenced` 를 달고 있는
    동안에는 정상으로 보인다. 16번을 안 고쳤으면 17번은 못 찾았다.

18. **처리 속도의 천장은 네이버 쿼터다 — 그리고 쿼터 소진은 "근거 없음"으로 위장한다**
    (2026-08-16). 오너 요구는 "빠르게 확보해서 요청 오면 바로 제공"이다. 백로그를 전수로
    재니 병목이 하나였다 — `evidenced`-무근거 재조사 **3,365건**(다른 레인은 3~6일치).

    ⚠ **SearXNG 로 우회하려다 실재 K 를 무더기 오거부했다.** 재조사는 새 발굴이 아니라
    근거 회수이니 쿼터 없는 자체 SearXNG 를 앞에 두면 천장이 사라진다 — 논리는 맞았고
    실측이 막았다. 40건 배치에서 **강등 19 / 승급 1**(네이버 우선은 8/8)이었고 강등 목록에
    `니쥬` `BTS 진` `정택운(레오)` `우리 이혼했어요2` `멜론티켓` 이 있었다. 원인을 직접

    ★★**그 실험이 더 큰 잠복 결함을 드러냈다.** 네이버가 **쿼터 소진·장애로 실패**하면

    재조사 경로에서 **강등**된다. 즉 **쿼터가 떨어지는 순간부터 멀쩡한 엔티티가 줄줄이
    unverified 로 내려간다.** 로그에서 "근거가 없다"와 구별되지 않는다. 배치를 키울수록
    위험이 커지므로 **배치를 올리기 전에 이걸 먼저 막아야 했다.**

    넘긴다. 연속 `naverFailStop`(5)회면 쿼터 소진으로 보고 회차를 **강등 없이** 끝낸다.
    이 저장소가 네 번 고친 계열과 같다 — **전송실패는 판정이 아니다.**

19. **"굳이 네이버 API 가 필요한가?" — 필요 없었다. Google News RSS 가 무키·무쿼터다**
    (2026-08-16, 오너 질문이 병목을 없앴다).

    18번에서 나는 "네이버 1,000콜/일이 외부 제약이고 코드로 짜낼 여지가 없다, 플랜 상향이
    유일한 레버"라고 보고했다. **틀렸다.** 오너가 전제를 되물었고, 확인해 보니
    `https://news.google.com/rss/search?q=…&hl=ko&gl=KR&ceid=KR:ko` 가 **키도 쿼터도 없이**
    질의당 100건의 한국어 기사를 준다. 네이버가 못 찾던 것들이 여기선 전부 나온다:

    | 엔티티 | 네이버 결과 | Google News RSS |
    |---|---|---|
    | 니쥬 | 근거 부족 → 강등 | "니쥬, 日 첫 베스트 앨범 오리콘 1위"(알파경제) |
    | BTS 진 | 근거 부족 → 강등 | "BTS 진, 전 세계 매료시킨 '환상의 왕자님'"(스포츠동아) |
    | 멜론티켓 | 근거 부족 → 강등 | "'붕괴:스타레일' 전시 예매 멜론티켓 오픈"(매경) |
    | 부산MBC | 근거 부족 → 강등 | "제81주년 광복절 부산 경축식 개최"(부산MBC) |

    실측 효과: 60건 배치에서 **승급 23 / 강등 10**(네이버만일 때 40건에 10/8).
    처리량은 쿼터가 아니라 gemma 판정 속도가 정한다 — 재조사 3,365건이 **11일 → 약 40분**.

    ★**왜 SearXNG 는 안 되고 Google News 는 되나.** 품질이 아니라 **모양**이다. 웹검색은
    홈페이지를 주고(`멜론티켓`→"Melon::음악이 필요한 순간") 뉴스검색은 기사 제목을 준다
    (`…멜론티켓 오픈`). 적합성 게이트가 "엔티티명이 본문에 나오는가"를 보므로 기사 제목
    형태여야 통과한다. SearXNG 엔진 4개(baidu·sogou·startpage·mojeek)가 CAPTCHA/차단으로
    죽어 bing 만 살아 있는 것도 확인했지만, 그건 부차적이다 — bing 이 답해도 모양이 다르다.

    ★★**이 저장소는 Google News RSS 를 이미 무키 소스로 등록·검증해 두고 있었다**
    (`apikeys.go` 의 IssueURL, `probe.go` 의 `<item>` 프로브). 검색 클라이언트만 없어서
    아무도 쓰지 않았다. **"이미 있는 자산"을 먼저 훑는 것이 새 소스를 찾는 것보다 싸다.**

### 지표를 새로 정의할 때

`active-cjk-actionable`(44차) · `active-latin-actionable`(46차) 이 쓴 처방이 같다.
**세 번 다 같은 병이었으니 네 번째도 있다고 보는 게 맞다.**

- actionable 을 새로 정의하고 **종전 값은 `-raw` 로 남긴다**(경보 없음). 재정의가 무언가를
  가리는지 두 값의 차이로 항상 확인할 수 있어야 한다.
- **이름을 바꾼다** — 정의 변경이 조용히 묻히지 않게.
- 조건은 **레인의 가드를 그대로 뒤집어** 쓰고 정규식·상수도 재사용한다. 사본을 만들면
  규칙이 갈라진다.
- ★**0 을 보고하는 지표는 "정확해서 0"인지 "좁아서 0"인지 확인해야 믿을 수 있다.**
  가드를 하나씩 빼서 지표가 반응하는지 본다(47/26/3 이 정확히 나오고 합이 원래 값이면
  술어가 실제로 가르고 있는 것이다). 42차의 "임계 90일인데 DB 수명 70일"이 이 확인을
  안 한 경우다 — 그 조건들은 DB 역사상 한 번도 울릴 수 없었다.

### 적용법

- **큰 UPDATE 전에는 반드시 드라이런하고 표본을 읽는다** — 건수만 보지 않는다.
  **한 변경이 건드리는 가드가 둘이면 드라이런도 둘이다.** 결과 건수가 예상과 자릿수로
  다르면(14 → 144) 그건 성공이 아니라 **먼저 읽어야 할 신호**다.
- 새 레인이 처음 쓴 값은 양이 적을 때 **전건 검수**한다(11칸 중 4칸이 틀렸다).
- "X 가 있다"와 "X 를 쓸 수 있다"를 같은 쿼리에서 세지 않는다.
- **별칭·alt 표기·짧은 활동명으로 일치한 앵커는 무조건 의심한다** — 네 번 밟았다.
- 검수 쿼리의 컬럼 범위를 **하위 소비자 기준**으로 넓힌다.
- 가드를 넓히기 전에 **"이 조건이 우연히 걸러주던 게 뭔가"** 를 따로 묻는다. 통과시킬
  것 목록만 만들면 안 보인다.
- 값을 지어내 근거 있는 값을 덮지 않는다. 승격할 근거가 없으면 **남긴다.**
- **경보 사유를 근거로 쓰기 전에 "이 지표가 정말 그 명제를 재고 있나"를 먼저 묻는다** —
  세 번 중 세 번 아니었다(`candidate-stuck` 은 지금도 TTL 과 다른 컬럼으로 나이를 센다).
- 종결·복원처럼 **상태를 되돌리는 레인이 둘 이상이면 명제를 나란히 적어 본다.**
  한쪽의 산출물이 다른 쪽의 입력이 되면 덫이 생긴다.

### 보이지 않는 문자는 쓰는 쪽에서도 보이지 않는다

폭 0 문자(U+200B/200E/202C/FEFF 등)를 조회하려고 정규식 문자클래스에 **리터럴**을 넣었다가
일반 공백이 섞여 **수천 건 오탐**을 냈고, 그래서 "코드포인트로 다뤄라"고 주석에 써놓고는
정작 Go 소스에 리터럴 BOM 을 넣어 **컴파일을 깨뜨렸다**(Go 는 소스의 리터럴 BOM 을 거부한다).

**SQL 이든 Go 든 항상 `chr()` · `\uXXXX` 로 다룰 것.**

실해는 조용하다 — 보이지 않아 눈으로는 못 찾는데 문자열 비교가 어긋나 중복 탐지 · 별칭
매칭 · 소비자 검색이 전부 빗나간다. 유입 차단은 `IsValidSpellingForLocale`
(외부 소스 쓰기 경로의 공통 관문)에 들어 있다.

## 4. 빌드 · 배포

**빌드** — 호스트에 `go`/`gofmt` 가 없다. 컨테이너에서 돌리고 `-buildvcs=false` 를 붙인다
(마운트 소스에서 VCS 스탬핑이 실패한다).

```bash
docker run --rm -v "$PWD":/src -w /src \
  -v kdb_go-mod-cache:/go/pkg/mod -v kdb_go-build-cache:/root/.cache/go-build \
  -e PATH=/usr/local/go/bin:/usr/bin:/bin golang:1.23-bookworm sh -c '
  go build -buildvcs=false ./... && go test -buildvcs=false ./internal/...'
```

⚠ `cmd/kdb/main.go` · `internal/kdb/backlog_watch.go` · `internal/kdb/tmdb/tmdb.go` 는
**원래부터 gofmt 미준수**다(기존 주석 블록·import 순서). 전체 포맷하지 말 것.
`internal/kdb/romanize.go` 는 반대로 **준수 파일**이라 고칠 때 포맷을 유지해야 한다.

**배포** — compose 파일을 **둘 다** 넘긴다. `-f` 하나만 쓰면 override 가 자동 로드되지
않아 `dockers_backend` 정적 IP **172.19.0.240** 을 잃고 nginx 오라우팅이 난다(23d8be8).

```bash
sed -i 's/^KDB_APP_IMAGE=.*/KDB_APP_IMAGE=kdb-app:<tag>/; s/^KDB_BUILD_VERSION=.*/KDB_BUILD_VERSION=<tag>/' .env
docker build -q -f Dockerfile.kdb-app -t kdb-app:<tag> .
docker compose -f docker-compose.kdb.yml -f docker-compose.override.yml up -d kdb-app
docker inspect kdb-app --format '{{.Config.Image}} {{range .NetworkSettings.Networks}}{{.IPAddress}} {{end}}'
```

`KDB_APP_IMAGE`(compose 가 읽음)와 `KDB_BUILD_VERSION`(health 가 읽음,
`kdbapi/api.go:748`)은 **별개 변수**다. 후자를 안 바꾸면 health 가 옛 버전을 보고한다.
