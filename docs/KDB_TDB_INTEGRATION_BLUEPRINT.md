# KDB 통합 Entity 플랫폼 기획안 — TDB 흡수 및 전 분야 확장

작성: 2026-09-12 KST · 버전 1.3 · 상태: **필수 분류·동명별 값 소유 계약 보강 / 상세 구조 인수 전 / 흡수 금지**.
대상: KDB 운영자·개발팀·데이터 검수자·PressLocale 연동 개발팀.

이 문서는 실제 운영 DB의 읽기 전용 조사와 현행 코드를 바탕으로 작성했다.
설계 문서 작성이 데이터 이전, 정책 승인, 신규 기능 배포의 완료를 뜻하지 않는다.
이번 작업에서는 운영 데이터·스키마·worker·Gemma 일정·관리 화면을 변경하지 않았다.
기존 실행 계획 0~11은 유지하며, 본 문서는 그중 통합 작업의 선행 설계다.
실행 task·게이트·완료 증거·현재 상태의 단일 정본은 [KDB_INTEGRATION_TODO.md](KDB_INTEGRATION_TODO.md)다.
본 문서는 설계 근거이며 진행률을 따로 관리하지 않는다.
후속 상세 산출물: [분류 코드표](KDB_CLASSIFICATION_RULES.md), [목표 물리 구조 초안](KDB_TARGET_SCHEMA.md).
코드표는 기존 11유형 보존+brand/character 추가안을 명시한다. 운영 허용값 변경은 아직 하지 않았다.
후속 계약: [UUID/병합·분리](KDB_IDENTITY_CONTRACT.md), [표기·준비](KDB_NAME_READINESS_CONTRACT.md),
[필드/API 대조](KDB_ABSORPTION_CONTRACT_REVIEW.md), [UI 시안](KDB_ENTITY_ADMIN_UI_DESIGN.md), [인수 기준](KDB_ACCEPTANCE_LIMITS.md).
이 산출물의 구현/운영 완료 여부는 실행 원장만 따른다.

v1.1 변경: 사용자는 ‘TDB의 불필요한 기능을 가져오지 말고, 용도에 맞는 DB 구조를 먼저 설계한 뒤
흡수하라’고 지적했다. v1.0의 **TDB 운영 기능·이력·메뉴까지 일괄 흡수** 방침을 철회한다.
전체 원본을 조사하는 것, 복구용으로 보존하는 것, KDB 업무 DB에 넣는 것은 다르다.
아래 설계는 선택 흡수 원칙으로 수정했으며, 실제 컬럼/제약/조회 계약과 표본을 인수하기 전에는 적재하지 않는다.

v1.2 추가 지시: 인물의 기업인/연예인/가수/배우/정치인 등 분류와 장소/상품 등 Entity 구분은 필수다.
운영 기능을 줄이는 것과 필수 분류를 없애는 것은 다르다. 4.4~4.7에 분류 레지스트리·인물 직업·ID·
동명 판정·조회/검수 계약을 구체화했다. 직업/유형이 달라져도 동일 대상의 UUID는 바꾸지 않는다.

v1.3 추가 지시: 이름이 같은 가수와 배우가 다른 사람이면, 기사/출처 문맥에 맞는 사람에게 정확한 값을 줘야 한다.
4.8에 문맥 판정과 ID별 이름/프로필/보충·캐시 소유 계약을 추가했다. ID를 나누어 저장하는 것만으로 해결됐다고 보지 않는다.

## 1. 결정 요약

**TDB를 KDB로 흡수한다. 정치·경제·스포츠용 세 번째 마스터 DB는 만들지 않는다.**

| 결정 | 구체적 의미 |
|---|---|
| 운영 기반 | 기존 KDB PostgreSQL·Go 서비스·KDB 관리자 계정을 유지 |
| 통합 원본 | KDB 안의 `kentity_*`를 확장해 모든 분야가 사용하는 공통 Entity 마스터로 전환 |
| 기존 KDB | UUID와 고객 API를 보존하고, 연예 전용 컬럼·정책을 공통 모델로 단계적으로 옮김 |
| 기존 TDB | 목표 모델에 필요한 고유명사·언어별 표기·근거·식별 정보를 선별/변환해 흡수. 프로그램·운영 테이블 일괄 복제 금지 |
| 최종 TDB 서비스 | 실제 사용하는 고객 계약만 호환 전환. 의존성 해소 후 구 writer를 종료하며 원본 보관/폐기는 별도 승인 |
| 분야 확장 | 공통 유형+복수 분야+필요한 구분 정보. 분야마다 새 DB·전문 프로필·수집/관리 시스템을 만들지 않음 |
| 품질 원칙 | 목표 스키마·분류 기준·필드 매핑 확정 → 격리 검증 → 승인 범위만 흡수 |
| UI | 공통 검색·등록·검수·보충을 중심으로 통합. 이전 도구/고급 진단은 일반 운영 화면과 분리 |

기존 `kwave_entities`에 관광 컬럼과 새로운 언어 컬럼을 계속 추가하는 방식은 채택하지 않는다.
KDB를 유지한다는 것은 운영 기반을 유지한다는 뜻이며, 연예 전용 구조를 모든 분야에 강제한다는 뜻이 아니다.
통합은 단일 거대 테이블이 아니라 **하나의 정체성 원본 + 정규화된 이름·근거·관계 + 유형별 속성**이다.
단, 유형별 속성은 실제 판정·번역·갱신에 필요한 것만 추가한다. 분야가 생겼다는 이유로 빈 전문 테이블부터 만들지 않는다.

### 1.1 포함 기준 — 어떤 업무에 필요한가

목적은 ‘모든 분야의 백과사전/관광 운영 시스템’이 아니라 **뉴스에 등장하는 고유명사를 정확히 식별하고,
요청 언어의 적합한 표기를 제공하며, 모르는 대상·표기를 보충하고 잘못된 값을 정정하는 DB**다.

| 업무 | 꼭 제공할 결과 |
|---|---|
| U1 대상 식별 | 같은 이름의 서로 다른 인물·기관·장소를 구별한 UUID/후보 |
| U2 표기 제공 | locale별 이름·별칭, 사용 가능 여부와 근거 |
| U3 보충·갱신 | 무엇이 부족한지, 어떤 출처를 확인할지, 변경·철회를 어디에 반영할지 |
| U4 간단한 관리 | 등록·검색·분류·검수·오류 교정과 이력 |
| U5 기존 사용 보호 | 실제 이용 중인 ID/API/잠금/교정 계약 유지 또는 승인된 전환 |

새 필드·테이블·worker·메뉴는 U1~U5 중 사용처, 없을 때 실패하는 실제 사례,
값의 공급 출처, 갱신 책임을 설명해야 포함한다. ‘나중에 필요할 수 있다’만으로 1차 범위에 넣지 않는다.

| 범위 | 내용 | 처리 |
|---|---|---|
| 필수 데이터 | 원본/공통 ID, 유형, 이름·별칭·locale, 근거·출처, 품질/권리/잠금/버전 | 목표 스키마로 변환해 흡수 |
| 필요할 때의 구분 정보 | 인물의 직업·소속·공개 생년, 장소의 지역·주소·좌표, 조직의 관할/등록 ID | 동명 해소·유효 시점·고객 조회에 필요한 대상만. 없는 값은 NULL 허용 |
| 재사용할 보호 규칙 | 오연결 차단, 표기 위생, 출처 우선순위, 수동 정정 보호, 제한 재시도 | 공통 writer/보충 경로로 이식하고 회귀 시험. 옛 시스템 구조를 복제하지 않음 |
| 기본 흡수 제외 | TDB 에이전트 관리, 수집 레인 관리 UI, 원천 정찰 포털, 과거 실행 통계/로그 전체, 세션 | KDB 업무 DB/메뉴에 옮기지 않음. 필요한 감사 자료는 보관 정책으로 처리 |
| 후속 검토 | 범용 용어 조합 엔진, 전 분야 상세 프로필, 대회 성적/상품 사양 같은 별도 서비스 데이터 | 실제 요구와 별도 설계가 생기기 전 미구현 |

‘선택 흡수’는 관광지·음식점·스포츠 인물 같은 특정 분야를 임의로 버린다는 뜻이 아니다.
모든 원본 유형을 조사하되 뉴스 고유명사로 쓸 수 있는 기록을 같은 기준으로 평가한다.
현재 기사 수요는 보충 우선순위이지, 기존 유효 데이터를 삭제하거나 흡수 대상에서 자동 제외하는 조건이 아니다.
이번 수정은 기획 변경이며, 운영 중인 기능 중지·데이터 삭제·고객 계약 폐기를 허가하는 것이 아니다.

### 검토한 대안

| 대안 | 판단 |
|---|---|
| KDB·TDB·정치/경제 DB 세 개 유지 | 동일 인물·기관의 ID/표기/수정 책임이 중복되므로 제외 |
| TDB를 현재 KDB wide-column 테이블에 그대로 복사 | 장소 속성·행 기반 언어·출처 정책을 잃거나 임의 JSON에 묻으므로 제외 |
| 두 DB를 API에서만 합쳐 검색 | 전환기의 비교 수단으로만 사용. 이중 원본과 worker가 남으므로 최종 목표가 아님 |
| 목표 공통 Entity를 먼저 설계하고 필요한 TDB 자산만 흡수 | 채택. 필요한 데이터·보호 규칙·실사용 계약만 수렴 |

### 2.2 현행 구조와 쓰기 경로

```text
KDB 기존 worker / 관리자
  └─ kwave_entities: UUID + 고정 언어 컬럼 + 별칭 배열 + 연예 중심 유형
       ├─ kwave_entity_person_details: Entity UUID 기반 인물 속성
       ├─ kwave_entity_external_refs / relations / evidence_refs
       └─ 트리거 → kentity_entities: 동일 UUID 투영
                       └─ kentity_name_catalog: 기존 언어 컬럼을 읽는 view
  └─ kwave_persons: 별도 UUID / 한국어 이름 UNIQUE → 이름 기반 결합 위험

TDB 수집·정합·보충 worker / 관리자
  └─ tdb_src_records → tdb_place_links → tdb_places
                                  └─ tdb_place_names: 언어별 행 + 출처 + 잠금
  └─ tdb_sources / locales / type_locale_forms / terms / 검수·판정·감시

현재 시험 연결
  TDB 일부 QID → kentity_tdb_shadows → 독립 조사 → 후보/연결 검수
  ※ TDB 원본 전체를 KDB가 보유·관리하는 구조는 아직 아님
```

주요 현행 제약과 개선 이유:

1. `kwave_persons.name_ko`의 유일성과 이름 기반 연결은 동명이인 확대에 맞지 않는다.
   이전 조사에서 약 5,700개의 별도 인물 UUID가 존재했다. 전환 전 최신 수량·연결을 다시 검증한다.
2. `kentity_entities.entity_type`은 현재 11개 값의 CHECK이고, 분야는 8개 레지스트리다.
   UI에서 선택할 수 있다는 것과 그 분야의 데이터/공식 출처/자동 보충이 준비됐다는 것은 다르다.
3. 현행 `kentity_legacy_type()`은 일부 미열거 유형을 `work`로 투영한다.
   `event_tour`, `brand_place`, `channel_outlet` 등을 이 결과만 믿고 최종 분류하면 안 된다.
4. `kentity_names`는 현재 이름당 단일 `evidence_id`, 공통 이름 자체의 잠금 컬럼 없음,
   대표명 유일성은 종료일 없는 승인 행 중심이다. 복수 근거·필드 잠금·과거 기간 겹침 보호를 보강해야 한다.
5. TDB `verified_at`은 설치/재관측 과정에서도 갱신된다. 이를 공통 시스템의 사람 검수나 공식 표기 승인 시각으로 복사하면 안 된다.
6. TDB `installName()`과 DB 트리거의 위생·우선순위 보호를 가져와야 한다.
   현재 함수는 기존 대표명/잠금을 트랜잭션 밖에서 먼저 읽으므로, 통합 writer에서는 잠금 뒤 다시 판정한다.
   정합 경로의 `promoteTx` 등 직접 쓰기 경로도 함께 조사·통합해야 한다.
7. 기존 장소→역 오연결 두 건은 공통 편입을 막았을 뿐, 원본 링크와 파생 표기는 아직 교정하지 않았다.
8. 일반 Wikidata 검색·언어 준비 원장·기본 UI는 이미 구현되어 있으나, 전 분야 수집과 전량 이전을 대신하지 못한다.

Gemma는 추출/분류/번역 제안을 수행할 수 있지만 DB 직접 쓰기·동일인 승인·권리 승인 권한은 갖지 않는다.
API, 상태 관리, 이관 도구의 주 언어는 Go를 유지한다. 새로운 언어로 전면 재작성하지 않는다.

## 4. 분류 설계 — 유형, 분야, 직업, 기사 카테고리 분리

### 4.1 네 가지 축

| 축 | 질문 | 예 |
|---|---|---|
| Entity 유형 | 무엇인가? | 인물, 기관, 기업, 장소, 팀, 리그, 작품, 행사, 상품, 개념 |
| 세부 유형 | 어떤 종류인가? | 정당, 음식점 지점, 법정동, 영화, 경기장, 대회 회차 |
| 분야 | 어떤 영역에 관련되는가? 복수 가능 | 정치+행정, 경제+스포츠, 여행+문화 |
| 역할·관계 | 누구와 어떤 관계를 언제 가졌는가? | 선수로 팀 소속, 기업 대표 재임, 정당 소속, 작품 출연 |

기사의 ‘스포츠’ 카테고리는 Entity 후보를 찾는 문맥이지, 기사 속 기업·장소를 전부 운동선수나
스포츠 전용 Entity로 바꾸는 규칙이 아니다. 모든 카테고리에서 공통 Entity를 검색·사용할 수 있다.

가상 예: 선수였다가 기업인이 된 한 사람은 **인물 UUID 하나**에 스포츠/경제 분야와 기간별 역할을 갖는다.
이름이 같은 정치인과 선수는 **다른 UUID 두 개**다. 유명하다는 정도는 순위 속성이지 별도 인물 DB가 아니다.

### 4.2 분야 레지스트리와 확장 계약

1차 분야는 현행 8개를 유지한다: 정치, 행정, 경제, 사회, 연예, 스포츠, 여행, 문화.
과학기술·교육·보건·환경·국제 등은 같은 구조로 추가 가능하도록 설계한다.

1차 `kentity_domains`는 code/표시명/활성/정렬 중심의 단순 목록으로 유지한다.
계층형 분류 엔진, 분야별 별도 workflow, 동적 폼 생성기, 직업/관계의 범용 온톨로지 구축은 필수 범위에서 뺀다.
다만 아래의 **통제된 유형/세부유형/직업 코드와 FK 검증은 필수**다. 자유 문자열/태그만으로 대체하지 않는다.
유형 코드의 허용 범위·세부유형 대응·필수값은 상세 구조 설계에서 표로 고정하며,
기존 11개 유형 계약을 깨는 재분류/코드 변경은 별도 호환 검증 없이 하지 않는다.

새 분야는 원칙적으로 분야 코드와 Entity의 분야 연결을 추가하고 같은 등록·검색·검수·보충을 사용한다.
새 테이블은 ‘새 카테고리’ 때문이 아니라 기존 모델로 담을 수 없는 **입증된 필수 속성**이 있을 때만 검토한다.
표시 가능한 분야와 그 분야의 실제 데이터/언어/보충 준비 수준은 구분해 보여준다.
분야별 메뉴·독립 서버를 늘리는 대신 기존 운영 화면의 필터와 준비 집계를 사용한다.

분야 판정은 뉴스 분류 기준을 먼저 확정한다. 음식점이 사업체라고 전부 경제 분야를 붙이거나,
주소가 있다고 행정 분야를 붙이지 않는다. 여행 장소가 경제 기사에 등장해도 검색·사용에는 제한이 없다.

### 4.3 미분류를 해결하는 방식

- 서비스용 활성 Entity: 승인된 유형과 하나 이상의 근거 있는 분야가 있어야 한다.
- 아직 판단할 수 없는 원본: `classification_pending` 또는 `classification_conflict` 작업을 만들고 담당자·사유·다음 조치를 기록한다.
- 유형/분야 제안과 승인값을 분리하고, `assigned_by`, 근거, 규칙/모델 버전, 유효 기간을 기록한다.
- `other`, `unknown`, 빈 분야를 일괄 연예/여행으로 치환하지 않는다. ‘미분류 없음’은 숨김이나 강제 분류로 달성하지 않는다.
- 비고유명사·수집 시험 자료·기각 자료는 별도 제외 사유로 남긴다. 분류를 채웠다는 이유로 활성화하지 않는다.
- 최초 수용 기준은 **활성 서비스 대상 미분류 0 + 전체 원본 처리 상태 100% 설명 가능**이다.
  원천 자체가 불명확한 모든 기록을 즉시 올바르게 분류할 수 있다고 보장하지 않는다.

### 4.4 필수 분류 사전 — 분야가 아니라 대상의 성격을 구분한다

| 구분 축 | 통제된 코드 예 | 저장 방식 | 허용하지 않는 방식 |
|---|---|---|---|
| Entity 유형 | person / organization / company / team / league / location / work / event / product / concept | 모든 Entity가 하나의 기본 유형을 FK로 참조. unknown은 검수용 | 같은 이름이면 같은 유형/같은 대상이라고 간주 |
| 유형 안의 세부유형 | organization.political_party, location.restaurant, work.film, product.vehicle_model | 해당 유형 아래에만 허용된 subtype 코드 | 인물에게 음식점 세부유형, 기업에 선수 직업을 부여 |
| 인물 직업·직군 | businessperson, politician, entertainer, singer, actor, athlete 등 | person에만 복수 연결, 근거·판정 상태·필요한 유효 기간 | 가수/배우/정치인을 각각 다른 인물 master로 저장 |
| 뉴스 분야 | politics / economy / entertainment / sports 등 | Entity와 분야 N:M 연결 | 기사 카테고리마다 동일 Entity를 복제 |

회사·팀·리그를 조직 범주로 함께 탐색할 수 있어도 현행 별도 유형 코드/UUID를 즉시 합치지 않는다.
필요한 경우 목록의 ‘조직 전체’ 필터가 organization/company/team/league를 함께 조회하도록 한다.
유형과 세부유형은 적용 범위가 겹치지 않도록 코드표를 인수한다. 예: 법인은 company, 그 법인이 운영하는
점포는 location, 판매 상품은 product이며 같은 명칭이라도 별개 대상일 수 있다.
브랜드는 회사명과 동일하다고 company로 복제하지 않는다. 브랜드의 목표 유형은 상세 코드표에서 명시적으로 결정하고,
결정 전 임의 매핑하지 않는다. 허구 인물도 실존 person으로 자동 수용하지 않는다.

인물 직업의 초기 통제 사전 제안:

| 상위 직군 | 세부 직업 예 | 운영 규칙 |
|---|---|---|
| 기업인 `businessperson` | 창업자 `entrepreneur`, 기업 경영자 `executive` | 특정 기업의 대표/임원 여부는 해당 기업·기간 관계로 별도 기록 |
| 정치인 `politician` | 구체 직책은 국회의원·지방의원·선출직 등의 역할 코드로 관리 | 정당 소속·선거·재임은 관계/기간. 현재 직책으로 사람 ID를 만들지 않음 |
| 연예인 `entertainer` | 가수 `singer`, 배우 `actor`, 아이돌 `idol`, 방송인 `broadcaster`, 코미디언 `comedian` | 복수 직업 허용. singer+actor는 같은 인물에 두 연결 |
| 스포츠인 `sports_person` | 선수 `athlete`, 지도자 `coach`, 심판 `referee` | 종목·팀·시즌/소속 기간은 구분 정보/관계 |
| 언론·학술·문화 등 | 기자 `journalist`, 연구자 `researcher`, 작가 `writer`, 감독 `director`, 창작자 `creator` | 필요한 코드부터 추가. 전부 연예인이나 유명인으로 묶지 않음 |

‘유명인’은 직업이 아니다. 필요하면 주목도/수요로 표시하며 직업을 대체하지 않는다.
정치인/기업인 등의 상위 구분만 근거가 있으면 그 범위까지만 승인한다. 상세 직책을 추측하지 않는다.
가수와 배우가 각각 확인되면 둘 다 표시하고, 상위 ‘연예인’ 조회에는 하위 직업을 포함한다.
상위 직군은 표시/검색에 유도할 수 있으므로 singer를 넣을 때 entertainer를 별도 원본 행으로 매번 중복 생성하지 않는다.
직업 자체의 기간과 특정 조직 소속/직책의 기간은 다르다. 퇴사했다고 기업인 역할이나 과거 경력을 삭제하지 않는다.

사전은 1차에 얕고 통제된 상하 관계로 둔다. code/표시명/parent_code/활성/버전과 허용 범위를 관리한다.
순환·없는 부모·유형이 다른 세부유형은 거부한다. 코드명을 바꾸면 기존 code/ID는 유지하고 표시명만 변경한다.
사용하지 않는 코드의 폐기는 기존 참조를 처리한 뒤에만 허용하며, 이름 변경/직업 변경으로 Entity를 재생성하지 않는다.

### 4.5 분류·ID의 목표 테이블과 제약

아래는 v1.2의 구체 설계 제안이다. 적용 SQL이 아니며 기존 migration/소비자에 대한 검증 후 확정한다.

| 테이블 | 주요 키/필드 | 핵심 제약/책임 |
|---|---|---|
| `kentity_types` | code PK, label_ko, enabled | 기존 11개 코드를 먼저 대응. 새로운 유형은 검수된 코드 변경으로 추가 |
| `kentity_subtypes` | (entity_type, code) PK, label_ko, 선택적 parent_code | 유형 FK. 부모는 같은 유형. 코드 순환 금지 |
| `kentity_entities` | id UUID PK, entity_type FK, subtype, canonical_ko, classification_status, status, revision | (entity_type, subtype) FK. 이름 UNIQUE 금지. 표기/분류/정체성 승인 상태를 혼동하지 않음 |
| `kentity_role_types` | code PK, label_ko, parent_code FK, enabled | 직군/직업의 통제 사전. 자유 입력 역할은 제안으로만 접수 |
| `kentity_person_roles` | id UUID PK, entity_id, role_code FK, status, evidence_id, valid_from/until, revision | person 전용. 복수 직업 허용. 같은 승인 직업/기간의 중복을 차단하고 근거를 보존 |
| `kentity_domains` / `kentity_entity_domains` | code PK / (entity_id, domain) PK, 판정 근거·상태 | 복수 뉴스 분야. 직업 테이블과 별개 |
| `kentity_relations` | subject_id, predicate, object_id, 역할, 기간, 근거 | 특정 기업 임원/정당 소속/팀 소속 등. 해당 predicate의 주체/대상 유형 검증 |
| `kentity_names` | name_id, entity_id FK, locale, value, kind, status, evidence_id | 동일 이름이 다른 UUID에서 자유롭게 공존. 이름을 FK 대상으로 쓰지 않음 |
| 원본 binding | (source_system, source_table, source_id) 고유 키, entity_id FK, 상태·판정 | 원본 단위 재실행 멱등성. 원본 수용과 기존 Entity와의 동일 대상 승인은 구분 |
| 동일/별개 판정 이력 | 정렬된 두 UUID, decision, 근거, 양쪽 revision, actor, 시각 | distinct/possible_same/confirmed_same 판정. 이름이 같다는 이유로 distinct를 자동 취소하지 않음 |

직업의 person 전용 제약은 UI만으로 보장하지 않는다. 예를 들어 하위 테이블의 유형을 person으로 제한하고
`(entity_id, entity_type) → entities(id, entity_type)` 복합 FK와 부모의 해당 조합 UNIQUE를 사용하거나,
동등한 DB 잠금/제약으로 보장한다. FK 방식은 하위 테이블에 person 고정 식별 컬럼도 필요하다.
유형 변경 시 남아 있는 직업·전문 정보·관계가 모순되지 않는지 같은 트랜잭션에서 확인한다.
동일 직업의 중복 방지는 ‘한 사람은 직업 하나’라는 제약이 아니다. singer와 actor의 동시 승인은 정상이다.
모르는 유효 기간은 NULL로 두고 관측 시각과 구분한다. 날짜가 모호하면 과거 특정 시점의 직업/소속을 단정하지 않는다.

필수 조회 인덱스 후보: 이름(locale, 정규화 검색값), 직업(role_code, entity_id),
분야(domain, entity_id), 유형/세부유형/상태, 외부 ID(namespace, value), 관계(object_id, predicate, 기간).
검색용 정규화는 후보 탐색을 위한 것이며 현실 대상의 유일 키로 사용하지 않는다.
실제 질의 계획/선택도로 인덱스를 인수하고 모든 조합의 인덱스를 미리 만들지 않는다.
분류 제안/확정/충돌과 이름의 승인 상태는 별도 계약이다. 분류 코드가 들어갔다는 이유로 인물 정체성이나 번역값을 승인하지 않는다.

### 4.6 이름이 같아도 독립적으로 관리되는 예

아래 이름/ID/소속은 구조 설명용 가상 예다. 실제 등록이나 동일인 판정이 아니다.
표의 짧은 ID는 설명용이며 DB에는 UUID를 쓴다.

| 이름 | UUID 별칭 | 유형 | 직업/세부유형 | 구분 근거 | 처리 |
|---|---|---|---|---|---|
| 김민수 | E-P01 | person | singer + actor | 가상 소속사 A/인물 원천 ID A | 한 사람, 직업 2개 |
| 김민수 | E-P02 | person | politician | 가상 정당 B/인물 원천 ID B | P01과 다른 인물 |
| 김민수 | E-P03 | person | businessperson | 가상 기업 C/인물 원천 ID C | P01/P02와 다른 인물 |
| 김민수 | E-P04 | person | athlete | 가상 팀 D/선수 원천 ID D | 별도 인물 |
| 푸른별 | E-C01 | company | 법인 | 공개 법인 식별자 | 이름이 같아도 아래 장소/상품과 별개 |
| 푸른별 | E-L01 | location | 점포 | 지역·주소·시설 ID | 기업과는 필요하면 운영 관계로 연결 |
| 푸른별 | E-G01 | product | 상품 모델 | 제조 주체·모델 식별자 | 기업/점포와 같은 Entity로 병합하지 않음 |

유형·직업·소속은 구분 근거지만 그것만으로 동일인/별개 인물을 항상 확정할 수는 없다.
같은 직업·같은 생년·같은 이름의 사람도 여러 명일 수 있고, 한 사람이 직업·소속을 바꿀 수도 있다.
UUID는 **확정한 대상을 독립 관리하는 키**이지 ‘어느 원본이 같은 사람인가’를 저절로 해결하는 도구가 아니다.

ID 사용 규칙:

1. 새 Entity ID는 이름·직업·카테고리의 해시나 조합으로 만들지 않는다. 불변 UUID를 배정한다.
2. 개명·직업 변경·분야 추가·소속 이동은 같은 UUID의 이름/분류/관계 버전 변경이다.
3. 후보 검색은 복수 결과를 허용한다. 가장 유명한 사람이나 첫 번째 결과에 자동 연결하지 않는다.
4. 한 기사에 동명이인 둘이 등장하면 span별로 다른 UUID를 연결한다. 이름 문자열 하나로 기사 전체를 묶지 않는다.
5. 기존 `kwave_persons.name_ko UNIQUE`는 신규 공통 모델에 승계하지 않는다. 기존 경로는 검증된 UUID 호환을 거쳐 전환한다.
6. 병합은 별도 검수/트랜잭션 작업이다. 외부 ID 충돌·잠금·기존 distinct 판정·영향 참조를 확인한다.
7. 병합 후에도 이전 ID/원본 binding과 변경 이력을 유지한다. 잘못된 병합의 분리와 모호한 참조 재검수 경로를 설계한다.

### 4.7 등록·검색·분류 검증 시나리오

- 등록에서 Entity 유형을 먼저 선택한다. 인물은 복수 직업, 장소/상품 등은 해당 세부유형을 입력한다.
  분야·이름·출처·구분 정보는 같은 공통 폼에서 제공하고, 관련 없는 필드는 숨긴다.
- 같은 이름이 있으면 ID·직업·소속/지역·근거를 나란히 제시해 기존 대상 선택/새 대상 등록/보류를 지원한다.
  후보 목록이 있다는 이유로 새 동명이인 등록을 막지 않는다.
- 목록에는 `이름 | 유형 | 직업/세부유형 | 분야 | 구분 정보 | 짧은 ID | 검증 상태`를 표시한다.
  직업별 필터와 연예인→가수/배우 등 하위 직업 포함 검색을 제공한다. 모든 분야가 동일 검색/API를 사용한다.
- 상세에서 ID가 기준임을 보여주며 직업·분야 변경과 동일인 병합 버튼을 분리한다.
- KDB의 primary_role/secondary_roles는 통제 사전으로 대응하고 원본 근거를 검증한다.
  TDB person을 일괄 연예인/스포츠인으로 바꾸지 않는다. 직업 근거가 없으면 분류 검수 상태를 남긴다.
- 미확인 직업/세부유형을 ‘기타’라는 승인값으로 숨기지 않는다. 분류 완성도와 언어 준비를 별도 표시한다.

흡수 전 필수 시험: 같은 이름의 같은/다른 직업 인물, 복수 직업 1인, 같은 생년의 다른 인물,
인물/기업/장소/상품의 동명, 직업 변경 후 ID 유지, 개명 후 옛 이름 검색,
유형 변경의 관계 제약, 기존 distinct의 자동 병합 차단, 원본 재수집/재실행의 ID 보존.
이 사례를 통과하기 전 ‘이름이 같은 대상도 안전하게 관리된다’고 인수하지 않는다.

### 4.8 동명 인물의 값은 문맥으로 대상을 확인한 뒤 해당 ID에만 저장·제공

아래는 가상 예다. 가수/배우의 공식 외국어 표기는 서로 다를 수 있고, 우연히 같아도 각자의 근거가 필요하다.

| 원본의 대상 | 공통 ID 별칭 | 승인 직업 | 이름/프로필의 소유 |
|---|---|---|---|
| 가상 가수 김민수 | E-S01 | singer | 가수 원천이 확인한 언어별 이름·소속·음반 관계는 S01 소유 |
| 가상 배우 김민수 | E-A01 | actor | 배우 원천이 확인한 언어별 이름·소속·출연 관계는 A01 소유 |
| 실제로 두 활동을 하는 별도 인물 | E-SA01 | singer + actor | 동일인 근거가 있는 경우만 한 ID에 복수 직업 |

첫 두 사람을 이름 일치로 한 사람의 복수 직업으로 합치지 않는다. 반대로 동일 인물이 두 직업으로 발견됐다고
직업마다 서로 다른 UUID를 최종 확정하지 않는다. 두 경우 모두 정체성 근거를 먼저 확인한다.

처리 계약:

1. 이름·별칭 검색은 후보 ID 목록을 반환한다. `한국어 이름 → 사람 ID 하나` 조회를 정답 계약으로 사용하지 않는다.
2. 원본/기사에서 직업 표현, 소속, 작품·음반·팀, 알려진 공개 출생 정보, 기사 시점과 승인 외부 ID를 확인한다.
   ‘신곡’이면 가수, ‘드라마’면 배우라는 키워드 하나로 확정하지 않는다. 배우도 음반 활동을 할 수 있다.
3. 이미 검증된 원본 ID 연결을 우선 활용하고, 문맥·유형·기간의 상충 여부를 재검사한다.
   남는 후보가 여럿이거나 근거가 부족하면 `ambiguous`와 후보/사유를 반환해 검수한다.
4. 대상을 확정한 뒤 이름·별칭·직업·소속·관계·근거에 **동일한 entity_id**를 부여한다.
   다른 Entity의 근거나 값은 저장 제약에서 거부한다. 이름이 같아도 서로의 빈칸을 대신 채우지 않는다.
5. 보충 job은 이름 대신 entity_id+locale+정책/입력 버전을 기준으로 실행한다.
   비동기 조사 결과 적용 직전에 대상 revision·원본 연결·잠금·근거가 여전히 유효한지 재확인한다.
6. 이름의 준비/캐시는 entity_id+locale+표기/정책 버전으로 분리하고, 고객 전용 값은 tenant도 구분한다.
   후보 해소 캐시는 문맥/후보 집합/기사 버전을 포함하거나 사용하지 않는다. 이름 하나를 키로 확정 표기를 캐시하지 않는다.
7. 한 기사에 가수 김민수와 배우 김민수가 함께 나오면 각 mention/span을 S01/A01로 따로 연결한다.
   Glossary도 이름 문자열 하나가 아니라 해당 mention의 UUID별 표기를 사용한다.
8. 분류 수정과 동일인 병합은 분리한다. S01에 actor 역할을 추가하려면 S01의 활동 근거가 필요하며,
   동명 A01이 배우라는 사실은 S01의 직업 추가 근거가 될 수 없다.

UI에서는 동명 검색 결과를 한 행에 뭉개지 않고 이름·직업·소속·주요 활동·구분 ID·근거 상태로 나란히 보여준다.
운영자가 대상 ID를 선택한 뒤 ‘이 값이 어느 사람에게 저장되는가’를 확인할 수 있어야 한다.
기사 span 연결기의 구현은 기존 TODO 9에 남지만, 데이터 흡수/보충 단계의 ID별 값 소유 보호는 선행 필수다.

추가 인수 시험: 동명 가수/배우의 언어값이 각각 올바른 ID에서만 조회되고 서로 전파되지 않는지,
두 직업을 가진 한 사람은 두 필터에서 같은 UUID로 검색되는지, 문맥 없는 이름은 보류되는지,
동일 기사 속 두 인물이 서로 다른 표기를 사용하는지, 오래된 보충 응답이 다른 대상/버전을 덮어쓰지 않는지 검증한다.

## 5. 목표 데이터 모델과 ERD

아래는 필요한 논리 역할의 설계다. ‘기존 확장’은 일부 테이블이 존재한다는 뜻이다.
이를 각각 새 테이블/서비스로 무조건 만들지 않는다. 기존 구조 재사용과 실제 쿼리로 물리 설계를 확정해야 한다.

```text
source_objects ──< source_bindings >── entities ──< entity_domains >── domains
      │                                  │
      ├─ 필요한 근거 스냅샷 참조         ├─< names ──< name_evidence >─ evidence
      └─ migration_items                 ├─< external_ids ──────────── evidence
                                         ├─< relations >── entities
                                         ├─< person_roles >── role_types
                                         ├─ 필요한 인물/장소 구분 정보
                                         ├─< classification_decisions / field_locks / audit_events
                                         └─ 요청 언어 준비 (기사 연결/고객 표기는 후속)

sources ──< policy_versions ──< evidence ──< evidence_dependencies
preparations ──< requested_locale_readiness ──< fill_jobs / readiness_events
migration_runs ──< batches ──< migration_items
```

### 5.1 공통 원본과 근거

| 테이블/영역 | 핵심 내용 | 조치 |
|---|---|---|
| `kentity_entities` | UUID, 유형/세부유형, 한국어 표시명, 상태, 최초 origin, 현재 write_owner, revision, 시각 | 기존 확장. UUID는 정체성, 이름은 UNIQUE 아님 |
| `kentity_entity_domains` | Entity↔분야, 승인 상태, 근거, 판정 버전·기간 | 기존 확장. 복수 분야와 이력 보장 |
| `kentity_names` | Entity, 정확 locale, 표기, 종류, recorded/generated/translated 구분, 승인/기간/revision | 기존 확장. raw 이름과 정규화값 분리, 필드 잠금 연동 |
| `kentity_name_evidence` | 이름 버전↔근거 버전 N:M, 지지/반박, 선택 이유 | 추가. 동일 철자를 지지하는 여러 출처를 보존 |
| `kentity_evidence` | identity/name/relation/classification/attribute 주장, 원천 레코드 버전, 관측·검증·권리 | 기존 확장. 출처 홈페이지 하나를 모든 사실의 근거로 재사용하지 않음 |
| `kentity_evidence_dependencies` | 정체성 근거→파생 이름/속성의 의존 | 기존 확장. 철회 영향 추적 |
| `kentity_external_ids` | provider+namespace+외부 ID, 주장/검증/충돌/철회 | 기존 확장. 미검증 중복 주장은 보존, 승인된 동시 소유권은 유일 |
| `kentity_relations` | subject, predicate, object, 역할, 기간, 근거, 상태 | 기존 확장. 소속·재임·이적·출연·개최·운영 관계 |
| `kentity_sources`, `kentity_source_policy_versions` | 출처/경로별 허용 범위, 우선순위, 언어, 형식, 보관·공급 조건, 버전 | 추가. API 비밀값은 secret reference로 분리 |
| `kentity_field_locks`, `kentity_audit_events` | Entity/이름/필드 잠금, 보호 사유·권한, 변경 전후·주체·revision | 추가/확장. 자동 수정 방지와 공급 차단은 별도 플래그 |
| 고객별 표기 override | tenant+Entity+locale별 편집 표기 | 후속 범위. 기존 격리는 유지하되 흡수의 선행 개발 조건으로 추가하지 않음 |

표시용 `canonical_ko`는 한국어 대표 표기의 투영값으로 수렴시킨다. 원본 철자와 수정 이력은 이름/근거 계층에 남긴다.
`origin_system`은 불변이고 ‘현재 어디서 수정하는가’는 `write_owner`가 나타낸다.
최종적으로 활성 master의 writer는 common 서비스(`native`의 현재 의미) 하나다. source adapter는 제안만 제출한다.

### 5.2 목적에 필요한 최소 구분 정보

| 대상 | 필요할 때 유지하는 정보 | 1차에 만들지 않는 기능 |
|---|---|---|
| 인물 | 직업·종목·소속·직책, 구분에 필요한 공개 생년, 이름/소속의 유효 기간 | 전 생애 약력·수상 경력·성적·모든 가족관계 DB |
| 기관·기업·팀 | 기관 성격, 등록 namespace/ID, 관할 국가, 구분에 필요한 소속/운영 관계 | 기업 재무 DB, 구단 운영/선수 기록 시스템 |
| 장소 | 지역 코드, 지점 구분, 필요 시 주소/좌표와 근거 | 지도 서비스, 여행 일정/예약/상권 관리, 영문주소 전량 신규 생성 |
| 작품·행사·상품 | 종류, 제작/주최/제조 주체, 동명 구분에 필요한 발표 연도/회차 | 전 작품 카탈로그·시즌 편성·상품 상세 사양 관리 |

공통 `kentity_relations`를 필요한 소속·역할·기간에 재사용한다. 관계없는 Entity는 관계 행 없이 존재할 수 있다.
1차 전문 저장소 후보는 UUID 기반 기존 인물 구분 정보와 최소 장소 구분 정보다.
기관/작품/행사/상품별 새 profile 테이블, 범용 EAV/JSON 속성 엔진은 기본안에서 제외한다.
반면 유형/세부유형/직업의 통제 사전과 person_roles는 4.4~4.5의 필수 분류 구조이며 제외 대상이 아니다.
주요 조회·동명 판정이 현재 구조로 불가능하다는 사례가 확인될 때만 필요한 타입 있는 필드/테이블을 추가한다.

주소·좌표를 ‘관광 정보’라고 무조건 버리지는 않는다. 동일 이름 장소를 가르는 데 필요하면 필수 구분 근거다.
반대로 좌표가 있다는 이유만으로 인물·행사를 장소로 바꾸지 않는다. 의미 불명확 값은 원본 참조로 보류한다.
생년만 있으면 생일을 만들어 넣지 않으며, 기간을 모르면 NULL로 둔다. 부족한 정보는 검수/보충으로 처리한다.

### 5.2.1 흡수 전 작성·인수할 물리 구조 명세

본 기획안의 테이블 이름 나열이나 ERD만으로 설계가 완료된 것으로 간주하지 않는다.

- 각 컬럼: 타입, NULL/기본값, 의미, U1~U5 사용처, 원본/생성 주체, 갱신 책임, 보존 필요성.
- 각 테이블: PK/FK/유일성/인덱스, 삭제·병합·기간·잠금·동시 수정 계약.
- 필수 조회: 이름+문맥 후보 검색, Entity의 locale별 값/근거, 최근 신규·미분류, 부족한 언어의 다음 작업.
- 유형/분야: 판정 규칙, 복수 분야를 추가할 근거, unknown/보류 경계, 기사 카테고리와의 관계.
- 실제 표본: 동명 인물, 조직/브랜드/지점, 장소/역, 작품/행사, 원본 other와 다국어 별칭.
- 원본→목표 매핑: 포함/조건부/보관만/제외, 변환·검증 규칙과 예상 수량/오류 처리.

이 명세와 격리 표본 검증이 인수되기 전에는 TDB 대량 후보를 공통 운영 테이블에 먼저 넣지 않는다.

### 5.3 원본 수용과 동일 대상 판정은 다른 연결

추가 제안:

- `kentity_source_objects`: `(source_system, source_table, source_id)` 고유 키, 최초/최종 관측, 원본 revision, 상태/병합 대상, 권리 상태.
- `kentity_source_record_versions`: 허용된 원본 값/해시/근거/변환 버전. 큰 payload는 권리·보존 정책을 적용한 제한 저장소 참조.
- `kentity_source_bindings`: 원본 레코드를 수용한 공통 UUID와 binding 종류(`imported_record`, `reviewed_same_entity`), 유효 버전.
- 기존 `kentity_crosswalks`: 서로 다른 원본이 같은 현실 대상을 가리키는지에 대한 검수와 결정 이력을 재사용·확장.
- `kentity_redirects`, `kentity_identity_decisions`: 승인된 병합/분리의 이전 ID, 새 대상, 적용 버전, 영향 범위, 근거.

TDB 한 레코드를 별도 공통 후보로 받아 ID를 배정하는 것은 ‘이 레코드를 보존했다’는 뜻이다.
그것이 기존 KDB 인물과 동일하다는 승인이나, TDB의 모든 외부 링크가 정확하다는 승인을 뜻하지 않는다.
현재 crosswalk의 `confirmed`를 전량 적재 완료 표식으로 사용하지 않는다.

### 5.4 무결성 계약

1. 모든 FK와 근거는 같은 Entity/원본 버전을 가리켜야 한다. 다른 사람의 근거로 이름을 승인할 수 없다.
2. 승인 대표명은 Entity+locale+용도+적용 기간에서 모호하게 겹치면 안 된다.
   현재 부분 UNIQUE만으로 과거/미래 기간을 보장할 수 없으므로 범위 제약 또는 직렬화된 기간 검사를 추가한다.
3. 동일 이름은 여러 Entity에서 허용한다. 검색용 정규화 문자열에도 전역 UNIQUE를 걸지 않는다.
4. 쓰기는 expected revision, writer epoch, 잠금, 정책 버전을 확인한 뒤 수행한다. 감사 로그·outbox를 같은 트랜잭션에 쓴다.
5. 대표명 교체는 기존 대표명 종료/대안 보존/새 대표명/근거/이력을 한 번에 커밋한다.
6. 정체성·출처 근거가 철회되면 종속 준비 상태와 캐시를 무효화한다. 독립된 유효 근거가 남으면 재평가한다.
7. 물리 삭제로 기존 ID와 이력을 잃지 않는다. 비활성/철회/redirect가 기본이며 개인정보·권리상 삭제는 별도 승인 정책을 따른다.

## 6. ID 및 동명이인·동명이소 정책

### 6.1 기존 ID 보존

- KDB `kwave_entities.id`: 현재 공통 UUID를 그대로 유지한다.
- `kwave_persons.id`: 기존 인물 ID를 별도 namespace로 보존하고 검증된 대응으로만 연결한다.
- TDB `tdb_places.id`: 원본 ID를 보존하고, 목표 구조에 수용하기로 승인된 기록에만 신규 공통 UUID를 한 번 배정한다.
  `source_objects/source_bindings` 고유 키로 재실행 시 같은 배정을 재사용한다. 기존 편입 1건의 UUID도 유지한다.
- 이전 시점에는 동일 이름의 KDB/TDB 두 레코드가 별도 공통 후보로 공존할 수 있다.
  중복 의심 군집을 UI에 묶어 보여주되 사용 시 하나를 임의 선택하지 않는다.
- TDB API의 기존 UUID 조회는 KDB의 binding/redirect를 통해 계속 동작한다. 고객에게 새 ID로 무조건 재등록을 요구하지 않는다.

### 6.2 동일 대상 판정

후보 검색은 이름·별칭·외부 ID·문맥으로 넓게 하되, 최종 판정은 유형과 독립 식별 근거로 좁힌다.

| 상황 | 정책 |
|---|---|
| 이름만 일치, 검색 결과 1개 | 동일인 자동 승인 불가 |
| 이름+직업 또는 생년만 일치 | 후보 순위 정보. 확정 근거로 부족 |
| 검증된 같은 외부 ID, 유형/소속·시기 등 일치, 충돌 없음 | 출처별 인수된 규칙 안에서만 연결 자동 승인 후보 |
| 같은 QID지만 상점과 역, 회사와 브랜드 등 유형 충돌 | ID 오류로 보류. 동일 QID를 강제 병합 근거로 쓰지 않음 |
| 동명 장소, 비슷한 좌표 | 같은 건물의 다른 시설/점포 가능. 주소·시설 종류·운영 주체·원천 식별자를 함께 검증 |
| 재임·이적·개명 | 기존 Entity에 기간 있는 관계/이름 버전을 추가 |
| 이미 합쳐진 두 사람이 사실 다른 사람 | 분리 검수. 표기·관계·기사 참조를 근거별로 재배정하고 옛 오결정을 보존 |

초기 **실제 Entity 병합은 수동 승인**을 기본으로 한다. 높은 정밀도가 인수된 제한 규칙만 이후 자동화한다.
병합은 UUID 정렬 순서 잠금 + SERIALIZABLE + source/target revision 및 근거 재확인 + 단일 트랜잭션으로 처리한다.
오래된 모델 응답, 잠금 후 변경, 동일 ID의 동시 승인, 순환 merge, 부분 실패를 반드시 시험한다.
SERIALIZABLE 충돌은 트랜잭션 전체를 제한 재시도해야 한다. [PostgreSQL 트랜잭션 격리 문서](https://www.postgresql.org/docs/current/transaction-iso.html).

## 7. 언어별 표기·근거·자동 보충 정책

### 7.1 표기의 의미를 보존한다

- locale은 BCP 47 형태로 저장하되 원천 locale도 별도 보존한다.
  언어·문자·지역은 다른 구성 요소다. [RFC 5646](https://www.rfc-editor.org/rfc/rfc5646.html).
- 본 서비스 정책에서는 `zh`, `zh-Hans`, `zh-Hant`를 임의로 같은 준비 상태로 취급하지 않는다.
  `pt`를 자동으로 `pt-BR`로 승격하지 않는다. 변환에는 근거·변환 버전·검증이 필요하다.
- `canonical/alias/transliteration`은 쓰임새, `recorded/generated/translated/unknown`은 값이 생긴 방식이다.
  두 축과 ‘공식 출처 여부’, ‘검수 상태’를 따로 표시한다. recorded라도 공식 명칭이라는 뜻은 아니다.
- TDB의 기존 canonical과 KDB의 wide-column 값은 우선 `legacy/unverified` 관측이다.
  승인 근거가 재현되는 항목만 규칙 기반 재검증하며, 268만 행을 LLM으로 다시 생성하지 않는다.
- 영어 fallback이나 생성 음역은 명시된 대체 정책에서만 사용하고, 요청 언어의 검증 표기 수에 넣지 않는다.
- `no_form`은 표기가 존재하지 않는다는 근거 있는 결론이다. 검색 실패·한도 초과·근거 부족은 `no_evidence` 등으로 구분한다.
  알 수 없는 인명 한자를 추측해 확정하지 않는다.

### 7.2 요청 단위 준비와 데이터 보유율을 분리한다

기존 `kentity_preparations`, `kentity_locale_readiness`, `kentity_locale_fill_jobs`를 확장한다.
일반 카탈로그의 값 보유율과 실제 기사 요청의 준비율은 서로 다른 지표다.

strict-ready 조건: 확정된 Entity, 요구 시점에 유효한 이름, 정확 locale, 허용된 형식,
유효한 정체성/이름 근거와 공급 권리, 서비스 차단 없음, 대표명 충돌 없음.
현재 common readiness의 recorded/verified 요구를 느슨하게 바꾸지 않는다.
기존 `operator_locked`가 수정·공급을 함께 막는 경로는 이관 시 의미를 명시하고,
신규 `edit_lock`/`serve_block` 분리는 호환 테스트 후 적용한다. 기존 보호를 자동 해제하지 않는다.

준비 응답에는 `entity_id`, `name_id/revision`, `entity_revision`, `policy_version`, 근거 버전,
`requested_locale`, `served_locale`, `form`, `ready_at`, `fallback_reason`을 추적한다.
최초 ready 시각과 현재 유효 여부를 분리한다. 근거 철회 뒤 과거 ready 이력은 보존하되 현재값을 제공하지 않는다.

### 7.3 신규 발견과 빈칸 채움

```text
기사/명부/운영자 입력
  → 기존 이름·별칭 후보 검색 + 전체 문맥의 미지 후보 추출
  → 원본 관측 저장 / 동일 요청 중복 제거
  → 유형·분야 제안 → 정체성 해소
  → 요청 locale별 기존 근거 확인 → 부족한 출처만 조사
  → 형식·권리·정체성·충돌 검사
  → 제한 자동 승인 또는 담당자 검수
  → 공통 writer 저장 → 준비 재평가 → 캐시/소비자 변경 이벤트
```

이미 알려진 이름이 문장에 있다고 NER를 생략해 다른 신규 인물을 놓치지 않는다.
사전 일치가 나왔더라도 문맥이 기존 인물과 다르면 신규 동명이인 후보를 만들 수 있어야 한다.
Gemma 결과의 confidence 하나로 HIGH/MEDIUM/LOW를 결정하지 않는다. 원천별 신뢰성,
독립성, 동일 대상 판정, 정확 locale, 생성 여부, 권리를 조합한 설명 가능한 규칙을 둔다.

신규 카테고리의 원천 후보는 다음처럼 준비한다. **아래는 수집 후보 범주이며 API 사용권·표기 정답을 확인했다는 뜻이 아니다.**

| 분야 | 우선 조사할 원천 범주 | 핵심 연결 근거 |
|---|---|---|
| 정치·행정 | 의회/선거/정당/기관의 공식 명부·약력·조직 자료 | 공개 인물·기관 ID, 선거/직책·기간 |
| 경제 | 기업 공시·법인/거래소 공개 자료·기업 공식 사이트 | 법인/상장 ID, 관할 국가, 임원 재임 |
| 스포츠 | 협회·리그·구단의 선수/팀/대회 등록 자료 | 종목, 선수 ID, 시즌·팀 소속 |
| 사회·교육 | 공공기관·대학·단체의 명부·공식 소개 | 기관 ID, 법인/캠퍼스 구분, 공적 역할 |
| 연예·문화 | 기존 KDB 원천 + 소속사/제작사/작품의 공식 자료 | 인물/작품 ID, 제작·출연·소속 관계 |
| 여행 | 기존 TDB 원천과 정합·주소·표기 규칙 | 장소 ID, 주소·좌표·유형, 원천 선언명 |

분야마다 출처 하나만 연결하면 끝나는 것이 아니다. adapter는 탐색·증분 수집·삭제 탐지·언어 공급·
rate limit·조건 검토·독립 정답 세트·실패 재현을 제공해야 production으로 표시한다.

### 7.4 재시도와 갱신

| 원인 | 다음 행동 | 반복 방지 |
|---|---|---|
| 일시 네트워크/429/서버 오류 | 지수 backoff+jitter, Retry-After 준수 | 출처/작업별 횟수·기간·비용 한도 |
| 근거 없음 | 다른 승인 원천 또는 주기 완화 | 같은 입력·출처의 즉시 반복 금지 |
| 동명/유형 충돌 | 추가 정체성 근거 또는 검수 | LLM 무한 재질문 금지 |
| 정책/권리 차단 | 정책 책임자 검토 | 모델/수집기로 우회 금지 |
| 잠금/수동 정정 | 관측은 저장, 변경은 승인 요청 | 새 worker도 잠금 존중 |
| 새 원천/기사/정체성 변경 | 관련 판정만 무효화 후 재평가 | fingerprint+정책/모델 버전별 예산 |

입력 지문이 같아도 TTL 만료·신뢰 근거 철회·정책 변경에는 다시 평가한다.
출처 전체가 아니라 **출처×수집 경로×유형×locale**별로 소진을 판단한다.
정정은 잘못된 외부 링크와 그 링크에서 파생된 이름·속성·준비 상태까지 추적한다.
재유입 방지 writer/정책을 먼저 배포한 뒤 기존 오염을 교정한다.

### 7.5 권리와 데이터 경계

`enabled/live`는 이용권 승인 상태가 아니다. AI Hub 등 조건 미확인 데이터는 공급 허용으로 자동 변경하지 않는다.
보관 허용, 내부 연구 허용, 외부 조회/일괄 export 허용을 분리한다.
이전 원장에는 전체 원본 ID와 처리 상태를 남기되, 값의 보관 권한까지 미확인이면 원래 제한 저장소에 두고 참조한다.
승인되면 KDB의 권한 분리된 보존 영역으로 옮긴다. 이 영역은 세 번째 서비스 마스터가 아니다.
외부 공급 보류값은 일반 관리자 역할·검색 인덱스·Gemma 프롬프트·로그·export에도 새지 않게 한다.
사용 조건 미해결 건은 보류 수량과 선택 범위 밖인지를 명시한다. 선택 범위의 처리 완료를 ‘모든 원본 공급 가능’으로 확대하지 않는다.
원본 폐기는 어떤 경우에도 별도 승인 없이 진행하지 않는다.
민감한 개인 정보는 수집 목적에 필요하지 않으면 가져오지 않는다. 주민등록번호·사적 연락처를 동일인 키로 사용하지 않는다.

## 8. TDB 전체 조사 및 선택 흡수 명세

### 8.1 유형별 대응 — 실제 19개 유형 전부

### 8.3 기능은 선별 재사용하며 운영 테이블은 일괄 이전하지 않는다

| TDB 테이블군 | 선택 처리와 운영 범위 |
|---|---|
| sources, locales, place_types | 채택된 데이터/보충 경로의 출처·언어·유형 설정만 공통 정책에 대응. 비밀값과 불필요한 수집 설정은 제외 |
| type_locale_forms, invariants | 이름 오류를 막는 규칙·근거를 재사용하고 공통 시험에 편입. 별도 TDB 정책/감시 시스템 복제 금지 |
| terms | 원칙적으로 보관/참조만. 필요한 고유명사 표기 규칙은 선별 검토. 범용 접미/접두/치환 엔진은 1차 제외 |
| review_queue, holds, corrections | 수용 대상에 영향을 주는 미해결 교정·동명·잠금과 재시도 차단 사유만 공통 검수/보충에 변환 |

| discovery_methods, source_candidates | 필요한 원천 후보만 개발/운영 작업 목록으로 이관. 자동 원천 정찰 포털은 1차 제외 |
| fill_lanes, locale_supply, name_misses | 필요한 결손·공급 근거만 기존 common readiness/fill에 통합. 레인 엔진/스케줄을 그대로 복제하지 않음 |
| serve_stats, worker_state, agents, agent_runs | 업무 DB 흡수 제외. 필요한 역사·복구 자료만 원본 보관. 과거 lease/running 상태 재실행 금지 |
| api_consumers | 실제 고객·필수 계약만 별도 호환 인수. 사용하지 않는 TDB 공급 관리 시스템을 재구축하지 않음 |
| admin_users, admin_sessions | KDB 기존 권한 체계 사용. 필요한 담당자만 승인 매핑/재인증. 세션 복사 금지 |

원본 전체 테이블/컬럼을 **조사 manifest**에 고정하고 `include / conditional / archive_only / exclude`로 판정한다.
각 포함 필드는 목표 컬럼·U1~U5 사용처·검증 기준을 먼저 갖춰야 한다. 보관만/제외는 사유와 영향을 기록한다.
조사 대상 변경을 확인하지 않은 채 이전 범위를 임의 확대하지 않는다. 선택된 범위의 미계상/손실은 허용하지 않는다.
업무 DB에 넣지 않는 것과 원본을 삭제하는 것은 다르다. 보존 기간·권리·인증 전환은 별도 승인 사항이다.

분류 우선순위: 이미 검수된 구조적 직업/기관/작품 정보 → 유효 외부 식별자·공식 근거 → 규칙 후보 → 모델 제안 → 사람 검수.
`athlete → sports`, `politician → politics`도 원본 역할의 신뢰 상태를 확인한 뒤 승인한다.
`other` 역할, 상충하는 정보, 단순 category_hint는 확정 규칙에 넣지 않는다.
배우·가수·방송인 등을 연예로 분류하되, 추가 활동 분야를 삭제하지 않는다.
기존 ‘연예 범위 밖’ 기각과 ‘실제 비고유명사/오염’ 기각을 구분해 전자만 근거 있는 재검토 대상으로 삼는다.

## 10. 실제 이관 절차 — 설계 선확정, 선별·검증 후 흡수

### 10.0 적재 전 통과해야 할 순서

```text
사용 목적·제외 기능 확정
  → 목표 논리/물리 스키마·유형/분야 기준·조회 계약
  → 원본 필드 선택·변환·권리·갱신 매핑
  → 격리 표본으로 동명/언어/교정/조회 검증
  → 설계 인수
  → 승인 범위 추출·정규화·분류·검증
  → 목표 KDB에 반영 → 수량 대조·운영 확인
```

분류·정체성·필드 대응을 나중으로 미루기 위해 운영 KDB를 staging으로 쓰지 않는다.
staging은 승인된 실험 범위의 격리/임시 작업 영역이며 영구적인 제3 마스터나 운영 메뉴가 아니다.
불확실한 기록은 원본/조사 원장에 보류한다. 지속 검수가 필요한 후보만 후보 관리 계약에 따라 수용한다.

### 10.1 이관 원장

`kentity_migration_runs/batches/items`를 추가한다. run에는 원본 snapshot ID, schema/policy/mapper 버전,
관측 시각, 테이블별 수량, 완료된 batch, digest, 검증 결과, 승인자, cutover 상태를 남긴다.
item은 원본의 완전한 PK로 식별한다. Entity 수, 이름 수, 원천 링크 수를 한 분모로 합치지 않는다.

조사 원장의 모든 기록은 포함/조건부/보관만/제외 중 하나의 판정을 갖는다.
**승인된 흡수 범위**에서 항목별 처리 상태를 상호 배타적으로 집계한다:
`not_copied / copied / restricted_reference / failed / explicitly_excluded`.
분류·정체성·표기 승인·소비자 사용 가능 여부는 별도 축이다.
조사 판정률, 승인 범위 적재율, 보류/제외 수량, 유형 분류율, 언어 준비율, 소비자 전환율을 따로 보여준다.
전체 536,329건을 분모로 한 흡수율과 승인 범위의 처리율을 혼동하지 않으며 승인 범위 변경 이력도 남긴다.

검증식:

```text
조사 스냅샷의 원본 PK 전체 = 포함 + 조건부 + 보관만 + 제외 (미계상 0)
승인된 흡수 원본 PK 전체 = 처리 상태별 합 (중복/미계상 0)
승인된 이름/필드별 원본 키 → 목표 값/근거 또는 명시적 보류·실패
공통 Entity 수 ≠ KDB 원본 수 + TDB 원본 수 (검증된 중복과 후보가 있기 때문)
```

SHA/digest는 복사 일치의 증거이지 내용의 정확성 증거가 아니다.
같은 입력 batch 재처리 결과는 ID·판정·이름·시도 예산을 중복 생성하지 않아야 한다.

### 10.2 스냅샷과 증분을 놓치지 않는 방법

설계 인수와 흡수 범위 확정 이후의 기본안은 **필요한 변경 원장(outbox) → 일관 스냅샷 → 증분 재생 → 최종 대조**다.
변경 원장 설치는 후속 승인·검증을 거쳐 수행하며 이번 설계 작업에서 적용하지 않는다.

1. TDB 및 이전 대상 KDB의 실제 쓰기 테이블·트리거·직접 SQL을 열거한다.
2. 이전 대상 INSERT/UPDATE/DELETE/잠금/병합/출처 정책 변경을 원본 트랜잭션 안에서 원장에 기록한다.
   이름·링크만 바뀌어도 해당 Entity가 재평가되게 한다.
3. READ ONLY REPEATABLE READ의 동일 스냅샷으로 원본 데이터를 export한다.
   오래 열린 트랜잭션의 운영 영향을 측정하고 복원본/일관 백업 활용 여부를 결정한다.
   PostgreSQL의 반복 읽기는 트랜잭션 동안 같은 스냅샷을 제공한다. [공식 격리 문서](https://www.postgresql.org/docs/current/transaction-iso.html).
4. 승인된 필드를 작은 batch로 staging에 적재하고, PK/해시/수량/필드 검사 후 해당 batch를 원자적으로 공개한다.
   전체 수백만 행을 운영 대상의 단일 거대 쓰기 트랜잭션으로 처리하지 않는다.
5. outbox의 **미처리 커밋 행**을 lease/ack 방식으로 읽는다. 증가하는 sequence ID나 updated_at의 최댓값만 저장해 건너뛰지 않는다.
   늦게 커밋한 낮은 ID, 같은 시각의 여러 PK, 변경 중 페이지 이동, 삭제된 행을 반드시 시험한다.
6. 이벤트는 영향을 받은 원본 키의 재관측 요청으로 취급한다. 같은 원본 키의 적용을 직렬화하고
   원본 revision·대상 generation을 비교해 오래된 결과의 덮어쓰기/삭제 뒤 부활을 막는다.
7. 삭제·병합 이벤트는 tombstone/연결 재검수로 전달한다. 원천 한 곳에서 사라졌다는 이유로 독립 근거가 있는 공통 Entity를 삭제하지 않는다.
8. 동결된 기준점의 원본/대상 PK 집합과 필드 해시를 최종 대조한다. 미처리·실패 이벤트가 없고 delta가 수렴해야 전환한다.

QID 기준 페이지는 전량 이전 커서로 쓰지 않는다. 원본 테이블의 완전한 PK가 기준이다.
타임스탬프 polling은 빠른 보조 동기화일 뿐 삭제·지연 커밋까지 포함한 완전성 증거가 아니다.
기존의 알려진 10개 ID 정기 관측도 전체 증분 수집을 대체하지 않는다.
기존 운영에 검증된 CDC가 있다면 snapshot과 연결한 논리 변경 스트림을 대안으로 채택할 수 있지만,
slot/WAL 보존·중복 재생·장애 복구를 먼저 시험해야 한다. [PostgreSQL 논리 디코딩 개념](https://www.postgresql.org/docs/current/logicaldecoding-explanation.html).

### 10.3 단계적 단일 쓰기 전환

| 시기 | 기존 원본 | 공통 KDB | 소비자 |
|---|---|---|---|
| 조사/설계 | 기존 writer 유지 | 운영 흡수 없음. 읽기 조사와 격리 표본만 | 기존 API 유지 |
| 인수 후 이전 | 승인된 원천/필드 변경 기록 | 목표 계약을 통과한 값/후보만 반영·대조 | 기존 API 유지 |
| 제한 검증 | 이전하지 않은 범위만 기존 writer | 승인된 cohort만 common writer로 전환 | 일부 고객 dual-read 비교 후 전환 |
| 최종 전환 | 대상 쓰기 중지·진행 job 배출·epoch 폐기 | 마지막 delta 적용, 새 epoch로 단일 쓰기 | 호환 API가 KDB 조회 |
| 안정화 이후 | 실사용 의존성 해소 후 구 writer 종료, 보관 정책 적용 | 채택된 공급 경로만 공통 보충에 연결. 불필요한 TDB worker 재구축 없음 | 합의된 공급 범위의 단일 원본은 KDB |

writer 전환은 현재의 ‘기각 Entity 채택’ 기능만으로 active 전체에 적용할 수 없다.
활성 데이터 전환용 감사된 migration/명령과 이전 소유자의 DB 권한·writer epoch 차단을 별도로 구현한다.
원본과 공통을 무제한 양방향 동기화하지 않는다. 새 스키마를 못 쓰는 구 worker가 보호 정책을 우회할 수 없어야 한다.
무중단을 선약하지 않는다. 필요한 짧은 쓰기 중지 시간은 복원본 실측 후 공지·승인한다.

### 10.4 복구

- 전환 전 실패: 해당 run/batch를 미공개로 두고 기존 서비스 유지. 원본이나 다른 run을 삭제하지 않는다.
- 전환 중 실패: 새 쓰기를 차단하고 원장으로 적용 위치를 확인한 뒤 진행/되돌림을 선택한다.
- **전환 후 새 쓰기가 있으면 단순히 옛 DB/이미지로 복귀하지 않는다.** 새 쓰기 보존과 역변환 호환성 확인이 선행되어야 한다.
- DB schema는 forward-only. 호환 가능한 직전 앱으로 롤백하거나 보정 migration으로 복구한다.
- 백업은 생성 확인뿐 아니라 격리 복원, ID 조회·준비·잠금·권리·트리거·소비자 API까지 검증한다.
- TDB 원본 폐기/백업 만료는 별도 사용자 승인 사항이다. 이전 완료와 동시에 자동 삭제하지 않는다.

## 11. KDB 관리자 UI 기획

UI는 먼저 정보 구조·표시 정의·업무 흐름을 합의하고, 이후 **화면+실제 API+검증을 묶은 작은 단위**로 구현한다.
UI 전체를 가짜 수치로 완성하거나, 백엔드 전체가 끝날 때까지 화면을 방치하는 방식은 채택하지 않는다.

### 11.1 정보 구조

```text
KDB 통합 Entity 관리
├─ 운영 개요: 신규/준비/검수/장애, 작업 목적·비용 요약
├─ 고유명사: 검색·등록·상세, 분야/유형은 같은 화면의 필터
├─ 검수함: 동명·분류·표기·교정·권리 보류를 작업 종류로 구분
├─ 언어 준비·보충: 부족한 값·이유·다음 행동·실행 결과
└─ 설정: 필요한 출처/정책·고객/API/권한

운영자 전용 도구 (평소 기본 메뉴와 분리)
  └─ TDB 이전 보고서·제한 재시도, 고급 진단·감사
```

기존 `/admin/kentity`, `/admin/preparations`, `/admin/workflow`를 확장한다.
현재 `/admin/kentity/tdb`는 제한 연결 비교 화면이다. 승인 범위의 이전 보고서는 운영자 도구로 재편하고,
이전 완료 후에는 일상 메뉴에서 숨겨 복구/감사 필요 시 접근한다. 상시 별도 TDB 운영 콘솔을 만들지 않는다.
새 URL은 구현 시 라우팅 계약으로 확정한다. 아래 화면 명칭은 이미 구현됐다는 뜻이 아니다.

### 11.2 업무별 수용 기준 — 독립 메뉴 개수를 의미하지 않음

| 화면 | 필수 표시 | 실제 조치 |
|---|---|---|
| 운영 개요 | 분야별 원본/후보/활성/준비 수, 최근 등록, 오류·지연, 집계 기준 시각 | 분야 클릭→같은 필터 목록, 신규 등록·검수 진입 |
| 전체 Entity | 구분명, UUID, 유형, 복수 분야, 원본 KDB/TDB, 검증 상태, 요청 언어, 실제 갱신 종류 | 상세, 출처/이전 항목 이동, 새 후보와 중복 비교 |
| TDB 흡수 보고서 | 전체 조사/승인 범위의 분모, 포함·조건부·보관만·제외, 적재/보류/실패, delta 지연 | 운영자만 원본 UUID/전후값·제한 batch 재시도 |
| Entity 상세 | 기본 정보·이름·근거·이력 중심, 필요한 대상에만 구분 정보 노출 | 수정 제안, 승인·보류·철회, 잠금, 동일/별개/분리 검토 |
| 검수함 | 문제 종류, 심각도, 영향 고객·요청, 담당자, 기한, 시도 이력 | claim/할당, 근거 비교, 승인·기각·추가 조사 |
| 언어 준비 | ko/en/ja/zh-Hans/zh-Hant 등 정확 locale별 값·형식·근거·ready 시각 | 왜 비었는지 확인, 한도 있는 조사·검수 |
| 출처·정책 설정 | 실제 쓰는 출처의 권리·우선순위·언어·수집 상태 | 승인 이력·적용 버전·영향 미리보기. 복잡한 정책 편집 엔진은 제외 |
| 작업·Gemma 요약 | 작업 목적·스케줄, 호출/시간·실제 승인 변경·준비 증가 | 기존 workflow 상세 연결, 제한 재시도. 전용 감독 시스템 복제 없음 |

전체 Entity 기본 목록은 50개 단위의 서버 검색을 유지하되 대량 페이지는 keyset으로 확장한다.
필터 URL·정렬·snapshot 기준을 유지하고, 분야 카드 합계는 복수 분야 중복 때문에 전체 UUID 수와 다를 수 있음을 표시한다.
관리자 페이지마다 수백만 행 전체를 스캔하지 않도록 읽기 모델/집계를 두고 **집계 지연·실패를 0건으로 표시하지 않는다.**

Entity 상세의 표기 표는 다음 정보를 한 행에서 비교할 수 있어야 한다:
`locale | 현재 값 | 공식/기록/생성/번역 구분 | 승인 | 출처 | 유효 기간 | 잠금 | 요청 준비 | 제안값`.
신규 후보는 저장 직후 상세로 이동하고 최근 등록/검수함에서 찾을 수 있어야 한다.
등록 완료 토스트를 ‘번역 사용 가능’으로 표현하지 않는다.

### 11.3 TDB 메뉴의 선별 처리 — 메뉴별 1:1 복제 금지

| 기존 TDB UI | 선택 처리 |
|---|---|
| 대시보드, places | 운영 개요, 전체 Entity의 travel/location 필터 |
| sources | 실제 사용하는 출처만 설정에 통합 |
| scout, agents, lanes | 메뉴 이전 제외. 필요한 공급 경로만 기존 보충에 연결 |
| decisions, holds | 관련 미해결 사안만 공통 검수/보충, 현재 값의 근거 이력은 상세에서 접근 |
| policy, watch | 필수 보호 규칙은 테스트·경보에 재사용. 기존 감시 콘솔 전량 복제 제외 |
| gaps, serve, demand | 요청 언어 준비·부족 사유로 통합, 과거 통계 전체 재구축 제외 |
| homonyms, conflicts, hanja | 한 검수함에서 작업 종류로 구분, 별도 메뉴 남발 금지 |
| consumers, API docs | 실사용 고객 계약만 기존 KDB 설정/문서에 통합 |

이전 대상으로 승인된 기능의 기존 링크만 해당 원본 ID/작업으로 연결한다.
제외 기능은 전환 안내를 제공하며 동등한 새 기능이 있는 것처럼 redirect하지 않는다.
이전 중에는 구 화면이 어느 DB를 읽고 수정하는지 배너로 표시하고, 전환 이후 수정 폼은 공통 writer만 호출한다.
권한은 조회자/검수자/운영자/정책 관리자/시스템 관리자를 구분한다.
대량 승인·동일인 병합·권리 변경에는 영향 미리보기, 근거, 확인 절차, 감사가 필요하다.
390px/1440px, 키보드 접근, 빈 데이터/오류/권한 부족/지연 상태를 포함해 인수한다.

## 12. Gemma 부하와 운영 관측

앞선 조사에서 기존 KDB의 야간 일정은 00~05 KST, 정체 후보 점검은 04~05 KST였고,
해당 작업의 모델/동시성은 `gemma4:26b`/12로 기록됐다. 이번에 일정을 바꾸거나 GPU 사용량을 새로 실측하지 않았다.
이 수치는 PressLocale의 목표 ‘3대×6 번역 slot’과 별개다.

통합 관측에서 작업 목적을 `discovery / classification / identity_review / locale_fill / translation`으로 구분한다.
목적 라벨은 별도 다섯 worker 시스템을 만들라는 뜻이 아니다. 채택한 common 작업의 로그/지표를 재사용한다.
각 호출에 job ID, Entity/기사 버전, 모델·prompt 버전, 입력 지문, 토큰, 소요, 재시도, 결과 판정을 기록한다.
GPU 점유율은 모델 서버 telemetry로 별도 측정하고, API 호출시간으로 대체하지 않는다.
UI에서 새벽 시간대 ‘무슨 작업이 얼마나 돌았고 실제 준비값이 얼마나 늘었는지’를 연결해서 확인한다.
최근 결과가 같은 무변경 반복은 변경 성과로 세지 않는다.
번역 고객 요청의 예약 용량과 Entity 유지 작업의 예산을 분리하되 상한은 동일 모델 서버의 실제 부하 시험으로 확정한다.

## 13. 기존 API·PressLocale 연결 경계

### 13.1 TDB 호환

현행 TDB의 `/v1/places/lookup`, `/match`, `/{id}`, `/changes`, `/v1/export/snapshot`,
`/v1/prepare`, `/v1/corrections`는 **의존성 조사 목록**이다. 실제 사용과 유지 의무를 확인해 호환 범위를 확정한다.
없는 고객 수요를 가정해 모든 API를 새로 구현하지 않는다. 반대로 미사용이라고 확인하지 않은 경로를 중지하지 않는다.
필드/정렬/동명 후보/지역 힌트/언어 fallback/인증/오류/캐시 변경 커서를 대조한다.
구형 `/changes?since=`가 삭제·표기 철회·원본 병합을 누락하는지 별도로 시험하고,
완전성 보강이 호환되지 않으면 새 버전 cursor를 추가하고 고객을 단계 전환한다.
보안·권리 차단으로 기존과 달라져야 하는 값은 승인된 변경 목록으로 제시한다. 무조건 기존 오답과 일치시키지 않는다.

### 13.2 기사 및 Glossary

Entity 통합 이후 `entity_mentions`에 article/version/span별 후보·확정 UUID·문맥·근거를 기록한다.
한 기사에서 같은 이름이 두 사람을 뜻할 수 있으므로 이름 문자열→UUID 한 개 사전으로 처리하지 않는다.
Glossary는 요청 locale별 이름/정체성/정책 버전과 기사 시점을 고정하며, 공급 전 철회를 다시 확인한다.
이미 발행한 기사에 관련된 정정은 영향 작업을 만들고, 고객 정책 없이 자동으로 과거 발행물을 수정하지 않는다.

Edipresso 이벤트 인증·버전/hash·recovery, PressLocale outbox/queue·worker lease·공정성,
Gemma 3대 처리량·validator·CMS 반환·구버전 덮어쓰기 방지는 기존 TODO 9~10에 남는다.
이 DB 통합 기획안의 작성이나 DB 흡수 완료를 전체 다국어 발행 플랫폼 완료로 보고하지 않는다.

## 14. 실행 단계와 검증 게이트

아래는 실행 단계의 **설계 요약**이다. 실제 task/체크/게이트/인수 시험/현재 상태는

### 14.1 필수 테스트

1. 전체 조사 분모와 선택 판정, 승인된 PK/유형/locale/출처별 수량·필드 대응 검증. 보관만/제외에 사유가 있는지 확인.
2. 같은 이름의 정치인/선수/배우, 동일 생년, 예명·개명, 인물/캐릭터, 이적·재임 기간.
3. 상점/역, 기관/건물, 학교/캠퍼스, 기업/브랜드/지점, 대회/경기장, 이동 유물/유적지.
4. 정확 locale/잘못된 문자/라틴만 있는 중문/생성값/번역값/한자 근거 없음/근거 철회/fallback.
5. 기존 대표명·필드 잠금, 더 낮은 출처 덮어쓰기, 동시 대표명 교체, 정화 후 중복 UNIQUE,
   DB 트리거가 쓰기를 거부한 경우의 실제 저장 결과 확인.
6. snapshot 중 수정/삭제/잠금, 같은 timestamp의 여러 PK, 늦게 commit한 outbox,
   worker crash/lease 만료/중복 재생/배치 중단/오래된 generation/역순 도착.
7. 병합의 중간 실패 rollback, 반대 방향 동시 병합, 외부 ID 충돌, 잘못된 병합의 분리·참조 복구.
8. 유지하기로 한 기존 API/ID 계약과 대표 고객 요청 replay, 권한·tenant 격리·CSRF·감사·민감값 비노출.
9. 19유형×실제 locale×주요 출처의 층화 표본과 희귀/충돌 사례 추가.
   평가 출처와 정답 출처의 자기 검증을 배제하고, 표본 수·오류·신뢰구간·미판정률을 함께 보고.
10. 스냅샷 크기/인덱스/로그/WAL/백업 여유, API 지연, worker 지연·비용, 피크와 1대 장애 측정.

자동 동일인 연결은 인수 표본에서 잘못된 연결이 나오면 확대를 중지한다.
표본 오류 0이 전체 오류 0을 증명하지 않으므로 위험 유형의 수동 검수와 운영 추적을 유지한다.
평가 기준과 목표 지연/SLO는 P0/P1에서 고정하고 시험 후 유리하게 분모를 바꾸지 않는다.

### 14.2 완료의 정확한 정의

- **기획 수정안 작성:** 목적·최소 범위·선택 흡수 방향을 문서화한 상태. 이번 산출물이며 구조 인수 완료는 아님.
- **구조 설계 인수:** 5.2.1의 컬럼/제약/조회·분류·필드 매핑이 실표본으로 검증되고 승인된 상태. 아직 미완료.
- **흡수 구축 완료:** 승인된 필드/근거를 목표 KDB가 보유, 조사·선택 원본을 추적, 실사용 API 호환,
  공통 단일 writer와 필요한 보충/최소 UI가 운영되며 복구 시험을 통과한 상태. 제외한 TDB 기능을 재구축할 의무는 없음.
- **데이터 품질 인수:** 서비스 대상에 미분류/알려진 차단 오류가 없고 요청 언어 준비를 증명하는 상태.
  권리·정체성 미해결 보류가 남으면 수량/이유를 공개하며 ‘모든 데이터 완성’이라고 표현하지 않음.
- **플랫폼 완료:** P7까지 검증되어 실제 CMS 다국어 발행이 가능한 상태. DB 통합과 별도.
