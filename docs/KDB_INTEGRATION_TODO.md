## 2. 변경하지 않을 방향

1. **목표 DB 구조를 먼저 설계하고, 검증한 구조에 필요한 TDB 데이터만 흡수한다.** 운영 KDB에 먼저 넣고 나중에 분리/정리하지 않는다.
2. 공통 Entity 원본은 KDB에 둔다. 정치·경제·스포츠용 독립 마스터 DB를 추가하지 않는다. Go 기반 운영을 유지한다.
3. 유형·세부유형·인물 직군/직업·뉴스 분야를 구분한다. 직업은 복수 가능하며 가수/배우/정치인마다 인물 테이블을 나누지 않는다.
4. 이름은 고유 키가 아니다. 같은 이름의 다른 사람/회사/장소/상품은 별도 UUID로 관리한다. 개명·직업/소속 변경 때 동일인의 UUID를 바꾸지 않는다.
5. UUID를 배정했다고 정체성 문제가 해결된 것은 아니다. 원본/기사 문맥·소속·활동·외부 식별자와 근거로 연결하고 불확실하면 보류한다.
6. 이름·프로필·관계·근거·보충 job·캐시는 정확한 Entity ID에 귀속한다. 동명 가수의 값을 배우의 빈칸에 복사하지 않는다.
7. 필요한 보호 규칙은 재사용한다. TDB 에이전트/레인/정찰 포털/과거 로그·통계/메뉴 전체를 KDB에 복제하지 않는다.
8. 전체 원본 조사, 복구용 보관, 운영 DB 적재는 다르다. 선별한다고 기존 유효 분야를 임의로 버리거나 원본을 삭제하지 않는다.
9. 분류 불명·근거 없음·권리 보류·생성값·fallback을 ‘기타/검증 완료/요청 언어 준비’로 숨기지 않는다.
10. UI는 공통 개요·고유명사·검수·보충·설정 중심이다. 이전/고급 진단은 운영자 도구로 분리하고 필요한 화면을 실제 기능과 함께 검증한다.

### 변경 통제

새 요청은 기존 목적에 추가되는지, 이전 결정을 대체하는지 먼저 기록한다.
필드/테이블/worker/메뉴 추가는 기획안의 U1~U5 사용처, 필요한 사례, 데이터 출처, 갱신 책임을 제시해야 한다.
범위 변경은 `변경 이유 → 영향 task ID → 선행/검증 영향 → 결정자·날짜`를 남긴 뒤 반영한다.
원칙을 바꾸는 요청·권리 변경·불명확한 동일인 병합·고위험 운영 변경은 사용자 또는 지정 책임자의 판단을 받는다.
작업 ID는 재번호화/재사용하지 않는다. 필요 없어진 항목은 완료 처리하지 않고 ‘범위 제외’ 사유와 대체 항목을 남긴다.
새 기능을 넣느라 이미 열려 있는 필수 안전성 작업을 삭제하지 않는다.

## 3. 실행·완료 기록 규칙

- 모든 `[ ]`는 아직 해당 단계의 완료 근거가 없다는 뜻이다. 기존에 비슷한 코드가 있어도 현재 계약으로 재검증하기 전 닫지 않는다.
- `[x]`는 그 항목의 산출물·검증 근거가 기록됐을 때만 사용한다. 설계/구현/격리 검증/운영 반영/관측 완료를 구분한다.
- 계획상 의존 관계가 있는 다음 단계는 앞 단계 게이트를 통과하기 전 시작하지 않는다. 게이트 실패 시 원인·재현·보정·재시험을 기록한다.
- 기술 작성/구현/검증 책임은 개발 담당이다. 정체성·권리·실사용 계약에 대한 미결 판단 책임은 사용자/지정 검수·운영 책임자로 구분한다.
- 날짜는 실측 후 산정한다. 기계 처리 시간, 수동 검수 적체, 외부 승인 대기는 별도로 보고한다.
- 소스·계정·권한·운영 DB 보호를 유지한다. KDB 산출물은 KDB 소유 작업 공간에 보관하며 사용자 수정 파일을 덮어쓰지 않는다.
- 배포 작업이 허용된 단계에서는 KDB 소유 변경 파일만 검토·검증·커밋/푸시하고 버전/복구점을 기록한다. TODO 작성 단계에서는 배포하지 않는다.

각 항목을 닫을 때 남길 기록:

```text
task_id / 상태(설계·구현·검증·운영·관측) / 실행일·담당
산출물 경로·코드 버전 / 테스트·실데이터 범위와 결과
변경 수량·분모 / 남은 보류·제외·오류 / 운영 영향·복구점
판단·승인 근거 / 다음 task_id
```

보고 단위는 이번에 완료한 task ID, 검증 결과, 미완료/보류, 다음 작업이다.
지표는 실제 준비율·오연결·미계상·재시도 비용을 포함하며 줄 수/등록 건수만 성과로 삼지 않는다.
