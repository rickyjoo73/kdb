## 0. 결론 먼저 — 세 가지는 따로가 아니라 한 줄기다

오너가 지목한 세 가지(TDB 병합 · 분류 확장 · 관리자 메뉴)를 따로 보면 방향이 안 나온다.
실측하니 **하나의 인과 사슬**이었다.

```
못 답하는 요청 (최근 7일, 유형별 실패율)
  government_body   26/68 = 38%      ← KDB 보유 active 23건
  sports_team        7/32 = 22%      ← KDB 보유 active  8건
  organization      17/95 = 18%      ← KDB 보유 active 16건
  (유형없음)        85/574 = 15%     ← 게이트 기각 1위 사유
  person            51/2341 = 2%     ← KDB 보유 active 5,561건
```

**못 답하는 유형 = 보유가 비어 있는 유형 = TDB 에 원본이 쌓여 있는 유형.**
person 은 5,561건을 갖고 있어서 98% 답한다. government_body 는 23건뿐이라 38%를 못 답한다.
보유량이 답변율을 결정한다. 그리고 그 보유량을 채울 원본이 TDB 에 있다.

그래서 순서는 이렇게 된다:

```
TDB 병합  →  분류 확장  →  답변율 상승
  (원본)      (유형 부여)     (오거부 감소)
                  ↑
           관리자 메뉴는 이 과정을 사람이 볼 수 있게 하는 창
```

### ★가장 중요한 실측: TDB 에는 다국어 표기가 없다

```sql
-- tdb_places 의 이름/언어 관련 컬럼 전부
name_ko · addr_en · prominence · confidence
```

`name_ko` 와 주소의 영문(`addr_en`)뿐이다. **en/ja/zh 표기가 없다.**

이것이 방향을 바꾼다. TDB 를 "번역 원본"으로 기대하면 안 된다. TDB 의 가치는 다른 데 있다:

| TDB 가 주는 것 | KDB 에서 쓰이는 곳 |
|---|---|
| **존재 증명** — 이 한국어 이름은 실존한다 | 게이트가 오거부하지 않게 한다 |
| **유형** — 이것은 organization / education / … 이다 | 게이트 기각 1위 사유가 "유형 없음"이다 |
| **prominence / confidence** | 우선순위·동명이의 판별 보조 |

즉 **TDB 는 사전이 아니라 어휘 목록**이다. 표기는 여전히 위키데이터·공식 사이트에서
가져와야 한다. 이 구분을 못 하면 "TDB 흡수했으니 표기가 채워지겠지"라고 착각하게 된다.

### 실측: 지금까지 흡수된 양

```sql
SELECT provider, count(*) FROM kwave_entity_external_refs
 WHERE provider LIKE '%tdb%' OR provider LIKE '%tour%';
-- (0 rows)
```

**TDB 출처로 붙은 앵커가 하나도 없다.** 관리자 화면에는 `/admin/tdb` 계열 라우트
(shadow · candidate · mapping · recheck)가 이미 있는데, 실제로 흘러 들어온 것은 없다.
장치는 있고 아무도 안 켠 상태 — 이 저장소가 오늘 하루에만 여덟 번 밟은 그 패턴이다.

### 가져올 것 / 안 가져올 것

가져온다 (K-콘텐츠 질의에 실제로 등장하는 것):

```
organization    2,557   ← government_body/organization 기아 상태 직결
education       1,122   ← school active 11건
festival_event  3,322   ← event_tour active 611건
cultural_facility 5,943 ← brand_place active 262건
work            3,822   ← 작품
admin_region      249   ← 행정구역
person         31,378   ← 단, 관광 DB 의 person 이 K-콘텐츠 인물인지 표본 검수 먼저
                          합계 약 48,000행
```

안 가져온다 (K-콘텐츠 질의에 안 나오고, 넣으면 동명이의 지뢰만 는다):

```
restaurant 145,433 · other 106,615 · district 83,897 · accommodation 26,568
shopping 25,504 · leisure_sports 20,796 · legal_dong 4,912 · food 2,774
                          합계 약 416,000행 — 전체의 78%
```

식당 145,000개를 넣으면 "아리랑"이라는 식당 때문에 아리랑(민요)의 동명이의 판정이
망가진다. 이건 가설이 아니라 이 저장소가 이미 겪은 계열의 사고다(아몬드→프랑스 영화,
이정후→야구선수).

### 단계

1. **표본 검수 먼저** — TDB `person` 200건을 뽑아 K-콘텐츠 인물 비율을 잰다.
   비율이 낮으면 person 은 빼고 organization/education 부터 간다. **재지 않고 4만 건을
   넣으면 되돌릴 수 없다.**
2. `/admin/tdb` shadow 경로로 소량(200건) 흘려 실제 동작을 확인한다.
3. 유형 매핑표를 코드에 고정하고 테스트로 잠근다 (TDB place_type → KDB entity_type).
4. 배치 흡수. **status 는 candidate 로만.** active 승급은 기존 근거 경로가 한다.

### 왜 안 차나 — 세 가지가 동시에 걸려 있다

1. **원본이 없다.** 이 유형들은 기사에서 잘 안 나오고, 기사 스니펫 기반 승급 경로가
   근거를 못 찾는다. → TDB 가 필요한 이유(§1).
2. **앵커가 틀려 있다.** 오늘 감사에서 **470건의 앵커 불일치**를 찾았다:
   `type-mismatch 278 · human-on-character 139 · name-element 33 · not-human 19 · fictional 2`.
   앵커가 틀리면 로케일 드레인이 그 틀린 항목의 레이블을 8개 언어에 복사한다.
   **이게 최악 시나리오다 — 한 번에 8칸이 오염된다.**
3. **드레인이 못 집는다.** 오늘 고쳤다(`67e0b15`): SELECT 가 3개 로케일만 보고
   UPDATE 는 8개를 덮고 있어서, `en=gtranslate` 496건이 영영 재선택되지 않았다.
   SELECT 대상이 1,932 → 4,631 로 늘었다.

   **★그런데 이 «4,631» 은 즉효를 뜻하지 않는다 — 내가 과장했다.** 배포 후 실측하니
   `checked=80 filled=0` 이었다. 파 보니 en 기계값 494건 중 **340건은 이미 방문해
   «레이블이 없거나 덮어쓰기 대상이 아님»으로 판정된 것**이었다(다른 로케일이 비어서
   집혔던 행들이다). 새로 열린 실질 대상은 미방문 60건 + 앞으로 앵커가 바뀌는 행이다.

   고친 것의 진짜 가치는 **앞을 향한다**: 앵커를 새로 붙인 행의 en 이 이제 재선택된다.
   전에는 영원히 안 됐다. 다만 그 효과가 지금 나타나지 않는 이유가 따로 있다 — 아래.

### ★오늘 밤 새로 찾은 것 — 이름 대조 규칙이 두 개고 서로 반대로 판정한다

오늘 `active-anchor`(d89dc98)로 앵커를 새로 붙인 20건을 실측했다. **18건이 여전히
기계번역 en 이다.** 드레인이 방문은 했는데, 7건이 이 사유로 막혔다:

```
냉부해              → QID Q18604987  ko 레이블/별칭이 정본과 불일치 — 앵커 재확인 필요
쇼미더머니6          → QID Q31179526  불일치
동상이몽-너는 내 운명 → QID Q33185231  불일치
UBC울산방송 · 만원의 행복 · 전국 TOP10 가요쇼 · 내가 매일 기쁘게
```

**같은 파이프라인에 이름 대조 규칙이 둘 있고 서로 반대 판정을 낸다.**

| 규칙 | 위치 | 별칭 인정 | 판정 |
|---|---|---|---|
| `findAnchorQID` | `org_anchor_drain.go` | 인정 (네 관문 통과 후) | **붙인다** |
| `wikidataAnchorMatches` | `wikidata_locale_drain.go` | **불인정 (레이블만)** | **거부한다** |

`냉부해` 는 `냉장고를 부탁해` 의 줄임말이라 위키데이터에 **별칭으로만** 있다.
`쇼미더머니6` 은 레이블이 띄어쓰기가 다르다.

**어느 쪽도 틀린 규칙이 아니다.** `wikidataAnchorMatches` 의 별칭 불인정은 실제 오염
4건(바이브→네이버 VIBE, DK→Dplus Kia, 제이→DAY6 제이 박, 라미→김성경)을 겪고 만든
가드다. 문제는 **이미 우리 레인이 네 관문으로 검증해 붙인 앵커를 다른 레인이 처음 보는
것처럼 다시 심사한다**는 것이다.

고칠 방향(내일): 앵커의 **출처(provenance)를 기록**해서, 우리 검증 레인이 붙인 앵커는
드레인이 재심하지 않게 한다. 출처 미상 앵커에는 엄격한 레이블 대조를 그대로 건다.
`kwave_entity_external_refs` 에 출처 컬럼이 있는지 먼저 확인해야 한다 — 없으면 마이그레이션.

**이것을 고치기 전에는 active-anchor 를 더 돌려도 표기가 안 바뀐다.** 앵커만 쌓인다.

### 순서

0. **★이름 대조 규칙 이원화 해소** — 위 문제. 이걸 안 고치면 1~5위가 전부 헛돈다.
1. **470건 앵커 불일치 정리.** 원본을 더 넣기 전에 틀린 앵커를 걷어낸다.
   순서를 뒤집으면 오염을 늘린 채로 규모만 키운다.
2. 유형별 근거 규칙 확장 — government_body/organization 은 기사보다 **공식 사이트**가
   1차 근거여야 한다. 지금은 뉴스 스니펫만 본다.
3. TDB 흡수(§1)로 후보를 공급한다.

**기계번역 30,807칸이 무슨 뜻인가.** active 13,534행 × 8로케일 = 108,272칸 중 28%가
`gtranslate` 계열이다. 빈칸이 아니라서 아무 화면에도 안 뜨는데, 요청이 오면 **그대로
외부로 나간다.** 오늘 실측한 실제 피해: `날리`→"Nalli"(정답 "Gnarly"),
`누난 너무 예뻐`→"Noona, You're So Pretty"(정답 "Replay"), `옌안`→`延安`(중국 도시가

**오거부 의심 90건이 무슨 뜻인가.** `status='rejected'` 인 엔티티와 같은 이름으로
**근거 URL 을 달고** 정정신고가 들어온 경우다. 우리가 "아니다"라고 판정해 둔 것을
소비자가 근거를 들고 반박한 것이다. 실물:

```
EGO GROUP            agency          egogroup.co.kr             ← 본인 공식 사이트
GloryDayz            event_tour      sports.khan.co.kr/...
2026 가요대전 SUMMER  event_tour      news.sbs.co.kr/...
KBS 2TV · MBC        channel_outlet  kstory 기사 다수
```

`MEOVV` 는 더블랙레이블 공식 사이트가 근거인데 rejected 다. 오늘 고친 게이트 수정
(`6556d5c`)은 **앞으로 들어올 신고**를 살린다. 이미 rejected 로 박혀 있는 90건은
**따로 되살려야 한다** — 수정만으로 자동으로 풀리지 않는다.

지금은 문제를 찾으려면 매번 SQL 을 써야 하고, 그래서 오늘처럼 우연히 발견하게 된다.
