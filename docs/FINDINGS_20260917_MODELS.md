# gpt-5.6-luna 시험 결과 (오너 요청)

> "생각보다 codex 를 많이 사용해야돼 그렇다면 gpt5.6 luna medium 을 사용해봐
> 기존 sol 보다 금액은 1/10 정도 이며, gemma 보다는 성능이좋아 퍼팩하지는 않치만
> 좀더 빠르게 저렴해 테스트 해보고 결과 알려줘"

## 시험 설계

실제 과제로 쟀다. 간체 칸에 남은 이체자 **26건** — 사전만으로는 «昇 을 升 으로
바꿔야 하나»를 못 가르는 진짜 판단 문제다. 세 모델에 **같은 프롬프트**를 주고
출력 스키마도 같게 했다.

## 결과

| | 판정일치 | 값 | 평균 응답 | 중앙 | 최대 | 번체잔류(오답) |
|---|---|---|---|---|---|---|
| gpt-5.6-sol / medium | 기준 | 기준 | **11.5초** | 10.7초 | 24.8초 | 1 |
| gpt-5.6-luna / medium | 26/26 | 22/26 | 16.4초 | 14.6초 | 58.4초 | 1 |
| gemma4:26b | — | 18/26 | **2.9초** | — | — | **5** |

«번체잔류» = 모델이 «고쳤다»고 답한 값에 번체 글자가 그대로 남아 있는 경우.
규칙으로 판정 가능한 객관적 오답이다.

## 1. luna 는 sol 보다 **느렸다**

기대와 반대다. 평균 16.4초 대 11.5초로 **43% 느리다.** 한 건은 58초가 걸렸다.

## 2. 금액 1/10 은 이 구성에서 적용되지 않는다

codex CLI 를 **ChatGPT 계정**으로 쓰고 있다. 호출당 과금이 아니라 계정 쿼터를
쓴다. 그래서 단가 차이가 비용으로 나타나지 않는다. 오히려 luna 가 벽시계 시간을
더 쓴다.

API 키로 전환하면 단가가 의미를 갖는다. 그런데 오너 지시가 "api 는 사용하지 않고,
cli 에이전트로 사용한다" 였다.

## 3. 품질은 판정 수준에서 동등, 근거에서 sol 이 낫다

verdict(keep/change)는 26/26 일치했다. 갈린 것은 값 4건이다.

```
CJ제일제당  CJ第一製糖   luna CJ第一制糖    sol 希杰第一制糖
조승구     趙昇久      luna 赵升久       sol 赵昇久
김승연     金昇淵      luna 金昇渊       sol 金升渊
마시마     眞嶋優      luna 真岛优       sol 真岛
```

sol 은 근거를 중국어로 대고 «通用规范汉字表» 를 인용했다. luna 는 영어로 더 짧게
답했다. 둘 다 昇 처리가 일관되지 않았다(15건 중 2건만 升 으로 바꿨는데, 바꾼 대상이
서로 달랐다).

## 4. gemma 는 빠르지만 이 과제에 못 쓴다

2.9초로 압도적으로 빠르다. 그런데 **«고쳤다»면서 번체를 그대로 남긴 답이 5건**이다:

```
尹啟相 → 尹啟相   (啟 그대로)
許楠儁 → 许楠儁   (儁 그대로)
金昇淵 → 金昇淵   (淵 그대로)
眞嶋優 → 真島     (島 그대로 — 게다가 優 를 잃었다)
```

두 codex 가 일치한 4건에서 gemma 만 달랐다. 자체 변환 과제에서 이 실패는 치명적이다 —
고쳤다고 믿고 쓰면 오염이 그대로 남는다.

## 결론

**sol 을 유지한다.** luna 는 더 느리고, 이 구성에서는 더 싸지도 않으며, 품질 이득도
없다. gemma 는 값싼 1차 통과용으로는 쓸 수 있어도 자체 판정에는 못 쓴다.

luna 가 의미 있어지는 조건: API 키로 전환해 호출당 과금이 되고, 동시 호출 수를
늘려 벽시계 손해를 상쇄할 때. 지금 구성에서는 아니다.

## 부수 소득

이 시험의 26건 답을 그대로 코드에 실었다 — `zhVariantVerified`(두 codex 일치분만).
모델이 «글자가 아니라 이름을 바꾸자»고 한 것(李儁→李仁, 讚美→许赞美, 孔昇延→孔升妍)은
싣지 않았다. 그건 자체 변환이 아니라 표기 교체이고, 정정·합의 레인이 근거를 갖고
할 일이다.
