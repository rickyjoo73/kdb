## 1. 정확 대상

설계(§5.2)가 정한 파일럿 둘을 실측으로 재확인했다.

### 파일럿 B — TDB 최소 앵커 (먼저 한다)

| 항목 | 값 | 확인 |
|---|---|---|
| 대상 | `tdb_places.place_type='admin_region'` | 249행 전수 |
| QID 보유 | **249 / 249 (100%)** | 실측. 설계 가정과 일치 |

## 4. 중지 기준 — 하나라도 걸리면 즉시 멈춘다

설계 §5.4 의 수치를 그대로 쓴다. batch 전용으로 셋을 더한다.

| 조건 | 중지 수치 | 출처 |
|---|---|---|
| 5xx (5분 창) | corrections ≥ 1.12%, 그 외 route ≥ 1.0% | §5.4 |
| p95 | lookup/bulk > 566ms · match > 4,015ms · prepare > 3,000ms | §5.4 |
| 저장 | `/data` 여유 < 200GB 또는 백업 1회 실패 | §5.4 |
| 무효화 적체 | outbox 미처리 > 1,000 또는 최고령 > 24h | §5.4 |
| 잠금 | lock wait > 30s 1건 | §5.4 |
| **batch: 계상 불일치** | 기록 수 ≠ 원본 수 **1건이라도** | 신규 |
| **batch: 제약 위반** | 어떤 제약이든 1건 | 신규 |
| **batch: 판정 오류** | 표본 검수에서 오류 1건 | §5.3 |

**"표본 0건을 전체 0으로 표현하지 않는다"**(§5.3)를 유지한다.

## 5. 복구

| 상황 | 복구 |
|---|---|
| batch 중간 실패 | 전체 rollback. 부분 성공을 완료로 보고하지 않는다(I10, P1.06 로 시험됨) |
| batch 후 오류 발견 | `kentity_migration_records.state='reverted'` + 만든 객체 역순 삭제. `run_id` 로 정확히 지목된다 |
| 잘못된 UUID 발급 | 지우지 않고 `status='retired'` + redirect. 소비자가 이미 저장했을 수 있다 |
| 오연결 승계 | `source_guards` 로 차단. 지우면 다음 수집에서 되살아난다 |
| DB 전체 | 일일 백업(2026-09-12 수리 완료, `scripts/kdb-db-backup.sh`) |

**되돌릴 수 있는 이유:** 모든 변경이 한 `run_id` 에 묶이고, 만든 객체마다
`migration_record_id` 로 출처가 남는다(P1.02 §10).

## 6. 승인 책임

설계 §5.5 대로 **운영자 단일**이다. 4개 소비자 사이트·운영·권리의 결정 주체가 같은 사람이며
(P0.06 실측: 동일 호스트·동일 운영자), 외부 담당자 대기 항목은 없다.

판정은 자율 판정기가 하고, 두 판정기가 불일치하거나 근거가 상충할 때만 운영자가 결정한다.

## 8. 승인을 구하는 것 — 정확히 이것

1. `p1_structure.sql` + `p2_structure.sql` 을 **운영 DB 에 적용**한다 (표 60 → 80).
2. Go 변경을 같은 배포로 내보낸다.
3. 원천 정책 13 provider 를 운영에 승인 INSERT 한다.
4. 의심 연결 751건을 `source_guards` 로 차단한다.
5. **파일럿 B batch 1 (121행)** 을 적재하고 계상·표본을 확인한다.
6. 통과하면 batch 2 (121행). 그 다음이 파일럿 A.

**승인하지 않으면 아무것도 실행하지 않는다.** 지금까지처럼 격리에서만 계속한다.

## 10. ★ D-37 — 원본 지문을 지어냈다

배포 뒤 감사에 `tdb_mapping_invalidated` 242 · `evidence_invalidated` 242 가 찍혔다.
흡수한 연결이 **전부 `conflict`** 로 내려가고 정체성 근거가 **철회**됐다.

**시스템이 제대로 잡은 것이다.** 원인은 내 batch 스크립트다.

`kentity_tdb_shadows.source_fingerprint` 를 `md5(tdb_id)||md5(qid)` 로 **지어내 넣었다.**
실제 지문은 `sha256(정책 + binding 구조체)`(`internal/kentity/tdb_shadow.go` `bindingFingerprint`)이고
SQL 로는 재현할 수 없다. 관측자가 다음 통과에서 실제 값을 계산해 보고 "원본이 바뀌었다"로
판정해 연결을 무효화했다.

### 배운 것: 관측이 먼저, 흡수가 나중이다

흡수가 shadow 를 만들면 안 된다. shadow 는 **원본을 아는 관측 경로**가 만들고, 흡수는 이미
있는 shadow 를 참조만 한다. 순서를 뒤집으면 흡수가 원본을 모르는 채로 연결을 확정하게 되고,
그건 이 프로젝트가 막으려는 바로 그것이다. 두 batch 스크립트의 대상 선정에
`EXISTS(실제 관측이 만든 shadow)` 조건을 넣었다.

## 11. 복구 선택지 (운영자 결정 필요)

**A. 그대로 두고 관측부터 다시** — 현재 상태가 안전하다. 실제 관측 경로(`kdb tdb-shadow-import`,
외부 호출 없음)로 242건의 진짜 shadow 를 만든 뒤, 새 관측 근거로 연결을 다시 확정한다.
단 그 뒤 워커가 242건의 wikidata 라벨을 가져가는데, 외부 호출 상한이 **provider 당 일 100회**
(§5.4)라 3일에 나눠 진행된다.

**B. 242건을 되돌리고 다시** — `run_id` 로 정확히 지목되므로 역순 삭제가 가능하다. 다만
같은 엔티티가 새 UUID 로 다시 만들어질 뿐이라 이득이 없다.

**권고: A.** 만든 것이 잘못된 게 아니라 **순서가 잘못됐다.** 엔티티·이름·외부 ID 는 옳고,
연결만 진짜 관측 위에서 다시 확정하면 된다. 되돌리면 옳은 것까지 버린다.

다만 외부 호출 예산을 며칠에 나눠 쓰는 문제라 **속도는 운영자가 정할 일**이다.

## 12. D-37 복구 실행 — 실측이 계획을 바꿨다

운영자가 안 A 를 승인한 뒤 실제 상태를 재보니, **계획한 것보다 훨씬 작은 일**이었다.

`kdb-app tdb-shadow-import`(dry-run)를 242건 전수로 돌린 결과 **unchanged 242/242**.
즉 **관측자가 이미 내가 지어낸 지문을 실제 값으로 교체해 놓았다.** 남은 문제는 그 교체가
일으킨 무효화의 뒷정리뿐이었다.

| 계획 | 실제 |
|---|---|
| shadow 를 지우고 실제 import 로 다시 만든다 | **불필요** — 지문이 이미 맞다 |
| wikidata 242회 호출 | **0회** |
| 외부 호출 상한 때문에 하루 100건씩 3일 | **한 번에 전량**, 당일 완료 |

### 한 것

1. shadow 의 **정책 표기만** 실제 값(`tdb-wikidata-bindings-v1`)으로 맞추고 `state='review'` 로 뒀다.
   **지문은 건드리지 않았다** — 건드리면 무효화 트리거가 또 돈다(트리거는
   fingerprint/locked/generation 에 걸린다). `review` 로 둔 이유는 이 연결을 운영자 batch 가
   이미 판정했기 때문이다. 워커가 다시 가져가 wikidata 를 부를 이유가 없다(5초당 1건이라
   242건이면 20분에 242회 — 상한 일 100회를 넘긴다).
2. **새** 정체성 근거를 기록했다. 실제 지문을 주장 지문으로 삼는다.
3. 외부 ID 를 새 근거로 되살렸다(철회는 옛 근거가 죽어서 일어난 것이다).
4. 연결을 다시 확정했다.

**철회된 옛 근거는 되살리지 않았다.** 설계가 "철회하고 새 관측을 기록한다"이므로
withdrawn 242건은 이력으로 남는다.

### 남는 교훈

- **관측이 먼저, 흡수가 나중이다.** 이 규칙은 두 batch 스크립트의 대상 선정 조건으로 들어갔다.

  이만큼 차이를 만든다.

# P3.06 확대 — 자체 ID 로 묶어 TDB 를 흡수한다

## 13. 병목은 QID 가 주 앵커였던 것이다

운영자 지시: **"wikidata QID 는 보조 역할이지 없는 DB 를 채우는 역할이 아니다. 자체적인 id
값을 가지고 있다."**

확대를 시작하려니 구조가 막았다. 0122 가 tdb 연결에 `source_binding_id`(→ `kentity_tdb_shadows`)
를 필수로 걸었는데 그 표는 `qid NOT NULL` 이다. 결과적으로 **wikidata QID 가 없으면 연결
자체를 만들 수 없었다.**

| 유형 | 전체 | QID 보유 | 비율 |
|---|---|---|---|
| admin_region | 249 | 249 | **100%** |
| person | 31,378 | 14,504 | 46.2% |
| heritage | 13,887 | 1,675 | 12.1% |
| legal_dong · tourist_spot · food · education · transit | 62,509 | **0** | **0%** |
| **전체** | **536,322** | **17,915** | **3.3%** |

즉 **96.7% 가 구조적으로 흡수 불가**였다. 보조여야 할 외부 식별자가 주 앵커 노릇을 한 것이다.

설계는 이미 이걸 예견했다 — "crosswalk source_system/source_id + TDB shadow 결합 | 원본
binding 계약 **보강 예정** | QID 없는 TDB 원본도 구분" / "현재 source_binding_id 는 TDB shadow
FK. **범용 원천 binding 으로 오인 금지**". P1.02 가 남긴 미구현 항목이었다.

## 14. 고친 것 — 0125 / 0126

**0125 원본 binding 계약 보강.** `kentity_crosswalks.basis_record_id`(→ `kentity_migration_records`)
를 더하고, tdb 연결이 **둘 중 하나 이상**의 binding 근거를 갖도록 CHECK 를 완화했다.

- **1차 binding = 원본 자기 ID 의 관측 기록.** `(source_system, source_table, source_pk)` 와
  지문·상태·관측시각을 이관 원장이 이미 갖고 있다.
- **wikidata shadow 는 있을 때 얹는 보조 앵커**로 남는다(호환 유지).
- 완화만 하므로 기존 행은 하나도 깨지지 않는다.
- `tdb` 를 원천으로 등록하되 `name_export_allowed=false` — TDB 의 표기는 TDB 가 만든 것이
  아니라 상류 원천에서 온다. 그 권리는 원천별로 따로 본다.

**0126 선매핑 코드표 승격.** `kentity_source_type_map` 이 격리에만 있어 확대가 무엇을 어디로
보낼지 알 수 없었다. 51 결정(map 33 · hold 16 · exclude 2)을 운영으로 옮겼다.

## 15. 흡수 규칙

대상 1건당 객체 4개(QID 있으면 6개):

| 객체 | 내용 |
|---|---|
| 이관 기록 | **1차 binding** — 원본 자기 ID·지문·관측시각 |
| Entity | `candidate`, 선매핑 유형/세부유형, **구분값을 분류사유에 기록** |
| 정체성 근거 | `provider='tdb'` — 외부 식별자가 아니라 **우리 원본의 관측**이 근거다 |
| 이름 | **`unverified`** — 보관하되 공급하지 않는다 |
| (외부 ID + 예약) | QID 가 **있을 때만** 얹는다 |
| 연결 | `basis_record_id` 로 자기 ID 관측을 가리킨다 |

**이름을 unverified 로 두는 이유:** 표기는 상류 원천(aihub_tour · 공공누리 · CC0)에서 온다.
그 정책이 승인되기 전까지는 기본 차단이 유지돼야 한다. 보관은 하되 공급하지 않으면
통합은 진행하면서 권리 게이트도 지킬 수 있다. 정책이 승인되면 그때 검증 승격한다.

**선매핑에서 `hold`/`exclude` 인 유형은 흡수하지 않는다** — other 106,602(추측 금지),
person 31,378(동일인 판정 선행), work · food · organization · education · transit.

## 16. 확대 중 잡은 것

- **요청키가 batch 마다 같았다.** `p3-expand-<유형>-<건수>` 로 만들었더니 두 번째 batch 가
  같은 키를 갖고 `UNIQUE(owner_key, request_key)` 에 걸려 **통째로 롤백**됐다. 첫 batch 만
  들어가고 나머지가 조용히 0건이었다 — 오류는 났지만 루프가 계속 돌아 눈에 안 띄었다.
  요청키에 run id 를 넣어 고쳤다.
- **psql 변수는 `DO $$ … $$` 안에서 치환되지 않는다.** 본문이 서버로 가는 문자열이라서다.
  매개변수를 임시 표로 넘긴다.

# P3.06 전량 흡수와 고유명사 범주 개방 — 2026-09-13

## 17. 운영자 지시

> "tdb 의 내용을 모두 흡수해서 kdb 에서 사용될 수 있도록 해야 돼. 또한 새로운 정치인·
> 경제인·스포츠인, 또한 제품명·상표 등 모두 고유명사를 포함할 수 있도록 준비해줘."

두 가지다. **전량 흡수**와 **모든 고유명사 범주를 받을 준비**.

## 18. 전량 흡수 — "모두 받되 추측은 안 한다"

선매핑에서 보류였던 7유형 141,166건을 받는 규칙으로 바꿨다(0127). 원칙은 하나다:

> **후보의 부모 유형이 하나로 모이면 그 부모 + 세부유형 NULL,
> 부모가 갈리면 `unknown` + 세부유형 NULL.**

둘 다 "모른다"를 정직하게 적는 것이지 그럴듯한 값을 찍는 것이 아니다.
`unknown` 은 사전이 정의한 **"유형 검수 대기"** 이고, 건수를 줄이려고 일괄 장소화하지
않는다는 규칙(분류 규칙 §8)은 그대로 살아 있다.

| 원천 유형 | 건수 | 목표 | 판단 |
|---|---|---|---|
| person | 31,378 | `person.real` | 인물 목록이므로 유형은 확실. 이름 겹치는 3,604건도 **각자 UUID**, 자동 병합 없음 |
| work | 3,822 | `work` + 세부 NULL | 후보가 전부 `work.*` → 부모는 확실, 세부(곡/앨범/영화/책)만 미상 |
| other | 106,602 | `unknown` | 범주 불명확 → 유형 검수 대기 |
| food · organization · education · transit | 7,364 | `unknown` | 후보의 부모 유형이 갈림 |

**구분값이 없어도 받는다.** 다만 숨기지 않는다 — 만들 수 없으면 `needs_disambiguation` 으로
적고 분류를 미완으로 둔다. **안 받는 것과 검수 대기는 다르다.**

**이름이 KDB 와 겹쳐도 받는다.** 각자 UUID 를 주고 겹치는 상대를 `candidate_ids` 에 적어
검수가 찾을 수 있게 한다. 같은 이름이 같은 대상이라는 뜻이 아니다(I01/I05).

## 19. 고유명사 범주 개방 — 사전만 열면 되는 줄 알았다

사전을 열고 끝낼 뻔했는데, 확인해 보니 **실제로는 두 군데가 막혀 있었다.**

### 공백 ① 사전은 열었는데 코드가 거부했다

`kentity_types.enabled` 로 `brand`(상표)·`character` 를 켰지만, Go 의 `supportedTypes` 가
**11종 하드코딩**이라 등록이 거부됐다. 사전과 코드가 따로 놀던 것이다 — D-14 가
"현행 Go supportedTypes/DB CHECK 의 11개만 enabled 로 시작한다"고 적어 둔 것의 나머지 절반이다.

코드를 사전에 맞추고, **어긋나면 시험이 잡도록** 대조 시험(`TestSupportedTypesMatchDictionary`)을
넣었다. 등록 폼의 선택지에도 상표·캐릭터를 더했다.

### 공백 ② 직업을 넣을 곳이 없었다

직군 26종(`politician`·`businessperson`·`entrepreneur`·`executive`·`athlete`·`sports_person`·
`coach`·`referee` …)이 사전에 열려 있는데, **`kentity_person_roles` 에 쓰는 코드 경로가 0개**였다.
운영의 직업 204건은 전부 내 SQL 배치가 넣은 것이고, 화면에서 기록할 수단이 없었다.
**새로 등록한 정치인의 직업을 적을 수 없으면 "받을 준비"가 된 것이 아니다.**

만든 것:

- `POST /admin/kentity/{id}/roles` — 인증·CSRF·운영자 권한
- 상세 화면의 직업 목록과 추가 폼
- **직업을 더하는 것이지 새 UUID 를 만들지 않는다.** 시험이 고정한다 —
  정치인+기업인+운동선수 3직업을 붙여도 대상 수는 그대로다.
- 근거 없이 만들지 않는다. 직업마다 `occupation` 근거를 함께 만들고 "무엇을 보고 판단했는지"를
  사유로 남긴다. 기간은 모르면 모른다고 둔다(관측 시각을 재임 시작으로 넣지 않는다 — I12).
- 인물 아닌 대상 · 사전 밖 직군 · 10자 미만 사유 · 잠긴 대상은 거부한다.

### 결과 — 받을 수 있는 범주

| 범주 | 코드 | 상태 |
|---|---|---|
| 상표 | `brand` | **열었다**(사전·코드·폼 3곳) |
| 제품명 | `product` | 열려 있었음 |
| 캐릭터 | `character` | **열었다** |
| 정치인 | `politician` · `public_official` | 직군 사전 + **부여 경로 신설** |
| 경제인 | `businessperson` · `entrepreneur` · `executive` | 〃 |
| 스포츠인 | `athlete` · `sports_person` · `coach` · `referee` | 〃 |
| 스포츠 조직 | `team` · `league` | 열려 있었음 |
| 분야 | 정치·행정·경제·사회·연예·스포츠·여행·문화 8종 | 전부 활성 |

## 20. 검수 수단 — 십만 건을 어떻게 찾나

전량 흡수하면 `unknown` 이 11만 건 넘게 쌓인다. 목록에서 골라낼 수단이 없으면 검수를
시작할 수가 없다. `/admin/kentity` 에 **분류 검수 필터**를 넣었다 —
분류 검수 대기 · 유형 미상 · 세부유형 미상 · 구분값 미상.

## 21. 이 단계에서 시험이 잡은 것

- **`jsonb_build_object` 안의 파라미터는 타입을 추론하지 못한다.** CI 의 `go test` 는 DB 없이
  돌아 이 경로를 건너뛰므로, 격리 복원 DB 시험이 아니었으면 **화면에서 처음 드러났을 것**이다.
- **"대상이 늘지 않는다"를 이름으로 세면** 앞선 실행의 잔여물까지 세게 된다. 전체 수를
  앞뒤로 비교해야 그 명제를 실제로 검사한다.
