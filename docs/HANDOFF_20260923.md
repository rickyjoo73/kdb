실측(표본 300칸): 위키데이터 라벨과 **불일치 6.5%**, 그 언어 라벨이 **아예 없는데도**

**값은 대체로 우리 쪽이 낫다** — 틀린 것은 라벨이다.

사실대로 내리면 `verified_only` 통과 칸이 **약 9.5%(23,751 중 2,200여) 줄어든다.**
갈래 둘 중 하나를 오너가 골라야 한다:
- ① 전부 사실대로 내린다 — 신뢰 신호가 정확해지고, 검증 폭은 준다
- ② 유도 경로가 결정적인 것(`opencc` 변환 등)은 검증으로 남기고 나머지만 내린다

고른 뒤 레인은 이렇게 짠다: QID 보유 칸마다 `wbgetentities` 로 라벨을 받아
같으면 유지, 다르면 사실 라벨로 교체, 없으면 `source-unrecorded`(신규, 미검증).
반드시 dry 로 «몇 칸이 verified 에서 빠지는가»를 먼저 찍는다.

### ③ 소비자 type 힌트 vs 위키데이터 P31 — dry 로 규모부터
`aijudge.ClassifyFromEvidence` 가 소비자 힌트를 **P31 보다 앞**에 둔다
(`internal/kdb/aijudge/classify_evidence.go` ①). 그래서 카카오가 `event_tour` 로,
케이뱅크가 `brand_place` 로 굳었다.

```

그중 위키데이터 앵커 보유                      2,106   ← 재판정 가능 모집단
```

전면 역전은 하지 않는다(기사를 본 쪽의 판단이 맞는 경우가 많다).
**«P31 이 명확하고 힌트와 충돌할 때만 P31»** 로 좁히고, dry 로 몇 건이 바뀌는지 찍은 뒤
`type-retrace` 와 같은 모양(`dataqa_log` 스냅샷 + `[retrace:type-fix a→b]` 노트)으로 쓴다.

새로 깔아 둔 신호를 쓰면 대상을 고를 수 있다 — 조회에서 유형 필터가 보유 이름을 가리면
