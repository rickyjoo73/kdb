# prepare 요청 분석 — 밤샘 결과 (2026-09-17 → 18)

오너 지시: "prepare 와 요청내용을 파악해봐 우리가 부족한것을 채워야지",
"빠르게 찾아 업데이트 하는것이 그게 능력이야", "외부 사용가능한 공신력있는 소스를
찾아서 계속 투입해 줘야돼".

## 0. 먼저 내가 틀린 것

밤 사이 세 번 틀렸다. 고친 순서대로 적는다 — 다음 사람이 같은 데서 헛돌지 않게.

**① "TDB 가 252건만 연결됐다"** → 틀렸다. TDB 는 `kentity_*` 로 **전량 이동 완료**돼
있었다(2026-09-13, `kentity_migration_records` 536,677건). 나는 `kwave_entities` 와
`kentity_tdb_shadows` 만 보고 엉뚱한 자리에서 없다고 했다.

```
kentity_entities  559,458   (origin tdb 537,837 · kdb 21,718)
kentity_names   2,699,388
```

**② "TDB 가 위키데이터 근거로 410건을 채워 준다"** → 틀렸다. kentity 의 근거 원장에
이미 이렇게 적혀 있었다:

> "TDB 가 자기 레코드에 갖고 있던 표기. TDB 는 출처를 wikidata 라고 적어 두었으나
> **어느 항목인지는 원본에 없다** — 확인되지 않은 출처 주장을 공급 근거로 쓰지 않는다."
> (policy `unpinned-source-claim-v1`)

출처 주장이 이미 감사돼 철회된 데이터였다. 나는 TDB 의 자기 주장을 액면 그대로 믿었다.
실제 품질도 섞여 있다 — `하일권 → 哈·伊尔-克旺` 처럼 한자가 아니라 음역인 것이 ~1%.

교차확인 기준(우리 권위 값 하나 이상이 TDB 와 일치)으로 다시 재니 **실제로 채울 수
있는 빈칸은 57칸**이었다(en 3 · zh 26 · zh_hant 28). 내가 처음 말한 "1,517 zh 빈칸"은
kentity 안의 **kwave 자기 미러**를 TDB 로 착각한 숫자다.

**③ "요청의 36%만 답한다"** → 지표를 잘못 읽었다. `kwave_kdb_request_terms.item_status`
는 **그 요청 시점의 상태**다. 14일 창에서 한 번도 ready 가 없었던 용어를 "답 못 함"으로
셌는데, 실제로 API 를 불러 보니 대표 사례가 전부 지금은 ready 다:

```
서울대학교      status=ready  8로케일 전부
방탄소년단(BTS) status=ready  8로케일 전부
국세청          status=ready  5로케일
```

응답률 지표를 **"그 시점에 못 답한 비율"과 "지금도 못 답하는 비율"로 나눠** 다시
정의해야 한다. 지금 숫자로는 «능력»을 판단할 수 없다.

## 1. 확실한 결함 — 중국어 칸에 영어가 나간다

실제 호출로 잡았다.

```
POST /v1/prepare  {"verified_only":true,"locales":["en","ja","zh"],...}
→ "zh":"Seoul National University"   provenance "en-fallback"
```

`verified_only` 를 켜면 검증 안 된 zh 값을 비우는 대신 **영어를 넣는다.** 중국어
소비자에게 영어가 중국어라고 나간다. 우리 채움 프롬프트는 "NEVER copy the English
title into a non-English locale — a field equal to the English title is a TRANSLATION
FAILURE" 라고 못 박아 두고, 서빙에서 그걸 하고 있다.

빈칸이 옳다. 번역 쪽이 자기 번역을 쓰면 된다(오너 방침).

## 2. 확실한 결함 — 병합 묘비를 따라가지 않는다

중복을 정본으로 합치면서 진 쪽을 `status='rejected'` 로 묻는다. 그런데 살아남은
정본이 그 이름을 별칭으로 갖지 않으면 **그 이름으로는 영원히 못 찾는다.**

```
병합 묘비                        813
  정본에 별칭 없음(구멍)          123
  그중 최근 14일 요청 있음         33
```

구멍 표본: 개그콘서트 · 놀면 뭐하니? · 핑클 · BOYNEXTDOOR · MEOVV · 유튜브 ·
쇼! 음악코어 · 딩고 뮤직.

## 3. 진짜 병목 — 재시도가 수요를 무시한다

```
candidate            1,346
  7일 쿨다운에 묶임    1,126  (84%)
  지금 처리 가능           6
```

on-demand 레인은 8초마다 도는데 뽑을 게 6건이다. 실패해도 `last_enriched_at` 을 찍어
7일을 재우기 때문이다(과거 '아리랑' 무한 공회전을 막으려 넣은 가드). 결과:

```
마지막 시도 이후 새 요청이 들어온 candidate   297
  그중 쿨다운에 갇힘                        247
```

스프링 레인이 7일간 13번 요청돼도 재시도는 7일 뒤다. **수요가 백오프에 전혀 반영되지
않는다.** 고칠 방향: 요청이 있으면 1h → 6h → 1d → 7d 지수 백오프, 아무도 안 찾으면
현행 7일 유지. 백오프가 있으니 무한 공회전은 재발하지 않는다.

## 4. 안 쓰는 근거 — 요청이 답을 들고 온다

```
요청 6,425건 중 근거 URL 동반  6,370 (99%)
```

그런데 문맥(`context_hint`)은 **게이트 판정에만** 쓰이고 표기 추출에는 안 쓴다.

```
스프링 레인  "'톡-토크'(Tock-Talk), '스프링 레인'(Spring Rain) 등 일본 오리지널 신곡"
채진아      "SBS 예능 '틈만나면,'(연출 최보필/작가 채진아)"
전북 현대    "강상윤(전북 현대)"
```

용어 바로 뒤 괄호 표기만 규칙으로 세도 **255건**, 그중 **196건이 `no_match` 로 죽었다**.
문맥 전체를 추출 레인에 넣으면 훨씬 넓어진다 — RSS 에는 이미 하고 있는 일이다.

# 실행 결과 (2026-09-18)

## ① 중국어 칸의 영어 폴백 — 제거, 실측 확인

`isFallbackLocale` 이 ja/zh/zh_hant 까지 en 폴백 대상으로 두고 있었다. 라틴권만 남겼다.

```
전:  "zh": "Seoul National University"   provenance "en-fallback"
후:  "missing": ["zh"]
     "absent_locales": {"zh": {"locale_absent":"unverified_source","fill_hint":"transliterate"}}
```

빈칸으로 두되 **이유와 힌트**를 함께 보낸다. 번역 쪽이 자기 번역을 할 수 있다.
라틴권(vi/es/id/pt_br)은 로마자가 실제 통용 표기라 폴백을 유지했다.

이 정책을 지키던 시험이 있었다 — `values["ja"] == "IU"` 를 요구했다. 시험이 결함을
지키고 있었으므로 함께 고쳤다(미검증 값 비노출이라는 진짜 가드는 유지).

## ③ 수요 기반 재시도 — 가장 큰 효과

```
             전          후
뽑을 대상     6건    →   281건
처리량       1~3건/틱 →  10건/틱 (가득)
1시간 처리   ~1건    →   280건
1시간 승급    -      →    10건 (전부 공식 앵커 보유)
```

마지막 시도 이후 새 요청이 있으면 6시간 뒤부터 다시 본다. 바닥이 6시간이라 한 행은
하루 4회를 넘지 않는다 — '아리랑' 무한 공회전은 구조적으로 재발하지 않는다.
실측: 281 → 7 로 11분 만에 소진되고 멈췄다. 승급은 전부 wikidata/tmdb/musicbrainz
앵커 보유였다(앵커 게이트가 정상 작동). 외부 API 레이트리밋 0건.

## ④ 요청 문맥 추출 — 배포, 아직 미발화

용어 뒤 괄호 표기를 규칙으로 뽑아 **관측 원장**에 넣는다. 값을 바로 쓰지 않고 기존
매체 합의(독립 2곳 일치)를 태우므로 기사 하나가 표기를 바꾸지 못한다. 한자만 있는
괄호는 버린다 — 「홍길동(洪吉童)」은 한자 이름이지 중국어 표기가 아니다.

배포·단위시험 통과. **운영에서는 아직 발화하지 않았다** — 최근 90분 문맥 30건을
직접 돌려 보니 뽑을 것이 1건이었다. 적중률 3~5%라 하루 몇 건 단위로 나온다.

## ② 병합 묘비 — 레인을 만들지 않았다

구멍 67건 중 자동 추적 가능한 것은 3건뿐이었다. 병합 사슬이 죽어 있어서다:
`쇼! 음악코어 → 쇼! 뮤직코어` 인데 둘 다 rejected, `유튜브 → YouTube` 도 둘 다
rejected. 별칭 문제가 아니라 군집 전체가 기각된 것이라 별도 판단이 필요하다.

## ⑤ iTunes — 두 겹의 «조용한 0건»

노래·앨범은 최대 구멍(요청 993건)인데 음악 출처 커버가 거의 없었다. 파 보니 레인이
두 번 죽어 있었다.

**첫째, 2026-09-15 확장이 무효였다.** SELECT 과 UPDATE 는 «기계값 전체»로 넓혔는데
루프 안 가드만 `codex-fallback` 으로 남아 있었다.

```
active song_album                     1,944
  SELECT 대상(ja/zh/hant 기계값)       1,371
    실제 처리됨(codex 포함)              346
    뽑히고도 버려짐                    1,025   ← 확장이 무효
```

같은 파일 주석이 «고르기만 넓히고 쓰기를 codex 로 두면 조용한 0건이 된다》고 경고하고
있었는데, 정작 그 줄이 그 함정이었다. 세 자리가 같은 목록을 보도록 `itunesUpgradable`
로 묶었다.

**둘째, NULL 이 Scan 을 깨뜨리고 그것을 삼키고 있었다.** 일회성 실행이 33ms 만에
`confirmed=0` 으로 끝나 파 보니, SELECT 은 1,529행을 돌려주는데 한 행도 처리되지
않았다. 값 칸이 nullable 인데 Go 는 string 으로 받고, Scan 결과를 `== nil` 로만
검사하며 조용히 건너뛴다 — **로그 한 줄 없이 0건**이 된다.

```
전:  30건 처리 → confirmed=0   (33ms, 한 행도 안 들어옴)
후:  30건 처리 → confirmed=7   (23%)
```

**셋째, en 이 대조 대상이 아니었다.** active song_album 1,944건 중 **1,565건의
canonical_en 이 기계값**(gtranslate 46%)인데 ja/zh/zh_hant 만 보고 있었다. 가장 큰
칸을 안 보고 있었던 것이다. US 스토어의 trackName 을 대조 대상에 넣었다.

검색어는 칸별로 고른다. ja/zh/hant 는 종전대로 en 우선(K-곡은 라틴으로 저장된다).
**en 칸만 한국어 원제로 찾는다** — 기계값 en 으로 검색하면 자기가 만든 값으로 자기를
확인하는 셈이 된다.

값은 바꾸지 않는다. iTunes 공식 제목과 **글자가 같을 때만** 출처 등급을 올린다.

## 남은 것

- **Spotify Client ID/Secret** — song_album 최대 구멍에 직접. 오너 등록 필요(무료).
- **공공데이터포털 data.go.kr 인증키** — 학교 공식 영문 교명, 공공기관 목록. 오너 등록 필요(무료).
- **행안부 정부조직 영문명 표** — 고시로 확정된 정답. 키 없이 가능.
- **MusicBrainz** — `no_match` 76%가 진짜 미수록으로 보인다(질의는 이미 en 우선으로 정상).
  iTunes 가 같은 코퍼스에서 10배 잘 맞으므로 우선순위는 낮다.
- **응답률 지표 재정의** — 로그의 `item_status` 는 그 시점 상태다. "지금도 못 답하는 것"을
  따로 세는 지표가 필요하다.
