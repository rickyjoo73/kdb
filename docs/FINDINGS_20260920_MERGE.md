# 고정 DB(흡수분) 병합 — 방법과 그 값어치 (2026-09-20)

운영자 지시: **"다른 에이전트는 계속 모니터링하며 업데이트하는 중이고 너는 고정 디비를
병합하는 것이다. 방법을 찾아."**

방법은 찾았다. 그런데 **방법보다 값어치가 먼저 걸린다.** 아래는 전부 운영 실측이다.

## 1. 먼저 안 자리 — ID 는 이미 공유한다

```
kwave_entities 22,558행  ↔  kentity_entities 에 같은 UUID 22,558행   (전수 일치)
```

두 원장은 **같은 UUID 공간**을 쓴다. 서빙 원장의 행은 트리거
`kentity_sync_legacy_identity` 로 공통 원장에 그대로 투영된다.
그래서 병합은 «새 ID 를 발급해 옮기는 일»이 아니다. ID 는 이미 붙어 있다.

## 2. 복사는 구조가 막는다 — 그리고 막는 게 맞다

흡수분의 UUID 로 서빙 원장에 행을 만들어 보았다(트랜잭션 안, 되돌림):

```
INSERT INTO kwave_entities (id, canonical_ko, entity_type, ...) VALUES (흡수분 UUID, '신승리', 'person', ...)
→ ERROR: Entity UUID belongs to another source
```

`kentity_sync_legacy_identity` 가 `origin_system<>'kdb'` 인 UUID 를 거부한다.
**설계가 의도한 것이다.** 복사를 허용하면 같은 대상이 서빙 원장과 공통 원장에서 각각
다른 소유자를 갖고, 두 writer 가 같은 대상을 쓰게 된다 — P5 의 G5 조건(이중 쓰기 0)과
정면으로 충돌한다.

새 UUID 를 발급해 넣는 방법도 있지만 그건 **한 대상이 두 UUID 를 갖는 것**이라 I01 위반이다.

## 3. 그래서 방법은 «복사»가 아니라 «읽기 통합»이다

데이터는 이미 같은 DB 안에 있고 ID 도 공유한다. 남은 것은 **서빙 경로가 공통 원장을
보게 하는 것**이다. 이 방법이 동시성에도 맞다:

| | 다른 에이전트 | 나 |
|---|---|---|
| 하는 일 | `kwave_entities` 행을 **UPDATE** | 읽기 경로에 공통 원장을 **더함** |
| 충돌 | — | 쓰기가 없으므로 잠금 경합 0 |

현재 공통 원장을 읽는 소비자 경로는 `/v1/preparations`(30일 8건)와 `/v1/prepare` 의
`homonym_risk` 신호뿐이다. 트래픽의 99.9%인 `lookup/bulk`·`match`·`prepare` 는 값을
서빙 원장에서만 읽는다. 넓힐 자리가 거기다.

## 4. ★그런데 값어치가 작다 — 이게 이 문서의 결론이다

최근 30일 요청 중 **중국어를 못 답하는** 낱말에 대해, 공통 원장(흡수분)이 답을 가졌는지:

| 게이트 | 낱말 | 요청 |
|---|---|---|
| ① 유형 힌트 일치 + 근거가 항목 지목 (현행 규칙) | **50** | **98** |
| ② 유형 힌트 일치만 (근거 지목 요구 안 함) | 126 | 251 |
| ③ 이름만 맞으면 | 288 | 555 |

같은 기간 **못 답하는 낱말은 4,272개 / 7,139요청**이다. 즉 흡수분 53만 건이 덮는 것은
가장 느슨한 게이트로도 **6.7%**, 안전한 게이트로는 **1.2%** 다.

이유는 새로운 사실이 아니라 이미 기록돼 있던 것이다 — **TDB 는 관광 DB 이고 소비자는
K-콘텐츠를 묻는다**([ROADMAP §1](ROADMAP_20260916.md), [P4.02 ⑧](KDB_P4_02_TRAVEL_SUPPLY.md)).

### ③을 쓰면 안 되는 이유가 실물로 나온다

이름만 맞으면 붙이는 게이트(③)가 새로 잡는 것들:

```
동치미      → location/restaurant  水萝卜辛奇    (소비자가 물은 건 음식·노래)
신데렐라    → location/accommodation 灰姑娘饭店  (경기 파주 모텔)
한빈        → location/district     汉滨          (경남 산청군 신안면)
열린음악회  → location              开放音乐会    (충남 당진·경기 의정부 공연장 2건)
```

**유형 힌트가 이걸 정확히 걸러낸다.** 실측으로 소비자가 `person` 으로 물었는데 흡수분이
`location` 인 것이 **495대상 / 1,484요청**이다. 구분값·유형 설계가 제 일을 한다는 증거이면서,
동시에 그 게이트를 풀면 안 된다는 증거다.

## 5. 사람 슬라이스를 끝까지 따라가 봤다 (요청 최다 버킷)

`person` 힌트로 요청됐고 흡수분도 `person` 인 것: **1,786대상 / 4,674요청**. 그 안을 가르면

| | 대상 | 요청 | 처방 |
|---|---|---|---|
| C. 서빙 원장에 active 로 이미 있다 | 1,641 | 4,373 | 표기 보강 — **그런데 채울 빈칸이 6칸뿐** |
| A. 서빙 원장에 이름 자체가 없다 | 91 | 155 | 등재 — 그런데 §2 가 막는다 |
| B. 있는데 active 가 아니다 | 54 | 146 | **승급 문제 — 다른 에이전트 레인의 몫** |

C 에서 «같은 사람 확정»(양쪽 wikidata QID 일치)은 545쌍인데, 그 545쌍에서 서빙 원장의
빈칸을 흡수분이 채울 수 있는 것은 `zh-Hans` 3칸 · `zh-Hant` 3칸이다.
**QID 가 있으면 위키데이터 레인이 이미 채워 놨기 때문이다.**

`이재명` 이 이 구조를 그대로 보여 준다:

```
kwave_entities  이재명  status=candidate  confidence=0.000  canonical_zh=李在明  ← 값은 이미 있다
```

못 답한 이유는 표기가 없어서가 아니라 **승급이 안 돼서**다(오늘 아침 강등 회수 건과 같은 집합).
흡수분에서 가져올 것이 없다.

## 6. 그래서 권고

1. **큰 공사를 지금 하지 않는다.** 읽기 통합은 옳은 방법이지만 30일 98~251요청을 위해
   소비자 최다 경로를 고칠 자리는 아니다. 전량 복사는 더 아니다 — 서빙 원장에 전량을
   넣으면 `match` 가 훑는 2~3자 순수한글 정본이 **7,680 → 152,165(20배)** 가 된다.
   그 경로는 2,106ms 를 35ms 로 내려놓은 자리다.
2. **증분은 이미 닫았다** — 원본이 더 쓰는 것은 매일 05:30 레인이 따라잡는다
   (`scripts/absorb-tdb-delta.sh`). 흡수 누락 0 은 유지된다.
3. **답이 진짜 없는 4,222낱말 / 7,041요청**이 남은 일이다. 흡수분도 답을 못 가진 자리이므로
   병합이 아니라 **발굴**이 답이다(Spotify 키·공공데이터포털 키가 여기에 직접 들어간다).
4. 그래도 흡수분을 열겠다면 **게이트 ①**(유형 일치 + 항목 지목)로 50낱말부터.
   ②는 근거가 «어느 항목인지» 못 대는 값을 내보내는 것이라 [P4.03-a](KDB_P4_03_PERSON_SUPPLY_AUDIT.md) 가
   막아 둔 자리다. ③은 위 실물 때문에 쓰지 않는다.

## 7. 이 문서가 바꾸는 앞선 판단

- "흡수분의 값어치는 장소가 아니라 사람이다"(P4.02 ⑧) — 맞다. 다만 **사람 쪽도 대부분
  이미 서빙 원장에 있다.** 새로 얻는 것은 91대상뿐이다.
- "고정 DB 를 병합한다"는 작업은 **데이터 이동 작업이 아니라 읽기 경로 설계 작업**이다.
  이동할 것이 거의 없다는 것이 실측 결론이다.
